# 1. 프롬프트 색 구분 — 반복 실수를 환경으로 고치기

## 왜

지난주 실수 세 건이 전부 같은 원인이었다.

```
맥에서 vi 를 열었음 (서버인 줄 알고)
서버에 ~/.ssh/config 를 만들었음 (맥인 줄 알고)
root 로 작업하고 있었음 (일반 계정인 줄 알고)
```

**공통 원인: "지금 내가 어디에 있는가"를 못 알아챔.**

훈련으로 고치는 것보다 **환경으로 고치는 게 확실하다.** 실무에서도 운영 서버는 빨강, 개발은 초록으로 구분해 실수로 운영에 명령 치는 사고를 막는다.

## 설정

```bash
cp ~/.bashrc ~/.bashrc.bak          # 백업 먼저

cat >> ~/.bashrc << 'EOF'

# 프롬프트 — 서버 구분용 (청록)
PS1='\[\e[1;36m\][DB \u@\h \W]\$ \[\e[0m\]'
EOF

source ~/.bashrc                     # 지금 세션에 적용
```

> `>>` 는 **이어쓰기**. `>` 하나면 파일 전체가 날아간다. (`tee -a` 의 `-a` 와 같은 의미)

## PS1 해석

| 부분 | 뜻 |
|---|---|
| `PS1` | 프롬프트 모양을 담는 셸 변수 |
| `\[\e[1;36m\]` | **색 시작** — `36` 이 청록 |
| `\u` | 사용자 이름 |
| `\h` | 호스트명 |
| `\W` | 현재 디렉토리 |
| `\$` | 일반 계정 `$` / **root `#`** — 자동으로 바뀜 |
| `\[\e[0m\]` | **색 종료** — 없으면 이후 글자가 전부 물듦 |

**색 번호**: `31` 빨강 · `32` 초록 · `33` 노랑 · `34` 파랑 · `36` 청록

## 왜 `~/.bashrc` 인가

```
로그인 → bash 시작 → ~/.bashrc 자동으로 읽음 → PS1 적용
```

또 나온 **임시 vs 영구**:

| | |
|---|---|
| 터미널에 `PS1=...` 직접 입력 | 그 세션만 |
| **`~/.bashrc` 에 기록** | **매번 적용** |

`source ~/.bashrc` 는 "지금 당장 다시 읽어라" — nginx의 `reload` 와 같은 성격.

**검증**: `exit` 후 재접속해서 색이 유지되는지 확인.

# 2. 첫 bash 스크립트 — 상태 점검

## 만든 것

```bash
#!/bin/bash
echo "=== $(hostname) 상태 점검 ==="
echo "시각   : $(date '+%Y-%m-%d %H:%M:%S')"
echo "가동   : $(uptime -p)"
echo
echo "--- 서비스 ---"
for s in nginx firewalld chronyd; do
  printf "%-12s %s\n" "$s" "$(systemctl is-active $s)"
done
echo
echo "--- 디스크 ---"
df -hT / | tail -1
echo
echo "--- 실패한 서비스 ---"
systemctl --failed --no-legend || echo "없음"
```

```bash
chmod +x ~/check.sh
~/check.sh
```

## 실행 결과

```
=== rhel-db 상태 점검 ===
시각   : 2026-08-04 13:53:53
가동   : up 13 minutes

--- 서비스 ---
nginx        active
firewalld    active
chronyd      active

--- 디스크 ---
/dev/mapper/rhel-root xfs    34G  3.3G   31G   10% /

--- 실패한 서비스 ---
```

> 실패한 서비스가 없어서 마지막이 비는 것도 정상. **조용한 게 좋은 것.**

## 문법

| | 뜻 |
|---|---|
| `#!/bin/bash` | **셔뱅** — "이 파일은 bash로 실행하라". 없으면 `./` 로 실행 불가 |
| `$(명령)` | 명령 결과를 값으로 치환 |
| `for s in A B C; do ... done` | A·B·C를 하나씩 꺼내 `$s` 에 넣고 반복 |
| `printf "%-12s %s\n"` | 12칸 왼쪽 정렬 + 값 + 줄바꿈 → **표처럼 정렬** |
| `\|\| echo "없음"` | 앞이 실패하면 뒤를 실행 |

## `chmod +x` 가 필요한 이유

```
-rw-r--r--   실행 권한 없음  →  ./check.sh 하면 Permission denied
-rwxr-xr-x   실행 가능       ←  chmod +x 후
```

지난주 배운 `rwx` 의 **`x`** 가 여기서 쓰인다.

## 이게 자동화의 출발점

```
전:  systemctl is-active nginx
     systemctl is-active firewalld
     df -h  ...  매번 5~6개 타이핑

후:  ~/check.sh
```

거창한 게 아니라 **"귀찮은 걸 안 하게 만드는 것"** 이 자동화의 전부다.

### 앞으로 자랄 방향

| 단계 | 내용 |
|---|---|
| **1. 묶기** | 여러 명령을 한 파일로 ← **지금 여기** |
| 2. 판단 넣기 | 디스크 80% 넘으면 경고 표시 |
| 3. 자동 실행 | `cron` 으로 매일 아침 |
| 4. 알림 | 이상하면 텔레그램 메시지 |
| 5. 여러 서버 | 반복문 + `ssh` 로 10대 한 번에 |

# 3. 장애 복구 훈련 #4 — nginx root 경로

## 증상

> "사이트 들어가니까 뭔가 못 찾겠다는 페이지가 떠요."

```
HTTP  (80)  → 200 정상
HTTPS (443) → 404
```

**앞의 세 판과 다른 층의 문제.** 접속도 되고 서비스도 정상인데 페이지만 안 나온다.

## 진단

### ① 범위 좁히기 — 80은 되고 443만 안 됨

두 포트가 **서로 다른 설정을 쓰고 있고, 443쪽만 잘못됐다**는 뜻. 볼 곳이 `posture-ssl.conf` 하나로 줄었다.

### ② 응답 코드 해석

| 코드 | 의미 | 원인 |
|---|---|---|
| 403 | 파일은 있는데 못 읽음 | 권한 · SELinux |
| **404** | **파일 자체를 못 찾음** | **경로 문제** |

### ③ 로그 확인 — 이번에 처음 열어본 파일

```bash
sudo tail -n 20 /var/log/nginx/error.log
```

```
[error] "/usr/share/nginx/www/index.html" is not found (2: No such file or directory),
        client: <IP>, server: <SERVER>, request: "GET / HTTP/1.1"
```

**로그가 답을 그대로 말해줬다.** 추측할 필요가 없었다.

```
실제 위치   /usr/share/nginx/html/     ← html
찾는 위치   /usr/share/nginx/www/      ← www
```

## 원인 · 복구

```nginx
root  /usr/share/nginx/www;    # 고장
root  /usr/share/nginx/html;   # 정상
```

```bash
sudo vi /etc/nginx/conf.d/posture-ssl.conf
sudo nginx -t
sudo systemctl reload nginx
```

## ⭐ 이번 훈련의 수확 — 로그에서 진짜 줄 고르기

로그에 `[error]` 가 두 줄 있었는데 **하나는 노이즈**였다.

```
① .../html/favicon.ico  failed        ← 브라우저 자동 요청. 항상 뜸. 무시
② .../www/index.html    is not found  ← 사용자 요청. 이게 원인
```

②에는 `request: "GET / HTTP/1.1"` 이 붙어 있었다 — **사용자가 홈페이지를 요청했는데 못 찾았다**는 뜻.

> `favicon.ico`, `robots.txt`, `/.env` 같은 요청은 로그에 늘 쌓이는 노이즈다. **실무에서도 이걸 보고 "에러가 났다"고 오판하는 경우가 흔하다.**

## 겪은 실수

```bash
sudo tail -20 파일     # 의도
sudo -20 tail 파일     # 실제로 친 것 → "sudo: 부적절한 옵션 -- '2'"
```

**`sudo` 다음 첫 단어는 실행할 명령이어야 한다.** `-n 20` 형태가 더 안전.

## 응답 코드 4종 — 이제 다 겪음

| 코드 | 의미 | 원인 | 훈련 |
|---|---|---|---|
| **timeout** | 패킷이 중간에서 막힘 | 방화벽 | #1 |
| **refused** | 패킷은 도달, 받는 게 없음 | 리스닝 주소 | #2 |
| **403** | 파일은 있는데 못 읽음 | SELinux 라벨 | #3 |
| **404** | 파일을 못 찾음 | 경로 설정 | **#4** |

**이 표가 웹 장애의 대부분이다.**

# 4. 로그를 볼 때 무엇에 집중하나

로그는 대부분 노이즈다. **거르는 게 실력.**

## ① 시간 — 가장 강력한 필터

증상 발생 시각을 먼저 확정하고 그 앞뒤만 본다.

```bash
sudo tail -n 50 /var/log/nginx/error.log
journalctl --since "10 min ago"
journalctl --since "13:50" --until "14:00"
```

> 이번에도 `13:55` 대 재시작 기록이 잔뜩 있었지만 실제 증상은 `13:59` 였다.

## ② 레벨 — `[error]` 만 먼저

```
[notice]  정상 동작 기록 — 무시
[warn]    경고 — 나중에
[error]   ← 이것부터
```

```bash
sudo grep -i error /var/log/nginx/error.log | tail -20
journalctl -p err -b
```

## ③ "내가 한 요청인가"

```
request: "GET / HTTP/1.1"     ← 사용자 요청  ✅
request: "GET /favicon.ico"   ← 브라우저 자동  ❌ 노이즈
client: <IP>                  ← 누가 요청했나
```

## ④ 뭐가 바뀌었나 — 실무 1순위

**장애 원인의 90%가 최근 변경이다.** 배포? 설정 변경? 패치? 재부팅?

```bash
tail -50 ~/.bash_history          # 뭘 쳤었나
ls -lt /etc/nginx/conf.d/         # 최근 수정된 설정
journalctl -b -1 -p err           # 직전 부팅의 에러
```

## 그리고 항상 — 정상과 비교

```
HTTP 는 되는데 HTTPS 만 안 됨   →  두 설정의 차이
서버 A는 되는데 B만 안 됨       →  두 서버의 차이
```

> **로그를 다 읽으려 하지 말 것.** 필터링해서 5줄로 줄이는 게 목표.

## 민감정보 치환

원본은 그대로 두고 **치환된 사본**을 만들어 공개한다.

```bash
python3 도구/sanitize.py . ~/Desktop/linux-se-notes
```

| 원본 | 치환 |
|---|---|
| 사설 IP | `<LAB_SERVER_IP>` / `<DB_SERVER_IP>` |
| 계정명 | `<LAB_USER>` / `<DB_USER>` |
| SSH 포트 | `<SSH_PORT>` |
| UUID · MAC · 공개키 | `<UUID>` `<MAC>` `...` |
| `~` | `~` |

→ **94곳 치환**, 재검사 0건

### 위험도는 낮았지만 치환한 이유

```
사설 IP(192.168.x.x)   인터넷에서 접근 불가 — 사실 무해
실습 VM 계정            키 인증 + 사설망 — 접근 불가
```

**보안보다 이 세 가지 때문:**
1. **문서가 범용적이 된다** — `<SERVER_IP>` 가 가이드로서 더 낫다
2. **습관** — 실무에서 안 하면 진짜 사고
3. **면접 포인트** — 보안 감각의 증거

> **PDF는 커밋하지 않는다.** 안에 원본 값이 그대로 박혀 있다. `.gitignore` 에 `*.pdf` 추가.
