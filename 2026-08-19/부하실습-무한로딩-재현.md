# 2026-08-19 — 실제 장애를 내 서버에 재현하고 해결하기

> 어느 대학 수강신청 서버가 정각에 터졌다. 사용자로서는 "무한로딩"만 보였다.
> **남의 서버는 찌르지 않는다**는 선을 지키면서, 그 증상을 **rhel2에 그대로 재현**해서
> 밖에서 못 본 원인을 안에서 확인하고, 발생한 장애까지 직접 해결했다.

**오늘 한 일**

```
① 실제 장애의 증상 분석 (공개 정보만)
② 같은 증상을 rhel2 에 재현      — 무한로딩 만들기
③ 방어를 걸어 해결               — 어디서 막느냐 비교
④ 실습 중 발생한 실제 장애 복구   — 장애 훈련 5판
```

---

# 1. 원본 장애 분석 — 밖에서 보이는 것까지

수강신청 서버가 정각에 무한로딩. 남의 서버이므로 **반복 요청·스캔은 하지 않고**, 브라우저가 이미 받는 공개 정보만 읽었다.

```
공개 정보로 확인   온프레미스(단일 IP, CDN 없음), <L4/L7 로드밸런서>,
                 <Java WAS>, <대기열 솔루션> 보유하나 이 경로엔 주석 처리, 학사 DB 연동
확인 불가         왜 느렸나 — WAS 스레드? DB 락? 커넥션 풀?  → 내부 지표가 있어야 안다
```

> ⭐ **밖에서 알 수 있는 건 "어느 층"까지고, "왜"는 내부 지표 없이는 못 간다.**
> 그래서 "DB가 원인" 이라는 말도 확정이 아니라 추론이다. 이걸 확인하려면 재현밖에 없다.

무한로딩을 내는 원인은 최소 셋(스레드 고갈·DB 락·커넥션 풀)이고, 밖에서는 구분되지 않는다. **그래서 rhel2에 직접 만들어봤다.**

---

# 2. 재현 — 무한로딩을 rhel2에 만들다

## 2.1 재료 — 워커 1개짜리 백엔드

```
retro-arcade 백엔드:  uvicorn app:app --workers 1
```

**워커 1개 = 한 번에 요청 하나만 처리.** 대규모 서비스의 WAS 스레드가 다 찬 상황을 축소한 것.

## 2.2 기준선 (정상을 알아야 이상을 안다)

```bash
curl -s -o /dev/null -w 'API: %{http_code} %{time_total}s\n' http://arcade.local/api/health
# → 0.002 ~ 0.016초    ← "정상"
```

## 2.3 부하 — 동시 요청 몰아넣기

이 백엔드엔 방어가 둘 있었다(앱 레벨 rate limit, 쓰기 직렬화). rate limit이 `X-Forwarded-For` 를 신뢰하길래 IP를 위장해 우회하고(=방어 없는 상태) 부하를 줬다.

```bash
# 창1: POST 30개 동시 투입 (IP 위장)
for i in $(seq 1 30); do curl -s ... -H "X-Forwarded-For: 10.0.0.$i" ... & done; wait
# 창2: 그동안 단순 GET 반복 측정
while true; do curl -s -w "GET %{time_total}s\n" .../api/health; sleep 0.3; done
```

## 2.4 결과 — GET 3ms → 5초

```
정상        GET 0.003초
부하 중      GET 5초        ← 1600배
```

GET `/api/health` 는 `{"ok":true}` 만 주는 초간단 요청이다. DB도 거의 안 건드린다. 그런데도 5초.

```
워커 1개 → POST 30개가 그 워커를 차지 → GET 은 줄 뒤에서 대기 → 5초
```

> ⭐ **무한로딩의 정체 = DB가 느린 게 아니라 요청을 처리할 일꾼이 다 찬 것.**
> 이 실습에서 DB는 거의 놀고 있었다. 병목은 워커였다.
> 밖에서 봤으면 "무한로딩 = DB 느림"으로 단정했겠지만, **안에서 보니 아니었다.**

# 3. 해결 — 방어는 "어디서 막느냐"가 전부다

## 3.1 앱 레벨 rate limit 만으로는 부족

방어를 켠 상태로 같은 부하를 줘도 GET 시간이 별로 안 줄었다.

```
앱 레벨 rate limit 은 요청이 워커까지 들어온 뒤 429 를 뱉는다
→ 429 를 뱉는 것도 워커를 거친다 → 워커 경합 자체는 못 막는다
```

## 3.2 nginx 레벨(`limit_req`)로 해결

nginx가 **워커 도달 전에** 쳐내게 했다.

```nginx
# 00-ratelimit.conf (http 블록, include 순서상 먼저 로드되게 00- 접두)
limit_req_zone $binary_remote_addr zone=apilimit:10m rate=5r/s;
# location /api/ 안
limit_req zone=apilimit burst=10 nodelay;
```

같은 부하 재실행:

```
POST 30개 → 201: 9개 / 503: 21개 (nginx 가 즉시 거절)
GET → 0.001 ~ 0.011초   ← 부하 중에도 기준선 유지. 해결됨
```

## 3.3 정리

| 방어 위치 | 무한로딩 | 이유 |
|---|---|---|
| 앱 레벨 (rate_limit) | 못 막음 (5초) | 요청이 워커까지 온 뒤 거절 |
| **프록시 레벨 (limit_req)** | **막음 (3ms 유지)** | 워커 도달 전에 거절 |
| 대기열 (앞단 전용) | 더 강함 | 접속 단계에서 대기 |

**제대로 만든 곳이 대기열을 앞단에 두는 이유가 이것.** 앱까지 들어오면 이미 늦다.
원본 장애도 이 층이 없었거나 꺼져 있었다면 정확히 이 5초 무한로딩이 났을 것이다.

# 4. 장애 훈련 5판 — 실습 중 발생한 실제 장애 복구

부하 실습 후 **테스트 데이터(`load*`)를 지우는 과정에서 실제 장애가 났다.** 훈련이 아니라 실제 상황이라 진단·복구를 그대로 기록한다. (상세: [장애기록 8/19](../장애기록/2026-08.md))

## 증상

```
DELETE 를 해도 API 에 load* 이 계속 나옴.  도중에 사이트 502.
```

## 진단 — 세 번 좁히고서야 원인을 찾음

```
① readonly → SELinux 라벨 탓?    ausearch 결과 <no matches>.  아님
② readonly → 디렉터리 권한 탓?    소유자 정상.  아님
③ load 유지 → 지워진 파일 물고 있나?  /proc/<pid>/fd 확인 → 아님
④ systemctl cat → 진짜 원인:     서비스는 User=arcade, ARCADE_DB=/var/lib/... 를 쓴다
```

```
내가 만진 파일   /opt/retro-arcade/server/arcade.db   (개발 잔재, 0행)
서비스가 쓰는 것  /var/lib/retro-arcade/arcade.db      (여기 데이터가 있었다)
```

**코드는 `/opt`, 데이터는 `/var/lib`** — 리눅스 표준 분리다. `sudo -u arcade` 로 진짜 DB에서 삭제하니 한 번에 끝났다.

## 재발방지

```
① 파일·서비스를 고치기 전에 systemctl cat 으로 User= 와 경로부터 확인한다
   → "보이는 파일" 이 "쓰이는 파일" 이 아닐 수 있다
② 되돌리기 어려운 명령(chown·rm·덮어쓰기) 전에 대상이 맞는지 두 번 확인
③ 서비스 데이터는 그 서비스의 계정으로 만진다 (sudo -u arcade)
④ WAL 모드 SQLite 백업은 파일 하나만 뜨면 빈 껍데기가 될 수 있다
```

# 5. 관통 원리 — "보이는 것 ≠ 쓰이는 것"

이 원리가 오늘 하루에만 반복해서 나왔다.

```
is-active active     →  방화벽은 꺼져 있었다        (8/18)
dpkg -S 없음         →  파일은 있었다              (8/18)
Storage=persistent   →  그런데 /run 에 쓰고 있었다   (8/18)
무한로딩             →  DB 가 아니라 워커 고갈       (오늘)
/opt 의 arcade.db    →  실제로는 /var/lib 를 썼다    (오늘)
```

상태·설정·파일 무엇이든, **표면을 믿지 말고 실제 동작을 확인한다.**

# 6. 얻은 것 / 남은 것

## 얻은 것
```
실제 장애를 내 서버에 재현하고 해결하는 전체 흐름을 경험
무한로딩의 정체 = 워커 고갈 (DB 원인은 확정 아님)
방어는 앞에서 막을수록 강하다 (앱 < 프록시 < 대기열)
"고치기 전에 systemctl cat 으로 확인" 습관
```

## 배포 취약점 (맥 미니 때 반영)
```
client_ip 가 X-Forwarded-For 를 그대로 신뢰 → rate limit 우회 가능
→ nginx 가 X-Forwarded-For 를 덮어써 진짜 접속 IP 만 넣어줘야 한다
```

## 남은 것
```
□ 모니터링에서 봐야 할 지표 = 워커 사용률·대기 큐 (자원 지표보다 먼저)
□ WAL 모드 SQLite 백업 방법 정리 (sqlite3 .backup)
```

> 원본 장애에 대한 판단은 **"증상을 봤다 + 공개 정보로 이렇게 보였다"** 까지다.
> "DB가 원인" 은 확정 못 한 추론이며, 내부 지표는 운영자만 안다.
> 이 문서의 실습·해결은 전부 **내 서버(rhel2)** 에서 한 것이다.
