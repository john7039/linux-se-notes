## [2026-08-03] [훈련] HTTPS 접속 불가 — refused

| | |
|---|---|
| **증상** | 위와 증상은 같으나 즉시 거부(0ms). 서버 안에서는 정상 |
| **영향** | 외부 접근 불가 |
| **탐지** | 훈련 시작 통보 |
| **원인** | nginx의 `listen` 이 **루프백 주소로 한정**됨 — `listen 127.0.0.1:443 ssl;`<br>서버가 자기 자신에게만 열어둔 상태라, 외부 주소로 들어오는 연결은 받지 않는다.<br>`curl https://localhost` → 200 / `curl https://<서버IP>` → 거부 |
| **조치** | `listen 127.0.0.1:443 ssl;` → `listen 443 ssl;` 로 수정 → `sudo nginx -t` → **`sudo systemctl restart nginx`** |
| **검증** | `ss -tln \| grep 443` → `0.0.0.0:443` 인지 확인 + 맥에서 curl → 200 |
| **재발방지** | ① **리스닝 주소를 바꿨을 때는 `reload` 가 아니라 `restart`** — 실제로 이 훈련 준비 중 `reload` 로는 반영되지 않았다<br>② "reload 했는데 왜 안 바뀌지" 싶으면 **설정 파일이 아니라 `ss -tln` 으로 실제 상태를 본다** (설정값 ≠ 실제 동작) |
| **소요** | 미상 (기록 안 함) |

> **⭐ `refused` 와 `timeout` 의 차이가 진단 방향을 완전히 바꾼다.**
> `timeout` = 패킷이 중간에서 막힘 → 방화벽 · 네트워크
> `refused` = 패킷은 도달했는데 받는 게 없음 → 서비스 · 리스닝 설정
> 증상이 같아 보여도(둘 다 "접속 안 됨") 원인 층이 다르다.

## [2026-08-03] [훈련] 페이지는 뜨는데 화면이 깨짐

| | |
|---|---|
| **증상** | HTML은 200인데 CSS/JS가 403. 디자인이 적용되지 않고 버튼도 동작 안 함 |
| **영향** | 사이트 이용 불가 |
| **탐지** | 훈련 시작 통보 |
| **원인** | `assets` 디렉터리의 SELinux 타입이 **`user_tmp_t` 로 변경**됨. nginx(`httpd_t`)는 `httpd_sys_content_t` 만 읽을 수 있어 거부.<br>심어진 고장: `chcon -R -t user_tmp_t /usr/share/nginx/html/assets`<br>**증거 확보**: `ausearch -m AVC` → `avc: denied { read }`, `scontext=httpd_t`, `tclass=file` |
| **조치** | `sudo restorecon -Rv /usr/share/nginx/html/` |
| **검증** | `ls -lZ` 로 `assets` 가 `httpd_sys_content_t` 로 돌아왔는지 + 해당 JS 파일에 직접 curl → 200 |
| **재발방지** | ① **403이면 SELinux를 의심하고 `ausearch -m AVC` 로 증거부터 확보** — "어쩌다 고쳐졌다"가 아니라 원인을 규명한다<br>② `restorecon` 은 **정책에 등록된 경로에서만** 통한다. `/data/web` 같은 비표준 경로는 `semanage fcontext -a` 로 규칙을 먼저 등록해야 한다<br>③ 브라우저 확인은 **강제 새로고침**(`Cmd+Shift+R`) — 캐시 때문에 안 고쳐진 것처럼 보인다 |
| **소요** | 미상 (기록 안 함) |

> **403 = 파일은 있는데 못 읽음 → 권한 · SELinux 라벨.** 아래 404 건(경로 문제)과 층이 다르다.

## [2026-08-05] 백업 스크립트가 조용히 실패

| | |
|---|---|
| **증상** | 스크립트는 정상 종료된 것처럼 보이는데 백업 파일이 갱신되지 않음 |
| **영향** | 백업이 며칠간 안 만들어질 뻔함 |
| **탐지** | 결과 파일의 타임스탬프가 안 바뀐 것을 확인 |
| **원인** | 두 겹이었다.<br>**① 진짜 원인** — `tar --selinux czf ...` 에서 `czf` 를 옵션으로 인식하지 못해 실패 (`--selinux` 뒤에 오면 `-czf` 로 `-` 를 붙여야 한다). 에러: `'-Acdtrux' 옵션 중 하나를 지정해야합니다`<br>**② 문제를 키운 것** — 스크립트 끝의 **`2>/dev/null` 이 그 에러를 숨겼다.** 그래서 스크립트는 정상 종료된 것처럼 보였고 **10분을 헤맸다** |
| **조치** | `2>/dev/null` 을 일시 제거해 에러를 노출 → `tar --selinux -czf` 로 수정 |
| **검증** | 실행 후 **결과 파일의 타임스탬프가 갱신되는지** 확인, `tar tzf` 로 내용물 목록 확인 |
| **재발방지** | ① **개발 중에는 에러를 보이게 두고, 동작을 확인한 뒤에 숨긴다.** `2>/dev/null` 남발은 **cron이 매일 조용히 실패하는데 아무도 모르는 상황**을 만든다<br>② 스크립트 성공 판정은 종료 코드가 아니라 **결과물**로 한다 — 타임스탬프·크기 확인<br>⚠️ **미구현(제안)**: 백업 스크립트에 "결과 파일이 실제로 생겼고 크기가 0이 아닌지" 검증 단계를 추가하면 자동으로 걸린다 |
| **소요** | 약 10분 (원인 규명까지) |

| **원인** | **`tar` 는 기본적으로 SELinux 라벨을 보존하지 않는다.** 백업 시 `--selinux --xattrs` 를 주지 않아 라벨 정보가 아카이브에 안 담겼고, 복구된 파일은 경로 기본 라벨(`usr_t`)을 받았다.<br>`복구된 라벨  usr_t` / `올바른 라벨  httpd_sys_content_t` |
| **조치** | `sudo restorecon -Rv /usr/share/nginx/html/` 로 정책 기준 라벨 복원. 백업 명령에 `--selinux --xattrs` 추가 |
| **검증** | `ls -lZ` 로 `httpd_sys_content_t` 확인. 백업본을 `/tmp` 에 풀었을 때도 `httpd_sys_content_t` 가 나오면 **라벨이 아카이브에 저장된 것** (`/tmp` 기본 라벨은 `user_tmp_t` 이므로 구분됨) |
| **재발방지** | ① 백업은 항상 **`tar --selinux --xattrs -czf`**<br>② 복구 검증에 **`ls -lZ` 를 포함**한다 — 응답 코드만 보면 놓친다<br>③ 복구 후 `restorecon -Rv` 를 절차에 넣는다 |
| **소요** | 미상 (기록 안 함) |

> **⭐ "동작한다"와 "올바르다"는 다르다.**
> 응답이 200이었던 건 RHEL targeted 정책이 `httpd_t` 의 `usr_t` 읽기도 허용하기 때문 — **우연히 동작한 것**이다.
> 정책이 강화되면 어느 날 갑자기 403이 나고, 무엇보다 **의도한 상태가 아니다.**

## [2026-08-10] 리버스 프록시 502 — ② (①을 고친 뒤에도 재발)

| | |
|---|---|
| **증상** | 백엔드는 살아있는데(직접 호출 200) nginx 경유만 502 |
| **영향** | 랭킹 기능 전체 불가 |
| **탐지** | ①을 고친 뒤 기능 재확인 중 발견 |
| **원인** | **SELinux가 nginx → 백엔드 연결을 막았다.**<br>범위 확정: `curl http://127.0.0.1:8090/api/health` → 200(백엔드 정상) vs nginx 경유 → 502 ⇒ **"nginx→백엔드 구간"** 으로 확정<br>nginx 에러 로그: `connect() to 127.0.0.1:8090 failed (13: Permission denied) while connecting to upstream`<br>`127.0.0.1` 은 자기 자신이고 방화벽은 루프백을 막지 않는다 → **일반 권한으로 설명이 안 되는 거부 ⇒ SELinux 의심**<br>`ausearch -m AVC` → `avc: denied { name_connect } comm="nginx" dest=8090`, `scontext=httpd_t`, **`tclass=tcp_socket`** |
| **조치** | `sudo setsebool -P httpd_can_network_connect on` |
| **검증** | `/api` 경유 호출 200, 재부팅 후에도 유지되는지 확인 (`-P` 가 영구 옵션) |
| **재발방지** | ① **SELinux 문제는 종류가 다르다** — 파일 읽기(`tclass=file`)는 `restorecon`(라벨), 포트 연결(`tclass=tcp_socket`)은 `setsebool -P`(기능). 8/3 건과 달리 `restorecon` 으로는 해결 안 됐다<br>② SELinux 해결 3단계: `① 라벨이 틀렸나 → restorecon` / `② 정책에 없는 경로인가 → semanage fcontext` / `③ 기능이 꺼져 있나 → setsebool -P`<br>③ `-P` 를 빼면 재부팅 시 원복된다 (임시 vs 영구)<br>💡 **더 안전한 선택지**: DB 연결만 필요하면 범위가 좁은 `httpd_can_network_connect_db` 를 쓴다 |
| **소요** | 미상 (기록 안 함) |

## [2026-08-18] 재부팅하면 로그가 사라지고 있었다 — 저널이 휘발성 저장

| | |
|---|---|
| **증상** | `journalctl --list-boots` 에 **부팅 기록이 1개뿐**. 어제·그제 재부팅한 기록이 없다 |
| **영향** | **재부팅 전 로그를 전혀 볼 수 없는 상태.** 서버가 죽고 자동 재부팅되면 원인 규명이 불가능하다 |
| **탐지** | 로그 다루기 실습 중 `--list-boots` 를 쳐보다 발견. **증상 신고가 아니라 평소 점검에서 나온 건** |
| **원인** | 저널이 **`/run/log/journal/`(메모리)** 에 저장되고 있었다. `Storage=` 기본값이 `auto` 인데, `auto` 는 **`/var/log/journal/` 이 존재할 때만** 영구 저장을 쓴다. 그 디렉터리가 없었으므로 휘발성으로 동작.<br>근거: `journalctl --header` → `File path: /run/log/journal/...` |
| **조치** | ① `/etc/systemd/journald.conf` 생성 — `[Journal]` / `Storage=persistent`<br>② `mkdir -p /var/log/journal` + `systemd-tmpfiles --create --prefix /var/log/journal` (소유 `root:systemd-journal`, 권한 `2755`)<br>③ `systemctl restart systemd-journald`<br>④ **`journalctl --flush`** — 이게 없으면 전환되지 않는다<br>⑤ `restorecon -v /etc/systemd/journald.conf` — 라벨 정정 |
| **검증** | `journalctl --header` → `/var/log/journal/...` 확인, `/run/log/journal/` 비워짐 확인, **재부팅 후 `--list-boots` 에 `-1` 과 `0` 두 개가 나오는 것까지 확인** |
| **재발방지** | ① **새 서버를 세울 때 저널 영구화를 구축 절차에 넣는다** → 맥 미니 이전 시 반드시 적용<br>② `--list-boots` 로 부팅 기록이 쌓이는지 주기적으로 확인<br>③ `Storage=auto` 는 "알아서 해준다"가 아니라 **"디렉터리가 있으면"** 이라는 조건부다 |
| **소요** | 약 40분 (원인 규명 포함) |

### 진단 과정 — 헛짚은 것 포함

```
① /etc/systemd/journald.conf 가 없다
   → RHEL 10 은 패키지 기본값이 /usr/lib/systemd/journald.conf 로 이동.
     man journald.conf 의 SYNOPSIS 가 우선순위 순으로 경로를 알려준다

② 파일을 만들었는데 무반응
   → 만들기 전에 restart 를 했다.  설정 변경 → 재시작 → 확인 순서를 어김

③ SELinux 라벨이 틀렸다 (etc_t, 정책 기대값은 systemd_conf_t)
   → 그럴듯했지만 sudo ausearch -m AVC -ts recent 결과 <no matches>.
     ⭐ 원인이 아니었다

④ 설정은 읽히는데(systemd-analyze cat-config 로 확인) 여전히 /run
   → tmpfiles 규칙을 보니 /run/log/journal 만 생성한다.
     /var/log/journal 은 h(있을 때만 속성 조정) 규칙뿐 — 아무도 안 만들어준다

⑤ 디렉터리를 만들고 restart 했는데도 안 바뀜
   → systemd-journal-flush.service 가 Type=oneshot, 부팅 때 한 번만 실행됐다.
     journalctl --flush 로 신호를 직접 보내야 전환된다
```

> ⭐ **③이 이 건의 핵심 교훈이다.** 눈에 띄는 이상을 발견했고 그럴듯했지만, **증거를 먼저 확인**하니 원인이 아니었다.
> 바로 `restorecon` 을 하고 "고쳐졌다"고 했다면 **엉뚱한 것을 원인으로 기록**했을 것이다.
> ```
> 그럴듯한 원인 ≠ 진짜 원인.  증거를 먼저 확보한다
> ```
>
> ⑤는 `active (exited)` 의 두 번째 얼굴이다. 같은 날 오전에 `ufw.service` 에서는 **"켜져 있다고 착각하게 만드는"** 함정이었고, 여기서는 **"다시 안 돌아서 반영이 안 되는"** 경우였다.
> **`Type=oneshot` 은 "지금 상태"가 아니라 "그때 한 번 했다"를 뜻한다.**
