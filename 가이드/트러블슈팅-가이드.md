# 트러블슈팅 가이드 — 리눅스 서버 장애 대응

> **증상에서 출발하는** 실무 대응 문서. "무슨 명령이 있더라"가 아니라 **"이 증상이면 어디부터 보나"** 로 구성.
> 모든 걸 외울 필요 없다. **어디를 봐야 할지만 알면 된다.**

**최종 갱신**: 2026-08-03

# PART 1. 진단의 기본 원칙

## 원칙 ① 기준선을 먼저 알아라

**정상 상태를 모르면 뭐가 이상한지 판단할 수 없다.**

```bash
# 평소에 기록해둘 것
systemctl list-units --type=service --state=running   # 어떤 서비스가 떠 있어야 하나
ss -tlnp                                              # 어떤 포트가 열려 있어야 하나
df -hT                                                # 디스크 사용률 평소 수준
sudo firewall-cmd --list-all                          # 방화벽 정책
```

> 서버를 구축한 직후 이 출력을 저장해두면 나중에 비교 기준이 된다.

## 원칙 ② 범위를 좁혀라 — 이게 핵심 기술

한 번에 원인을 찾으려 하지 말고 **가능성을 반씩 잘라낸다.**

```
서버 안에서는 되나?  →  안 되면: 서비스·설정 문제
                    →  되면:   나가는 길 문제 (방화벽·리스닝·네트워크)

다른 서버에서는 되나? →  되면: 이 서버만의 문제
                    →  안 되면: 네트워크·공통 인프라

어제는 됐나?         →  뭐가 바뀌었나 (배포? 설정 변경? 패치?)
```

**"장애 직전에 뭘 바꿨는가"가 원인의 90%다.**

## 원칙 ③ 추측하지 말고 증거를 봐라

```
❌ "방화벽인 것 같은데" → 방화벽 만짐 → 안 고쳐짐 → 다른 것 만짐 → 상황 악화
✅ 로그·상태를 확인 → 원인 특정 → 조치 → 검증
```

로그에 답이 적혀 있는 경우가 대부분이다. **읽지 않고 넘겨짚는 것이 가장 흔한 실수.**

## 원칙 ④ 한 번에 하나씩 바꿔라

여러 개를 동시에 바꾸면 **뭐가 고쳤는지 모른다.** 재발 방지도 불가능해진다.

## 원칙 ⑤ 바꾸기 전에 기록하고, 되돌릴 방법을 확보하라

```bash
sudo cp /etc/xxx/xxx.conf /etc/xxx/xxx.conf.bak.$(date +%Y%m%d)
```

운영 서버에서는 이게 **문서화된 절차(작업계획서 + 롤백 계획)** 로 존재한다.

# PART 2. 만능 첫 5분

**어떤 장애든 서버에 들어가면 일단 이것부터.**

```bash
# 1. 나는 어디에 있고 누구인가
hostname; whoami; date

# 2. 시스템이 살아있나
uptime                          # 부하, 가동시간 (방금 재부팅됐나?)
free -h                         # 메모리
df -hT -x tmpfs -x devtmpfs     # 디스크  ← 장애 원인 1위

# 3. 뭐가 죽었나
systemctl --failed              # 실패한 서비스 목록  ← 매우 유용

# 4. 최근에 무슨 일이 있었나
journalctl -p err -b --no-pager | tail -30    # 이번 부팅 이후 에러만
journalctl --since "30 min ago" -p warning --no-pager | tail -30
```

> **`systemctl --failed`** 와 **`df -h`** 두 개로 실무 장애의 상당수가 즉시 드러난다.

# PART 3. 증상별 대응

## 🔴 서버에 SSH 접속이 안 된다

**먼저 판별**: 어떻게 실패하는가

| 실패 방식 | 의미 | 확인 |
|---|---|---|
| `Connection refused` | 서버는 살아있는데 **sshd가 죽었거나 포트가 다름** | 콘솔 접속 필요 |
| `Connection timed out` | **방화벽·네트워크·서버 다운** | `ping` 부터 |
| `Permission denied (publickey)` | 접속은 되는데 **인증 실패** | 키·권한 문제 |
| `Host key verification failed` | 서버가 재설치됐거나 IP 재사용 | `ssh-keygen -R <IP>` |

```bash
# 클라이언트에서
ping <IP>                       # 살아있나
nc -z <IP> 22                   # 포트가 열려 있나
ssh -v <호스트>                  # 상세 로그 — 어느 단계에서 실패하는지
ssh -G <별칭>                    # 실제 적용되는 설정 확인 (config가 먹었나)
```

**서버 콘솔(UTM/IPMI)로 들어갈 수 있다면:**

```bash
systemctl status sshd
ss -tlnp | grep ssh             # 어느 포트로 듣고 있나
sudo firewall-cmd --list-all    # 포트가 허용돼 있나
sudo semanage port -l | grep ssh # 포트 변경했다면 SELinux 라벨
sudo journalctl -u sshd -n 50
```

### 키 인증이 안 될 때

```bash
ls -ld ~/.ssh                   # 700 이어야 함
ls -l ~/.ssh/authorized_keys    # 600 이어야 함
ls -lZ ~/.ssh/authorized_keys   # SELinux: ssh_home_t 여야 함
sudo restorecon -Rv ~/.ssh      # 라벨 복구
sudo journalctl -u sshd | grep -i "authentication\|denied"
```

> **sshd는 권한이 헐거우면 에러 없이 조용히 키를 무시한다.** "분명 키 넣었는데 비밀번호를 또 묻는" 상황의 1순위 원인.

### ⚠️ SSH 설정을 바꿀 때는

**기존 세션을 절대 닫지 말 것.** 새 터미널로 테스트하고, 되는 걸 확인한 뒤에 닫는다.

## 🔴 웹사이트가 안 뜬다

### ① 실패 방식으로 갈라라 ← 가장 중요

```bash
curl -kv https://<주소> --max-time 8
```

| 결과 | 의미 | 의심할 곳 |
|---|---|---|
| **Connection refused** (즉시) | 패킷은 **도달**, 받는 게 없음 | 서비스 다운, **리스닝 주소·포트** |
| **Connection timed out** (대기 후) | 패킷이 **중간에서 막힘** | **방화벽**, 네트워크, 보안그룹 |
| **TLS 오류** | 연결은 됨 | 인증서 (만료·이름 불일치·체인) |
| **HTTP 코드가 옴** | 서버는 응답함 | 코드별로 아래 참조 |

### ② 범위 좁히기

```bash
# 서버 안에서
curl -sk -o /dev/null -w "%{http_code}\n" https://localhost
```

```
안에서 200, 밖에서 실패  →  나가는 길 (방화벽 / 리스닝 주소)
안에서도 실패            →  웹서버·설정·콘텐츠
```

### ③ 계층별 확인

```bash
systemctl is-active nginx           # 서비스
sudo nginx -t                        # 설정 문법
ss -tln | grep -E ":80|:443"         # 리스닝 — 포트뿐 아니라 주소도 볼 것!
sudo firewall-cmd --list-all         # 방화벽
sudo journalctl -xeu nginx -n 50     # 로그
sudo tail -50 /var/log/nginx/error.log
```

> **`ss -tln` 에서 주소를 반드시 보라.**
> `0.0.0.0:443` = 모든 주소에서 수신 / `127.0.0.1:443` = **자기 자신만** → 외부에서 refused

## HTTP 상태 코드별 대응

| 코드 | 의미 | 확인 순서 |
|---|---|---|
| **403** | 권한 거부 — 파일은 있음 | ① `ls -lZ` (SELinux 라벨) ② 일반 권한 ③ `ausearch -m AVC` ④ 디렉토리 인덱스 설정 |
| **404** | 파일 없음 | ① 문서 루트 경로 확인 ② 파일 실제 존재 여부 ③ 배포 누락 |
| **500** | 앱 내부 오류 | 애플리케이션 로그 |
| **502 Bad Gateway** | 프록시 뒤 백엔드가 죽음 | ① 백엔드 서비스 상태 ② 포트 일치 ③ **SELinux `httpd_can_network_connect`** |
| **504 Gateway Timeout** | 백엔드가 응답은 하는데 느림 | 백엔드 부하, DB 지연, 타임아웃 설정 |

### 403 대응 상세

```bash
ls -lZ /경로/파일               # 라벨 + 권한 동시 확인
sudo ausearch -m AVC -ts recent # SELinux가 막았다는 증거
sudo restorecon -Rv /경로/      # 라벨 복구
```

**403의 두 가지 원인:**
1. 일반 권한 (`rwx`) — 웹서버 사용자가 읽을 수 있어야
2. **SELinux 라벨** — 웹 콘텐츠는 `httpd_sys_content_t`

> `mv` 로 파일을 옮기면 **원본 라벨이 따라온다** → 403.
> `cp` 는 목적지 기본 라벨을 받는다. **배포는 항상 `cp`.**

### 502 대응 상세

```bash
systemctl status <백엔드서비스>
ss -tlnp | grep <백엔드포트>       # 실제로 그 포트에 떠 있나
curl http://127.0.0.1:8000        # 백엔드에 직접 접근되나
sudo setsebool -P httpd_can_network_connect on   # SELinux가 프록시 연결을 막는 경우
```

## 🔴 서비스가 시작되지 않는다

**진단 5단계 — 이 순서로.**

```bash
① systemctl status <서비스> --no-pager     # 에러 메시지 (여기 답이 있는 경우가 많음)
② journalctl -xeu <서비스> -n 50            # 상세 로그
③ <데몬> -t                                 # 설정 문법 (nginx -t, sshd -T, httpd -t)
④ ss -tlnp | grep <포트>                    # 포트 충돌
⑤ sudo ausearch -m AVC -ts recent          # SELinux 차단
```

### 자주 나오는 원인

| 메시지 | 원인 | 조치 |
|---|---|---|
| `Address already in use` | **포트 충돌** — 다른 프로세스가 선점 | `ss -tlnp` 로 범인 찾기 |
| `Permission denied` | 파일 권한 또는 SELinux | `ls -lZ`, `ausearch` |
| `No such file or directory` | 설정에 적힌 경로가 없음 | 경로 오타, 파일 미배포 |
| `Failed to bind to port` | 1024 미만 포트를 일반 사용자로 | root 또는 capability 필요 |
| 설정 문법 오류 | 오타 | `-t` 로 검사 |

> **`systemctl --failed`** 로 실패한 서비스를 한 번에 볼 수 있다.

## 🔴 디스크가 꽉 찼다 ← 실무 장애 1위

**증상**: 서비스가 갑자기 멈춤, 로그 기록 안 됨, DB 쓰기 실패, 로그인 불가

```bash
df -hT -x tmpfs -x devtmpfs        # 어느 파티션이 찼나
df -i                              # ⚠️ inode 고갈 — 용량은 남았는데 파일 생성 불가
```

### 범인 찾기

```bash
sudo du -sh /* 2>/dev/null | sort -rh | head       # 최상위부터 큰 것
sudo du -sh /var/* 2>/dev/null | sort -rh | head   # /var 가 범인인 경우가 많음
sudo du -sh /var/log/* | sort -rh | head

# 큰 파일 찾기
sudo find / -xdev -type f -size +100M -exec ls -lh {} \; 2>/dev/null | sort -k5 -rh | head
```

### 삭제했는데 용량이 안 줄어들 때 ⚠️

**프로세스가 파일을 열고 있으면 삭제해도 공간이 반환되지 않는다.**

```bash
sudo lsof +L1 | head              # 삭제됐지만 열려 있는 파일
# → 해당 프로세스를 재시작해야 공간이 반환됨
```

### 조치

```bash
sudo journalctl --vacuum-size=200M      # journald 로그 정리
sudo journalctl --vacuum-time=7d
sudo dnf clean all                       # 패키지 캐시
```

### 재발 방지 — 이게 진짜 조치

```bash
# logrotate 설정 확인
cat /etc/logrotate.conf
ls /etc/logrotate.d/

# journald 크기 제한
sudo vi /etc/systemd/journald.conf
#   SystemMaxUse=500M
sudo systemctl restart systemd-journald
```

> **디스크 사용률 80% 초과 시 알림**을 걸어두는 것이 표준. 꽉 찬 뒤에 대응하면 이미 장애다.

## 🔴 서버가 느리다

```bash
uptime                    # load average — 코어 수와 비교 (4코어면 4 이상이 부하)
top    (또는 htop)         # 실시간. P=CPU정렬, M=메모리정렬
free -h                   # 메모리·swap
vmstat 1 5                # si/so(스왑 입출력)가 크면 메모리 부족
iostat -x 1 5             # %util 100%면 디스크 병목  (sysstat 패키지)
ss -s                     # 소켓 요약 — 연결 수 폭증 여부
```

### 원인별 판단

| 지표 | 의심 |
|---|---|
| load 높음 + CPU 높음 | 연산 폭주 프로세스 |
| load 높음 + CPU 낮음 | **I/O 대기** (디스크·네트워크) |
| swap 사용 증가 | 메모리 부족 → 스와핑으로 급격히 느려짐 |
| `%iowait` 높음 | 디스크 병목 |

### 메모리 부족 / OOM

```bash
sudo dmesg -T | grep -i "out of memory\|oom-killer"
sudo journalctl -k | grep -i oom
```

**OOM Killer가 프로세스를 죽였다면** 메모리 증설 또는 앱 튜닝이 필요하다. "서비스가 이유 없이 죽었다"의 흔한 원인.

## 🔴 재부팅했더니 설정이 사라졌다

**임시 설정을 했기 때문이다.** 리눅스 전반의 패턴:

| 영역 | 임시 (재부팅에 사라짐) | 영구 |
|---|---|---|
| 서비스 실행 | `systemctl start` | **`systemctl enable`** |
| 방화벽 | `firewall-cmd --add-xxx` | **`--permanent`** + `--reload` |
| 마운트 | `mount` | **`/etc/fstab`** |
| SELinux boolean | `setsebool` | **`setsebool -P`** |
| SELinux 라벨 | `chcon` | **`semanage fcontext`** + `restorecon` |
| 네트워크 | `ip addr add` | **`nmcli connection modify`** |
| 커널 파라미터 | `sysctl -w` | **`/etc/sysctl.d/`** |

### 확인

```bash
systemctl is-enabled <서비스>
sudo firewall-cmd --permanent --list-all
getsebool -a | grep <이름>
cat /etc/fstab
```

## 🔴 부팅이 안 된다 / emergency mode

**가장 흔한 원인: `/etc/fstab` 오타.** 없는 장치를 마운트하려다 부팅이 멈춘다.

### 대응 (콘솔에서)

```bash
# emergency mode 진입 시 root 비밀번호 입력
journalctl -xb                    # 부팅 실패 원인
mount -o remount,rw /             # 쓰기 가능하게
vi /etc/fstab                     # 문제 줄 수정 또는 주석 처리
mount -a                          # 검증
reboot
```

### 예방 — 이게 전부다

```bash
sudo mount -a                     # fstab 수정 후 반드시. 에러 없이 통과해야 안전
findmnt --verify --verbose        # 항목별 검사
```

> **`mount -a` 검증 없이 재부팅하지 말 것.** 리눅스 초보 사고 1위.
> `nofail` 옵션을 쓰면 마운트 실패해도 부팅은 진행된다 (중요하지 않은 볼륨에 유용).

## 🔴 네트워크가 안 된다

**아래에서 위로 하나씩 확인.**

```bash
ip link                          # ① 인터페이스가 존재하고 UP 인가 (NO-CARRIER?)
ip -4 -brief addr                # ② IP가 있나
ip route                         # ③ 기본 게이트웨이가 있나
ping -c3 <게이트웨이>             # ④ 게이트웨이까지 가나
ping -c3 8.8.8.8                 # ⑤ 외부 IP로 가나
ping -c3 google.com              # ⑥ 이름 해석이 되나  ← 여기서만 실패하면 DNS
cat /etc/resolv.conf             # DNS 서버 설정
```

| 어디까지 되나 | 원인 |
|---|---|
| ①에서 막힘 | 케이블·가상 NIC 미연결, 드라이버 |
| ②에서 막힘 | IP 미할당 — `nmcli` 설정 |
| ④에서 막힘 | 게이트웨이·라우팅·스위치 |
| ⑤에서 막힘 | 상위 네트워크·방화벽 |
| **⑥에서만 막힘** | **DNS 문제** — `resolv.conf`, DNS 서버 |

### NetworkManager

```bash
nmcli device status              # 장치 상태
nmcli connection show            # 프로필 목록
nmcli connection show <이름>      # 상세
sudo nmcli connection up <이름>   # 활성화
sudo nmcli connection reload     # 파일 직접 수정했을 때
```

> 설정 파일을 직접 고쳤으면 **`reload` + `up`** 을 해야 반영된다.

## 🔴 시각이 이상하다

**증상**: 인증서 오류, 로그 시각 불일치, cron 미실행, 인증 실패

```bash
date
timedatectl                      # 동기화 상태
chronyc tracking                 # 오차
chronyc sources                  # 참조 NTP 서버
sudo chronyc makestep            # 즉시 강제 동기화
sudo systemctl restart chronyd
```

> **VM을 일시정지했다 재개하면** 그 사이 시간만큼 시계가 뒤처진다.
> 시각이 틀리면 TLS 인증서가 "아직 유효하지 않음"으로 거부될 수 있다.

## 🔴 인증서 문제

```bash
# 만료일·주체 확인
openssl x509 -in /경로/cert.crt -noout -subject -dates -ext subjectAltName

# 서버에 실제 적용된 인증서 확인
openssl s_client -connect <주소>:443 -servername <도메인> </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -dates
```

| 오류 | 원인 |
|---|---|
| `certificate has expired` | 만료 — 갱신 필요 |
| `self-signed certificate` | 자체 서명 — 공개 서비스에는 부적합 |
| `hostname mismatch` | CN/SAN이 접속 주소와 다름 |
| `unable to get local issuer` | 중간 인증서(체인) 누락 |
| `not yet valid` | **서버 시계가 과거** 또는 인증서가 미래 발급 |

> **Let's Encrypt는 90일 만료.** `certbot` 자동 갱신이 도는지 반드시 확인:
> ```bash
> systemctl list-timers | grep certbot
> sudo certbot renew --dry-run
> ```

## 🔴 권한 거부 (Permission denied)

**세 층을 순서대로 확인한다.**

```bash
# ① 일반 권한
ls -l <경로>
namei -l <전체경로>              # 상위 디렉토리까지 전부 확인 ← 유용

# ② SELinux
ls -lZ <경로>
sudo ausearch -m AVC -ts recent

# ③ 그 명령 자체가 root를 요구하는가
sudo <명령>
```

> **경로 중간의 디렉토리에 `x` 권한이 없으면** 최종 파일 권한이 아무리 열려 있어도 접근이 안 된다. `namei -l` 이 이걸 한 번에 보여준다.

> **시스템 전체 상태를 조회하는 명령은 대부분 root가 필요하다** — 방화벽 정책, 감사 로그, 다른 사용자의 프로세스. "조회니까 괜찮겠지"가 아니다.

**어떤 장애든 이 층을 따라 내려가면 반드시 원인이 나온다.**

```
7. 애플리케이션    앱 로그, 코드, DB 연결
6. SELinux        ls -lZ, ausearch, getsebool
5. 서비스         systemctl, journalctl, 설정 문법(-t)

```

**아래(1)에서 위(7)로 올라가며 확인**하는 게 정석이다. 위부터 뒤지면 시간을 낭비한다.

# PART 4.5. 로그를 볼 때 무엇에 집중하나

**로그는 대부분 노이즈다. 거르는 게 실력이다.**

## ① 시간 — 가장 강력한 필터

증상 발생 시각을 먼저 확정하고 **그 앞뒤만** 본다.

```bash
sudo tail -n 50 /var/log/nginx/error.log
journalctl --since "10 min ago"
journalctl --since "13:50" --until "14:00"
```

## ② 레벨 — `[error]` 만 먼저

```
[notice]  정상 동작 기록 — 무시
[warn]    경고 — 나중에
[error]   ← 이것부터
```

```bash
sudo grep -i error /var/log/nginx/error.log | tail -20
journalctl -p err -b
```

## ③ "내가 한 요청인가"

로그에는 봇·브라우저 자동 요청이 섞인다.

```
request: "GET / HTTP/1.1"     ← 사용자 요청  ✅
request: "GET /favicon.ico"   ← 브라우저 자동  ❌ 노이즈
client: <IP>                  ← 누가 요청했나
```

> `favicon.ico`, `robots.txt`, `/.env` 같은 요청은 늘 쌓인다. **이걸 보고 "에러가 났다"고 오판하는 경우가 흔하다.**

## ④ 뭐가 바뀌었나 — 실무 1순위

**장애 원인의 90%가 최근 변경이다.** 배포? 설정 변경? 패치? 재부팅?

```bash
tail -50 ~/.bash_history          # 뭘 쳤었나
ls -lt /etc/nginx/conf.d/         # 최근 수정된 설정 파일
journalctl -b -1 -p err           # 직전 부팅의 에러
```

## ⑤ 그리고 항상 — 정상과 비교

```
HTTP 는 되는데 HTTPS 만 안 됨   →  두 설정의 차이를 보면 됨
서버 A는 되는데 B만 안 됨       →  두 서버의 차이
```

**비교 대상이 있으면 범위가 즉시 절반으로 줄어든다.**

> **로그를 다 읽으려 하지 말 것.** 필터링해서 5줄로 줄이는 게 목표다.

# PART 5. 로그 위치 지도

| 대상 | 위치 |
|---|---|
| **전체 (systemd)** | `journalctl` |
| 이번 부팅만 | `journalctl -b` |
| 에러만 | `journalctl -p err -b` |
| 특정 서비스 | `journalctl -u <서비스>` |
| 실시간 추적 | `journalctl -f` |
| 시간 범위 | `journalctl --since "1 hour ago" --until "10 min ago"` |
| 커널 | `dmesg -T` / `journalctl -k` |
| 인증·로그인 | `/var/log/secure` |
| 시스템 일반 | `/var/log/messages` |
| **SELinux 감사** | `/var/log/audit/audit.log` → `ausearch` |
| nginx | `/var/log/nginx/{access,error}.log` |
| dnf | `/var/log/dnf.log` |
| 부팅 | `journalctl -b -1` (직전 부팅) |

## 자주 쓰는 journalctl 조합

```bash
journalctl -xeu nginx -n 50            # 특정 서비스 최근 50줄, 상세
journalctl -p err -b --no-pager        # 이번 부팅 에러만
journalctl --since "30 min ago"        # 최근 30분
journalctl -f -u nginx                 # 실시간 추적
journalctl -b -1 -p err                # 직전 부팅의 에러 (재부팅 원인 추적)
```

# PART 6. 명령어 레퍼런스

## 상태 파악

```bash
hostname; whoami; date          # 나는 어디에 누구인가
uptime                          # 가동시간·부하
systemctl --failed              # 실패한 서비스
df -hT; df -i                   # 디스크 · inode
free -h                         # 메모리
ss -tlnp                        # 리스닝 (sudo 필요)
ps aux --sort=-%cpu | head      # CPU 상위
ps aux --sort=-%mem | head      # 메모리 상위
```

## 서비스

```bash
systemctl status/start/stop/restart/reload <서비스>
systemctl enable --now <서비스>        # 자동시작 + 지금 시작
systemctl is-active / is-enabled <서비스>
systemctl list-units --type=service --state=running
systemctl daemon-reload               # 유닛 파일·fstab 변경 후
```

**`reload` vs `restart`**

| | 동작 | 접속 중 사용자 |
|---|---|---|
| `reload` | 설정만 다시 읽음 | 안 끊김 |
| `restart` | 프로세스 재시작 | 순간 끊김 |

> 리스닝 주소·포트 변경은 `reload` 로 반영 안 될 수 있다 → `ss -tln` 으로 실제 확인.

## 설정 검증 — 적용 전에 반드시

```bash
nginx -t                        # nginx 문법
sshd -T                         # sshd 최종 적용값
httpd -t                        # apache
mount -a                        # fstab
findmnt --verify                # fstab 상세 검증
ssh -G <별칭>                    # ssh 클라이언트 최종 적용값
visudo -c                       # sudoers 문법
```

> **`-T` / `-G` 는 "파일에 뭐라고 적혀 있는지"만 보여준다.** 재시작하지 않았다면 실제 동작은 다를 수 있다. **최종 확인은 실제로 시도해보는 것.**

## 네트워크

```bash
ip link; ip -4 -brief addr; ip route
ss -tlnp                        # 리스닝 (주소도 볼 것)
ss -tnp                         # 연결된 세션
nc -z <IP> <포트>                # 포트 열림 확인
curl -kv <URL> --max-time 8     # 실패 방식 확인
dig <도메인> / nslookup <도메인>  # DNS
tcpdump -i any port 443 -nn     # 패킷 캡처 (최후의 수단)
```

## 방화벽

```bash
sudo firewall-cmd --list-all
sudo firewall-cmd --permanent --list-all       # 저장된 설정
sudo firewall-cmd --permanent --add-service=https
sudo firewall-cmd --reload
sudo firewall-cmd --add-port=8080/tcp --timeout=5m   # 임시 (자동 닫힘)
```

## SELinux

```bash
getenforce
ls -lZ <경로>
ps -eZ | grep <프로세스>
sudo ausearch -m AVC -ts recent
sudo sealert -a /var/log/audit/audit.log       # 해결책까지 제시
sudo restorecon -Rv <경로>
getsebool -a | grep <키워드>
sudo setsebool -P <이름> on
sudo semanage port -l | grep <서비스>
sudo semanage fcontext -a -t <타입> "<경로>(/.*)?"
```

**SELinux 해결 3단계**

```
① 라벨이 틀렸나?        → restorecon
② 정책에 없는 경로인가?  → semanage fcontext + restorecon
③ 기능이 꺼져 있나?     → setsebool -P
```

## 디스크

```bash
df -hT; df -i
lsblk; lsblk -f
sudo du -sh /* | sort -rh | head
sudo lsof +L1                   # 삭제됐지만 열려 있는 파일
sudo pvs; sudo vgs; sudo lvs    # LVM
sudo lvextend -r -L +5G /dev/<VG>/<LV>
```

## 프로세스

```bash
pgrep -af <이름>                 # 죽이기 전에 반드시 확인
kill <PID>; kill -9 <PID>
sudo lsof -i :<포트>             # 그 포트를 누가 쓰나
sudo fuser -v <파일>             # 그 파일을 누가 쓰나
```

> ⚠️ **`pkill -f <패턴>` 은 자기 자신의 명령줄까지 매칭해 세션을 죽일 수 있다.** `pgrep` 으로 먼저 확인하고 PID로 죽이는 게 안전하다.

# PART 7. 하지 말아야 할 것

| 하면 안 되는 것 | 왜 | 대신 |
|---|---|---|
| **`setenforce 0`** 로 SELinux 끄기 | 문제 해결이 아니라 **보안을 끈 것**. 면접에서 감점 | `restorecon` / `semanage` / `setsebool` |
| **`chmod 777`** | 아무나 접근 가능. "생각하기 귀찮아서 다 열었다"는 신호 | 그룹 + setgid |
| **원인 모르고 재시작** | 증상만 사라지고 재발. 원인 규명 기회도 사라짐 | 로그부터 확인 |
| **여러 개 동시에 변경** | 뭐가 고쳤는지 모름 | 한 번에 하나 |
| **백업 없이 설정 수정** | 되돌릴 수 없음 | `cp *.bak` |
| **검증 없이 `reload`/재부팅** | 서비스 전체 다운 | `nginx -t`, `mount -a` |
| **운영 서버에서 바로 실험** | 사고 | 개발/스테이징에서 먼저 |
| **`rm -rf` 를 변수와 함께** | 변수가 비면 `/` 삭제 | 경로를 직접 확인하고 실행 |

> **`setenforce 0` 은 원인 파악용으로 잠깐 쓰는 건 실무에서도 한다.** 껐을 때 문제가 사라지면 "SELinux가 원인"이 확인된다. **확인 후 반드시 `setenforce 1` 로 되돌리고 제대로 고친다.**

# PART 8. 장애 보고서 양식

**대응이 끝나면 반드시 기록한다.** 이게 쌓이면 포트폴리오이자 재발 방지 자산이 된다.

```
[YYYY-MM-DD HH:MM] <장애 제목> (지속 시간)

증상    : 사용자가 겪은 현상 (기술 용어 말고 관찰된 사실)
영향    : 어떤 서비스가 어느 정도 영향받았는가
탐지    : 어떻게 알게 됐는가 (알림 / 사용자 신고 / 정기점검)
원인    : 근본 원인. 추측이 아니라 근거(로그·상태)와 함께
조치    : 실제로 실행한 명령·작업
검증    : 복구를 어떻게 확인했는가
재발방지 : 같은 일이 다시 안 생기게 하려면 무엇을 바꿨는가
```

## 예시

```
[2026-08-03 15:27] 웹 정적 리소스 접근 불가 (약 10분)

증상    : 페이지는 로드되나 CSS/JS가 적용되지 않음. 기능 동작 불가
영향    : 서비스 이용 불가 (화면은 뜨나 사용 불가 상태)
탐지    : 사용자 신고
원인    : /usr/share/nginx/html/assets 의 SELinux 컨텍스트가
         httpd_sys_content_t → user_tmp_t 로 변경됨.
         nginx(httpd_t)의 파일 open 거부 (AVC 로그로 확인)
조치    : sudo restorecon -Rv /usr/share/nginx/html/
검증    : 해당 리소스 HTTP 200 확인, 브라우저 정상 렌더링 확인
재발방지 : 배포 시 cp 사용(mv 금지), 배포 후 ls -lZ 라벨 검증을 절차에 추가
```

> **"백업이 있다"보다 "복구해봤다"가 강하듯, "안다"보다 "겪고 기록했다"가 강하다.**

# 부록. 빠른 참조 — 증상 → 첫 명령

| 증상 | 첫 명령 |
|---|---|
| 뭔가 이상하다 | `systemctl --failed` + `df -h` |
| SSH 안 됨 | `ping` → `nc -z <IP> 22` → `ssh -v` |
| 웹 안 뜸 | `curl -kv <URL>` (refused/timeout 판별) |
| 403 | `ls -lZ` → `ausearch -m AVC -ts recent` |
| 502 | `systemctl status <백엔드>` → `ss -tlnp` |
| 서비스 시작 실패 | `systemctl status` → `journalctl -xeu` |
| 느림 | `uptime` → `top` → `free -h` → `vmstat 1 5` |
| 디스크 참 | `df -hT` → `df -i` → `du -sh /* \| sort -rh` |
| 부팅 실패 | 콘솔 → `journalctl -xb` → `/etc/fstab` |
| 네트워크 안 됨 | `ip addr` → `ip route` → `ping GW` → `ping 8.8.8.8` → `ping 도메인` |
| 인증서 오류 | `openssl x509 -noout -dates` + `date` |
| 재부팅 후 사라짐 | `systemctl is-enabled` / `firewall-cmd --permanent --list-all` |
