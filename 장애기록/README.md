# 장애 기록

운영하면서 겪은 문제를 한 건씩 남긴다. **월별 파일**에 누적한다.

```
장애기록/
├── README.md      ← 형식과 작성 원칙 (이 파일)
├── 2026-07.md
└── 2026-08.md
```

---

## 왜 따로 모으나

| | |
|---|---|
| **검색성** | "이 에러 전에 봤는데" → 한 곳에서 찾는다 |
| **패턴** | 반복되는 실수 유형이 드러난다 |
| **포트폴리오** | 면접에서 할 이야기. 신입 중에 이걸 가진 사람은 드물다 |
| **실무 그대로** | 회사는 장애 이력을 별도로 관리한다 |

> **"백업이 있다"보다 "복구해봤다"가 강하듯, "안다"보다 "겪고 기록했다"가 강하다.**

---

## 형식 — 한 건에 10줄이면 충분

길게 쓰면 안 쓰게 된다. **짧게, 대신 매번.**

```markdown
## [YYYY-MM-DD] 제목 — 한 줄로 무슨 일이었는지

| | |
|---|---|
| **증상** | 사용자가 겪은 현상. 기술 용어 말고 관찰된 사실 |
| **영향** | 어떤 기능이 어느 정도 안 됐나 |
| **탐지** | 어떻게 알게 됐나 (알림 / 검증 중 / 신고) |
| **원인** | 근본 원인. **추측이 아니라 근거(로그·상태)와 함께** |
| **조치** | 실제로 실행한 명령 |
| **검증** | 복구를 어떻게 확인했나 |
| **재발방지** | 같은 일이 다시 안 생기게 뭘 바꿨나 |
| **소요** | 발견부터 복구까지 |
```

---

## 작성 원칙

### ① 원인은 근거와 함께

```
❌ "SELinux 때문이었다"
✅ "AVC 로그에 name_connect denied, tcp_socket 확인"
```

**추측과 확인을 구분한다.** 근거가 없으면 "원인 미상"이라고 쓰는 게 낫다.

### ② 재발방지를 반드시 채운다

여기가 비어 있으면 **같은 장애가 또 난다.** 그리고 이 칸이 문서의 값어치를 만든다.

```
문서에 절차 추가 / 스크립트에 검증 추가 / 알림 임계값 설정 / 설정 변경
```

### ③ 훈련도 기록한다

일부러 만든 장애도 진단 과정은 실제와 같다. **[훈련]** 표시만 붙인다.

### ④ 사소해 보여도 남긴다

"오타였다", "sudo를 빼먹었다" 같은 것도 **반복되면 패턴**이다. 3번 반복되면 그건 습관 문제이므로 환경으로 고쳐야 한다.

## 소요 시간을 꼭 적을 것

```
같은 유형이 두 번째 났을 때 얼마나 빨라졌는가
```

**이 숫자가 실력의 증거다.** 진단 속도는 늘지만 눈에 안 보이므로, 적어두지 않으면 알 수 없다.
