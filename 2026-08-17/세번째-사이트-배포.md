# 2026-08-17 — 세 번째 사이트 배포: 순서를 손으로 익히기

> 새로운 기술을 배운 날이 아니다. **이미 두 번 해본 것을 다시 한 날**이다.
> 목적은 "무엇을 하는가"가 아니라 **"어떤 순서로 하는가"** 를 몸에 붙이는 것.

**결과**

```

http://arcade.local     →  /var/www/retro-arcade
https://<DB_SERVER_IP>  →  /usr/share/nginx/html
```

같은 서버, 같은 nginx, 같은 80번 포트. **소요 1시간 19분** (14:39 → 15:58).

# 0. 사이트 하나를 올릴 때 정해야 하는 것

설정 파일을 쓰기 전에, 결정해야 할 것이 **네 가지**다. 이건 어떤 사이트를 올리든 똑같다.

```
1. 파일을 어디에 둘 것인가
2. 이 사이트를 어떻게 구분해서 부를 것인가
3. 방화벽을 통과시킬 것인가
4. SELinux가 이 파일을 읽게 할 것인가
```

3·4번은 **RHEL 계열이라서 반드시 나오는 항목**이다. 우분투 기준 예제를 따라 하다 막히는 지점이 대개 여기다.

## 사이트를 구분하는 세 가지 방법

2번의 선택지:

| 방식 | 방법 | 비고 |
|---|---|---|
| **이름 기반** | 한 IP·한 포트에 여러 도메인. `Host` 헤더로 구분 | **실무는 거의 다 이것** |
| 포트 기반 | `:8080`, `:8081` 로 나눔 | 포트를 외워야 함 |
| IP 기반 | 서버에 IP를 여러 개 붙임 | IP가 아까움 |

이름 기반이면 서버 하나에 사이트를 수십 개 올려도 된다. 오늘도 이름 기반.

# 1. 순서 — 아래에서 위로

세 가지 접근이 있는데, 배울 때는 **아래에서 위로**가 맞다.

| 방식 | 흐름 | 평가 |
|---|---|---|
| **아래에서 위로** | 폴더 → 콘텐츠 → 설정 → 이름 | 배우기 제일 좋음 |
| 위에서 아래로 | 설정 먼저 쓰고 오류 따라가며 채움 | 익숙해지면 빠름 |
| 복사해서 고치기 | 기존 conf 복사 → 이름만 바꿈 | 빠르지만 **안 남음** |

## 왜 폴더부터인가

nginx 설정에 문서 루트를 적어놨는데 그 폴더가 없으면, **nginx는 정상적으로 뜬다.** 대신 접속하면 403이나 404가 난다.

그러면 "설정이 틀렸나?" 하고 엉뚱한 곳을 뒤지게 된다. **있는 것을 가리키게 해놓고 시작**하는 편이 낫다.

# 2. 문서 루트

```bash
sudo mkdir /var/www/notes
```

`sudo` 없이 하면 거부된다. 이게 정상이다.

```
mkdir: `/var/www/notes' 디렉터리를 만들 수 없습니다: 허가 거부
```

## 디렉터리에서의 rwx

파일과 뜻이 다르다. 이걸 알아야 위 오류가 이해된다.

| | 디렉터리에서의 뜻 |
|---|---|
| `r` | 안에 뭐가 있는지 **목록 보기** (`ls`) |
| `w` | 안에 **파일을 만들거나 지우기** |
| `x` | 그 디렉터리 **안으로 들어가기** (`cd`) |

`/var/www` 는 `drwxr-xr-x root root` 다. 일반 사용자에게는 `r-x` 만 있어서 들어가고 볼 수는 있지만 **만들지는 못한다.**

> `w` 는 "디렉터리 안 목록을 바꿀 권한"이지 "파일 내용을 바꿀 권한"이 아니다.
> 그래서 **디렉터리에 `w` 가 있으면 남의 파일도 지울 수 있다.** `/tmp` 가 특별 취급을 받는 이유가 이것 (sticky bit).

## 통과하는 두 가지 길

```
① sudo 로 잠깐 관리자 권한을 빌린다     ← 이걸 쓴다
② /var/www 의 권한을 헐겁게 바꾼다      ← 하지 말 것
```

**②는 안 된다.** 특히 `chmod 777` 은 시스템 디렉터리에 절대 금지. 나중에 반드시 문제가 되고, 면접에서도 감점이다.

## 위치 선택이 SELinux를 결정한다

만들고 나서 라벨을 확인했다.

```bash
ls -ldZ /var/www /var/www/notes
```

```
/var/www        drwxr-xr-x root root  ...:httpd_sys_content_t:s0
/var/www/notes  drwxr-xr-x root root  ...:httpd_sys_content_t:s0
```

`httpd_sys_content_t` = **"웹서버가 읽어도 되는 파일"**.

**SELinux 라벨은 부모 디렉터리에서 상속된다.** `/var/www` 가 이미 그 라벨이라 새 폴더도 자동으로 받았다. 그래서 `restorecon` 이 필요 없었다.

> 8/10에는 `restorecon` 을 써야 했다. 그때와 뭐가 달랐나 — **위치**다.
> `/home/...` 나 `/srv/...` 에 만들었으면 다른 라벨이 붙어서 nginx가 403을 뱉었을 것이다.
> **문서 루트를 `/var/www` 아래 두면 SELinux 문제 하나를 미리 피한다.**

`/usr/share/nginx/html` 은 **패키지가 설치한 기본 페이지 자리**라 nginx 업데이트 때 덮어쓰일 수 있다. 내 콘텐츠는 `/var/www` 로.

# 3. 콘텐츠

```bash
sudo vi /var/www/notes/index.html
```

내용은 `<h1>notes</h1>` 한 줄. 이건 웹 만들기가 아니라 **배포 훈련**이라 내용은 중요하지 않다.

## 리다이렉션은 sudo가 안 통한다

```bash
sudo echo "<h1>notes</h1>" > /var/www/notes/index.html   # ✗ 거부됨
```

`>` 는 sudo가 아니라 **내 셸이 처리**한다. 셸은 일반 사용자 권한이라 파일을 못 연다.

```bash
echo "<h1>notes</h1>" | sudo tee /var/www/notes/index.html   # ✓
```

`tee` 에게 sudo를 주는 것이 표준 관용구다. 덧붙이려면 `tee -a`.

---

# 4. nginx 설정

```bash
sudo vi /etc/nginx/conf.d/notes.conf
```

```nginx
server {
    listen       80;
    server_name  notes.local;
    root         /var/www/notes;
}
```

**필요한 정보는 세 가지뿐**이다.

| 정보 | 지시어 |
|---|---|
| 포트 | `listen` |
| 이름 | `server_name` |
| 폴더 위치 | `root` |

- 각 줄 끝 **세미콜론** — nginx 설정에서 제일 흔한 실수
- `index index.html;` 은 기본값이라 생략 가능
- **포트 80은 arcade.local 과 겹쳐도 된다.** 이름 기반이라 nginx가 `Host` 헤더로 갈라준다

---

# 5. 문법 검사 — 반드시 sudo로

```bash
sudo nginx -t
```

```
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful
```

**설정을 바꾸고 재시작하기 전에 항상 이걸 먼저 돌린다.** 문법이 틀린 채로 재시작하면 nginx가 아예 안 뜨고, 그러면 **멀쩡하던 사이트들까지 같이 죽는다.**

sudo 없이 돌리면 권한 오류가 잔뜩 나온다 → 자세한 것은 [막힌지점 문서](막힌지점-5가지.md) 3번.

---

# 6. 반영 — reload vs restart

```bash
sudo systemctl reload nginx
```

| | 동작 | 접속 중인 사용자 |
|---|---|---|
| `reload` | 설정만 다시 읽음 | **끊기지 않음** |
| `restart` | 프로세스를 죽였다 다시 띄움 | **끊김** |

운영 서버에서는 **거의 항상 reload**. 지금 서버에는 사이트가 셋이라, restart 하면 나머지 둘도 잠깐 죽는다.

> 성공하면 아무것도 출력되지 않는다. **리눅스 명령어는 조용한 게 정상**이고, 문제가 있을 때만 말한다.

# 7. 확인은 문제를 쪼개면서

브라우저로 가기 전에 서버 쪽부터 확인한다.

```bash
curl -H "Host: notes.local" http://<DB_SERVER_IP>
```

`-H "Host: notes.local"` 은 **"내가 그 이름으로 온 것처럼 쳐줘"** 라고 가짜 헤더를 붙이는 것. 아직 그 이름을 아무도 모르는 상태이기 때문이다.

이렇게 하면 문제가 둘로 갈린다.

```
나온다      →  nginx 설정은 정상.  남은 건 이름 문제
안 나온다   →  nginx 설정 문제
```

**"안 돼요"를 "여기까진 되고 여기서 안 돼요"로 좁히는 것** — 장애 대응의 핵심이다.

> `localhost` 로 찍었더니 엉뚱하게 301이 나왔다. 이게 오늘 제일 큰 수확 →
> [막힌지점 문서](막힌지점-5가지.md) 4번

# 8. 이름 해석 — 클라이언트 쪽 일이다

여기까지는 `Host:` 헤더를 손으로 붙여야만 됐다. 브라우저에 `notes.local` 을 쳐서 되게 하려면 **접속하는 쪽**이 그 이름을 알아야 한다.

```bash
# 맥에서 (서버가 아니다!)
sudo vi /etc/hosts
```

```
<DB_SERVER_IP> notes.local
```

**이름을 풀어야 하는 건 접속하는 쪽**이다. 서버의 `/etc/hosts` 를 고쳐도 브라우저는 모른다.

여기서 실수했다 → [막힌지점 문서](막힌지점-5가지.md) 5번

## 확인

```bash
ping -c 1 notes.local     # <DB_SERVER_IP> 로 나가면 성공
curl http://notes.local
```

# 9. 방화벽 — 이번엔 할 일이 없었다

80번 포트는 arcade.local 때문에 **이미 열려 있었다.** 같은 포트를 쓰는 사이트를 추가하는 것이므로 방화벽 작업이 없다.

> 새 포트를 쓰는 사이트였다면 `firewall-cmd --add-port` 가 필요했을 것이다.
> **"이번엔 왜 필요 없는가"를 아는 것**이 절차를 외우는 것보다 중요하다.

# 10. 재부팅 검증 — 이걸 해야 끝이다

```bash
sudo systemctl reboot
```

지금 되는 것은 **"지금 이 순간 메모리에 올라와 있어서"** 일 수도 있다. 진짜 확인은 껐다 켜는 것.

```
uptime          2 min        ← 진짜로 재부팅됨
notes.local     200
arcade.local    200
443 (posture)   200
SELinux         Enforcing
nginx           active / enabled
firewalld       active
```

`nginx enabled` 가 붙어 있어야 부팅할 때 자동으로 뜬다. 이게 없으면 **재부팅 후 사이트가 전부 죽는다.**

24시간 서버는 정전이든 커널 업데이트든 반드시 재부팅된다. **재부팅 후 안 뜨는 서비스는 없는 것과 같다.**

> 끌 때는 `sudo systemctl poweroff`. UTM 창을 강제로 닫으면 파일시스템이 더러운 채로 남는다.

# 최종 체크리스트

다음에 사이트를 올릴 때 이대로 하면 된다.

```
□ 1. 문서 루트를 /var/www/<이름> 에 만든다        sudo mkdir
□ 2. index.html 을 넣는다                        sudo vi
□ 3. /etc/nginx/conf.d/<이름>.conf 를 쓴다        listen / server_name / root
□ 4. sudo nginx -t                               test is successful 확인
□ 5. sudo systemctl reload nginx
□ 6. curl -H "Host: <이름>" http://<서버IP>       nginx 쪽 확인
□ 7. 클라이언트의 /etc/hosts 에 이름 추가          맥에서!
□ 8. 재부팅 후 세 사이트 전부 확인                 이걸 해야 끝
```
