# 1. 스크립트에 판단 넣기

숫자만 보여주는 것에서, **스크립트가 판단**하게 바꿨다.

```bash
echo "--- 디스크 ---"
USE=$(df --output=pcent / | tail -1 | tr -d ' %')
if [ "$USE" -ge 80 ]; then
  echo "⚠️  경고: 루트 파티션 ${USE}% 사용 중 (기준 80%)"
else
  echo "정상: ${USE}% 사용"
fi
```

## 문법

| | 뜻 |
|---|---|
| `df --output=pcent /` | 사용률만 출력 |
| `tail -1` | 헤더 빼고 값만 |
| `tr -d ' %'` | 공백과 `%` 제거 → 숫자만 남김 |
| `if [ "$USE" -ge 80 ]` | 80 이상이면 |

**`[ ]` 안쪽 좌우에 공백이 반드시 있어야 한다.** `[$USE -ge 80]` 은 에러.

## 비교 연산자

| | |
|---|---|
| `-eq` `-ne` | 같다 / 다르다 |
| `-gt` `-ge` | 초과 / 이상 |
| `-lt` `-le` | 미만 / 이하 |

> 숫자 비교는 `-ge` 같은 형태를 쓴다. `>` `<` 는 문자열 비교나 리다이렉션으로 해석되므로 주의.

# 2. cron 으로 자동 실행

```bash
crontab -e
```

```
0 9 * * * /home/<DB_USER>/check.sh >> /home/<DB_USER>/check.log 2>&1
```

## 시간 형식

```
분  시  일  월  요일   명령
0   9   *   *   *      매일 9시 정각
```

| 예시 | 의미 |
|---|---|
| `*/10 * * * *` | 10분마다 |
| `0 */6 * * *` | 6시간마다 |
| `30 3 * * *` | 매일 새벽 3시 30분 |
| `0 0 * * 0` | 매주 일요일 자정 |

## ⚠️ cron 3대 함정

**① 경로는 전부 절대경로로** — cron은 `~` 나 `PATH` 를 모른다

```
✅ /home/<DB_USER>/check.sh
❌ ~/check.sh
```

**② 출력을 반드시 파일로** — `>> 파일 2>&1` 없으면 결과가 사라진다

**③ 등록만으로는 확인이 안 된다** — 실제로 돌 때까지 기다려야 한다

> **테스트 요령**: 임시로 `* * * * *`(1분마다)로 등록해 동작을 확인하고, 되면 실제 주기로 바꾼다.

## 겪은 문제 — crontab 이 등록 안 됨

```
$ crontab -l
no crontab for <DB_USER>
```

`crontab -e` 를 열었다가 **저장 안 하고 나온 것**. 편집기를 안 거치는 방법이 더 확실하다:

```bash
echo '0 9 * * * /home/<DB_USER>/check.sh >> /home/<DB_USER>/check.log 2>&1' | crontab -
```

`crontab -` 는 **표준입력에서 읽어 등록**한다.

> ⚠️ 이건 **기존 crontab을 통째로 덮어쓴다.** 항목이 여러 개일 때는 `crontab -e` 로 추가할 것.

## 동작 확인

```
=== rhel-db 상태 점검 ===
시각   : 2026-08-05 12:29:01     ← 사람이 아무것도 안 했는데 실행됨
...
--- 디스크 ---
정상: 10% 사용
```

**자동화의 완성 형태.** 서버가 스스로 점검하고 기록한다.

# 3. 백업 스크립트

```bash
#!/bin/bash

BACKUP_DIR=/home/<DB_USER>/backups
DATE=$(date +%Y-%m-%d)
FILE=$BACKUP_DIR/backup-$DATE.tar.gz

mkdir -p $BACKUP_DIR

tar --selinux --xattrs -czf $FILE \
  /usr/share/nginx/html \
  /etc/nginx/conf.d \
  /etc/pki/tls/certs/posture.crt \
  /home/<DB_USER>/check.sh \
  2>/dev/null

find $BACKUP_DIR -name "backup-*.tar.gz" -mtime +7 -delete

echo "백업 완료: $FILE ($(du -h $FILE | cut -f1))"
```

## tar 옵션

| | |
|---|---|
| `c` | create — 새로 묶기 |
| `z` | gzip 압축 |
| `f` | file — 결과 파일명 지정 |
| `t` | list — 내용 목록만 보기 (풀지 않음) |
| `x` | extract — 풀기 |
| `--selinux --xattrs` | **SELinux 라벨·확장속성 보존** |

## `-mtime` 주의

```
-mtime +7    7일보다 오래된 것    ← 이게 맞음
-mtime 7     정확히 7일 전 것
-mtime -7    7일 이내
```

**`+` 하나로 의미가 완전히 달라진다.** 없으면 어제 만든 백업이 지워질 수도 있다.

## 왜 오래된 걸 지우나

백업을 안 지우면 **디스크가 찬다.** 그리고 디스크가 차면 서비스가 멈춘다 — **백업하려다 장애를 만드는 셈.** 실무에서 실제로 일어나는 일이다.

# 4. ⭐ 복구 훈련 — 오늘의 본론

> **"백업이 있다"보다 "복구해봤다"가 훨씬 강하다.**

백업만 만들고 복구를 안 해보면 정작 필요할 때 안 되는 경우가 많다. 실무에서 분기마다 복구 훈련을 하는 이유.

## ① 일부러 망가뜨리기

```bash
sudo mv /usr/share/nginx/html /usr/share/nginx/html.broken
sudo mkdir /usr/share/nginx/html
curl -sk -o /dev/null -w "%{http_code}\n" https://localhost   # → 403/404
```

## ② 백업에서 복구

```bash
sudo tar xzf ~/backups/backup-$(date +%Y-%m-%d).tar.gz -C / usr/share/nginx/html
```

| 옵션 | 뜻 |
|---|---|
| `-C /` | **어디에 풀지** — 루트 기준 |
| 마지막 인자 | 특정 경로만 골라서 복구 |

> `tar` 는 경로 앞의 `/` 를 떼고 저장한다(`usr/share/...`). **절대경로로 풀리는 사고를 막기 위해서**다. 그래서 복구할 때 `-C /` 로 위치를 지정한다.

## ③ 검증에서 발견한 것 — 이게 오늘의 수확

```
복구된 라벨   unconfined_u:object_r:usr_t:s0        ← 잘못됨
올바른 라벨   unconfined_u:object_r:httpd_sys_content_t:s0
```

**`tar` 는 기본적으로 SELinux 라벨을 보존하지 않는다.**

### 그런데 응답은 200이 나왔다

RHEL targeted 정책은 `httpd_t` 가 `usr_t` 를 읽는 것도 허용하기 때문. **우연히 동작한 것**이다.

> **"동작한다"와 "올바르다"는 다르다.**
> - 정책이 바뀌거나 강화되면 **어느 날 갑자기 403**
> - 다른 SELinux 설정에서는 안 될 수 있음
> - 무엇보다 **의도한 상태가 아님**

### 해결

```bash
sudo restorecon -Rv /usr/share/nginx/html/
```

### 예방 — 백업 시 라벨도 저장

```bash
tar --selinux --xattrs -czf 파일 대상...     # 백업
tar --selinux --xattrs -xzf 파일 -C /        # 복구
```

**다만 복구 후 `restorecon` 은 습관으로 할 것.** 옵션을 빼먹을 수도 있고 다른 도구로 복구할 수도 있다. 옵션은 보험이고 `restorecon` 이 확실한 방법.

### 검증 방법

```bash
rm -rf /tmp/rt && mkdir -p /tmp/rt
tar --selinux --xattrs -xzf 백업파일 -C /tmp/rt usr/share/nginx/html/index.html
ls -lZ /tmp/rt/usr/share/nginx/html/index.html
```

`/tmp` 에 풀었는데도 `httpd_sys_content_t` 가 나오면 **라벨이 백업에 저장된 것**이다. (`/tmp` 기본 라벨은 `user_tmp_t`)

# 5. 오늘 만난 함정 3개

## ① crontab 이 저장 안 됨

`crontab -e` → 편집기 → 저장 실패. → `crontab -` 로 파이프 입력이 확실하다.

## ② `tar` 옵션 순서

```
tar czf 파일 ...              ✅ 맨 앞이면 - 생략 가능
tar --selinux czf 파일 ...    ❌ czf 를 옵션으로 인식 못 함
tar --selinux -czf 파일 ...   ✅ - 를 붙이면 됨
```

에러 메시지: `'-Acdtrux' 옵션 중 하나를 지정해야합니다`
= **"만들지(c) 풀지(x) 뭘 할 건지 안 알려줬다"**

## ③ `2>/dev/null` 이 진짜 에러를 숨겼다

②의 에러가 `2>/dev/null` 때문에 안 보여서 **10분을 헤맸다.** 스크립트는 동작하는 것처럼 보였지만 백업 파일이 갱신되지 않고 있었다.

> **개발 중에는 에러를 보이게 두고, 동작을 확인한 뒤에 숨긴다.**
>
> 실무에서도 `2>/dev/null` 남발은 사고의 원인이다 — **cron이 매일 조용히 실패하는데 아무도 모르는 상황**이 생긴다.

**증상 판별법**: 스크립트를 실행했는데 결과 파일의 타임스탬프가 안 바뀌면, 조용히 실패하고 있는 것이다.

# 6. 실무 백업은 어떻게 하나

## GFS (Grandfather-Father-Son) — 표준 로테이션

한 가지 주기로 쌓지 않고 **여러 층으로 나눈다.**

| 층 | 주기 | 보관 |
|---|---|---|
| **일간** (Son) | 매일 | 최근 7~14일 |
| **주간** (Father) | 매주 일요일 | 최근 4~8주 |
| **월간** (Grandfather) | 매월 1일 | 최근 12개월 |
| **연간** | 매년 | 3~7년 (규제에 따라) |

```
어제 실수로 지운 파일     →  일간 백업
지난달 상태로 되돌리기    →  월간 백업
2년 전 감사 자료 요청     →  연간 백업
```

**최근 것은 촘촘하게, 오래된 것은 듬성듬성.**

## 왜 전부 안 쌓나 — 용량과 비용

```
매일 100GB × 365일 = 36TB/년
```

계층을 나눈다:

| 시점 | 저장 위치 |
|---|---|
| 최근 7일 | 빠른 디스크 (즉시 복구) |
| 1~3개월 | 저렴한 디스크 / NAS |
| 1년 이상 | **테이프, S3 Glacier** — 싸지만 꺼내는 데 시간 |

> 아직도 테이프를 쓴다. GB당 비용이 압도적으로 싸다.

## 보관 기간은 사실 법이 정한다

| 대상 | 근거 |
|---|---|
| 금융 거래 기록 | 전자금융거래법 — 5년 |
| 회계 자료 | 상법 — 10년 |
| 접속 로그·의료 기록 | 관련 법령 |

**SE가 마음대로 정하는 게 아니라, 법무·감사가 정해준 기간을 지킨다.** 그래서 백업 정책 문서가 따로 있다.

## 3-2-1 규칙

```
3개의 사본
2가지 다른 매체
1개는 다른 장소(오프사이트)
```

같은 서버에만 백업하면 **서버가 죽을 때 백업도 같이 죽는다.** 랜섬웨어가 백업까지 암호화하는 사례도 많다.

## 제일 중요한 건 보관 기간이 아니다

| 지표 | 뜻 |
|---|---|
| **RPO** (Recovery Point Objective) | 데이터를 얼마나 잃어도 되나 → **백업 주기**가 결정 |
| **RTO** (Recovery Time Objective) | 얼마 만에 복구해야 하나 → **백업 방식**이 결정 |

**10년치 백업이 있어도 복구를 못 하면 0점이다.**

## 설정 파일은 백업보다 git

```
tar 백업   시점 스냅샷. 뭐가 바뀌었는지 모름
git       변경 이력이 남음. 누가 언제 왜 바꿨는지
```

`/etc/nginx/conf.d` 같은 건 git으로 관리하는 것이 실무 방향이다.
