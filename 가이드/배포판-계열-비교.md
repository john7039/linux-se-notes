# 배포판 계열 비교 — 레드햇 ↔ 데비안

> 같은 일을 두 계열에서 각각 어떻게 하는지 **직접 확인해가며** 정리한다.
> 책에서 옮긴 표가 아니라, 두 서버에서 실제로 명령을 쳐본 결과다.

**비교 대상**

```
RHEL 10.2          내 실습 서버 — 직접 조작
Pop!_OS 24.04 LTS  관찰용 서버 — 읽기만 (권한 범위 밖은 손대지 않음)
```

> Pop!_OS는 우분투 기반이고, 우분투는 데비안 기반이다. 패키지 도구와 정책 구조는 데비안 계열 그대로다.

---

# 0. 결론부터 — 생각보다 차이가 작다

```
다른 것    패키지 명령, 방화벽 도구, 강제접근제어, 기본 경로 몇 개
같은 것    systemd, 네트워크, 권한, 프로세스, 로그, 파일시스템, SSH ...
```

**밑에 깔린 개념은 거의 같다.** 개념을 아는 사람은 `dnf` → `apt` 전환에 며칠이면 된다.
반대로 명령어만 외운 사람은 두 계열을 다 외워도 장애가 나면 못 고친다.

진짜로 다시 배워야 하는 것은 **SELinux ↔ AppArmor** 하나다. 사고방식이 다르다.

---

# 1. 한눈에 보는 대응표

| 하는 일 | 레드햇 계열 | 데비안 계열 |
|---|---|---|
| 저장소 다루기 (상위) | `dnf` | `apt` |
| 설치된 것 조회 (하위) | `rpm` | `dpkg` |
| 파일 소유 패키지 | `rpm -qf <파일>` | `dpkg -S <파일>` |
| 패키지가 설치한 파일 | `rpm -ql <패키지>` | `dpkg -L <패키지>` |
| 패키지 상세 | `rpm -qi <패키지>` | `dpkg -s <패키지>` |
| 방화벽 | `firewall-cmd` | `ufw` |
| 강제접근제어 | SELinux (**라벨**) | AppArmor (**경로**) |
| 서비스 | `systemctl` | `systemctl` — **같음** |
| 로그 | `journalctl` | `journalctl` — **같음** |

**서비스와 로그가 같은 이유**는 둘 다 systemd를 쓰기 때문이다. 배포판이 달라도 init 시스템이 같으면 이 영역은 통째로 같다.

# 2. 패키지

## 2.1 도구가 두 층이다

```
dnf  ↔  apt        저장소를 다룬다 — 검색, 의존성 해결, 다운로드
rpm  ↔  dpkg       이미 설치된 것의 DB를 조회한다 — 로컬 질의
```

**"이미 깔린 것에 대한 질문"은 하위 도구로 한다.** `dnf` 로 `-qf` 같은 걸 찾으면 헤맨다.

## 2.2 패키지가 잘게 쪼개져 있다 (레드햇)

```bash
dnf list installed | grep nginx
```

```
nginx.aarch64             2:1.26.3-6.el10_2.5    @rhel-10-...-appstream-rpms
nginx-core.aarch64        2:1.26.3-6.el10_2.5    @...
nginx-filesystem.noarch   2:1.26.3-6.el10_2.5    @...
```

| 패키지 | 역할 |
|---|---|
| `nginx` | 상위 패키지 — 나머지를 끌고 온다 |
| `nginx-core` | 실제 실행 바이너리 |
| `nginx-filesystem` | **디렉터리 구조와 `nginx` 사용자 계정** |

`nginx-filesystem` 이 `.noarch` 인 것이 힌트다 — **아키텍처 무관**. 실행 파일이 없고 디렉터리·계정 정보만 있으니 ARM이든 x86이든 같은 걸 쓴다.

> **왜 나누나** — 여러 패키지가 같은 디렉터리를 필요로 할 때 **한 군데서만 만들게** 하려고. `/etc/nginx`, `/var/log/nginx` 를 누가 만들지 다투지 않는다.

### 버전 표기 읽기

```
2 : 1.26.3 - 6.el10_2.5
↑      ↑        ↑
epoch  업스트림  레드햇 빌드 번호 + 대상 배포판(el10)
```

`el10` = Enterprise Linux 10. **같은 1.26.3 이라도 el9용과 el10용은 다른 패키지다.**
`@` 접두사는 "설치됨", 뒤는 어느 저장소에서 왔는지.

## 2.3 ⭐ 설정 파일의 소유권 — 여기가 진짜 다르다

### 레드햇 — 패키지가 설정 파일을 소유한다

```bash
rpm -qf /etc/nginx/nginx.conf
# → nginx-core-1.26.3-6.el10_2.5.aarch64
```

설정 파일이 패키지 안에 `%config` 로 들어 있다. 업데이트할 때 사용자가 고친 게 있으면 **`.rpmnew` / `.rpmsave`** 파일을 남겨 충돌을 알린다.

### 데비안 — 소유자가 없을 수 있다

```bash
dpkg -S /etc/ssh/sshd_config
# → dpkg-query: no path found matching pattern /etc/ssh/sshd_config
```

**파일은 분명히 존재하는데** 소유 패키지가 없다고 나온다. 이유:

```bash
dpkg-query -L openssh-server | grep -i sshd_config
```
```
/etc/ssh/sshd_config.d              ← 디렉터리만
/usr/share/openssh/sshd_config      ← 원본 템플릿
/usr/share/openssh/sshd_config.md5sum
```

```
① 패키지는 템플릿을 /usr/share/openssh/ 에 놓는다
② 설치 후 스크립트(postinst)가 그걸 /etc/ssh/ 로 복사한다
③ 업데이트 때는 md5sum 을 비교해 "사용자가 고쳤나"를 판단하고 물어본다
```

**패키지가 설치한 게 아니라 스크립트가 만들어낸 파일**이라 dpkg 목록에 없다.

> 데비안에도 패키지가 직접 소유하는 설정(**conffile**)은 있다. `openssh-server` 만 해도
> `/etc/default/ssh`, `/etc/pam.d/sshd`, `/etc/ssh/moduli` 는 conffile로 등록돼 있다.
> **`sshd_config` 만 특별하게 다루는 것**이다.
>
> ```bash
> dpkg-query -W -f='${Conffiles}\n' <패키지>    # conffile 목록 확인
> ```

### 실무 결론

```
❌ dpkg -S 가 빈손이다 = 손으로 만든 파일이다      ← 틀린 추론
✅ conffile 인지 한 번 더 확인해야 한다
```

## 2.4 설치 시각 — rpm에는 있고 dpkg에는 없다

### 레드햇

```bash
rpm -qi nginx-core        # Install Date 필드가 있다
rpm -q --last nginx-core  # 한 줄로
```
```
Install Date: 2026년 08월 03일 오후 02시 01분 14초
```

### 데비안 — DB에 없다. 우회로 두 개

```bash
# ① 패키지 관리자 로그
zcat /var/log/dpkg.log.*.gz | grep " install openssh-server"
cat /var/log/dpkg.log

# ② 파일 목록이 만들어진 시각
ls -l /var/lib/dpkg/info/openssh-server.list
# → -rw-r--r-- 1 root root 1219 Mar 18 23:05
```

```
rpm    DB에 설치 시각을 저장     →  언제 조회해도 나온다
dpkg   로그에만 흔적이 남는다    →  logrotate 로 회전되면 사라진다
```

②는 **정식 조회가 아니라 추론**이다. 누가 그 파일을 건드리면 틀어진다.

> `/var/log/dpkg.log` 가 0바이트여도 놀라지 말 것. 회전돼서 `.1`, `.10.gz` 로 밀려 있다.
> 압축본은 `cat` 이 아니라 **`zcat` / `zless`** 로 읽는다.

### 서명 — 여기는 두 계열이 같다

```
RSA/SHA256                 Key ID 199e2f91fd431d51
ML-DSA-87+Ed448/SHA512     Key ID fcd355b305707a62   ← 양자내성 서명
```

RHEL 10부터 **양자내성 서명(post-quantum)** 이 함께 들어간다. 데비안 계열도 GPG 서명으로 같은 일을 한다 — **패키지에 서명이 있고, 설치 전에 검증한다**는 구조는 동일.

# 3. 방화벽

## 3.1 firewalld는 zone, ufw는 목록

```bash
sudo firewall-cmd --list-all
```
```
public (default, active)
  interfaces: enp0s1
  services:  cockpit dhcpv6-client http https ssh
  ports:     (비어 있음)
```

**포트 번호가 아니라 서비스 이름으로 관리한다.** 정의는 `/usr/lib/firewalld/services/*.xml` 에 있다.

```
firewalld   zone 단위.  인터페이스마다 다른 정책 가능
            (public / internal / dmz / trusted ...)
ufw         zone 없음.  단순 allow/deny 목록
```

랜카드가 둘이고 하나는 외부, 하나는 내부망이면 **인터페이스마다 다른 정책**을 줄 수 있다. firewalld가 복잡한 대신 유연한 이유.

## 3.2 ⭐ 임시/영구 개념이 다르다

```
firewalld   규칙 추가 → runtime 에만 적용.  --permanent 를 따로 줘야 영구
ufw         규칙 추가 → 즉시 영구.  임시라는 개념이 거의 없다
```

ufw가 단순한 대신, **firewalld는 "시험해보고 확정"이 가능하다.** 원격 서버에서 방화벽을 잘못 건드려 자기 SSH를 끊어먹는 사고를 막을 수 있다 — runtime으로만 걸어보고, 접속이 유지되면 그때 permanent로 저장.

```bash
sudo firewall-cmd --list-all              # runtime
sudo firewall-cmd --permanent --list-all  # 영구
```

**두 목록이 같아야 정상이다.** 방화벽을 건드린 뒤 나란히 비교하는 습관을 들일 것.

## 3.3 함정 — `is-active` 를 믿지 말 것

관찰용 서버에서 모순처럼 보이는 것을 만났다.

```
systemctl is-active ufw    →  active      "켜져 있다"
/etc/ufw/ufw.conf          →  ENABLED=no  "꺼져 있다"
```

```bash
systemctl show ufw -p Type -p SubState
```
```
Type=oneshot
SubState=exited
```

`ufw.service` 는 **한 번 실행되고 끝나는 서비스**다. 계속 떠 있는 데몬이 아니다.

```
① 부팅 시 ufw-init 실행
② ufw.conf 가 ENABLED=no 라 아무것도 안 함
③ 정상 종료 → systemd 는 "실패하지 않음" 으로 기록
④ is-active 가 active (exited) 를 반환
```

> **`is-active` 는 "규칙이 적용 중"이 아니라 "유닛이 실패하지 않았다"는 뜻이다.**

### 상태 확인은 세 겹으로

| 층 | 레드햇 | 데비안 |
|---|---|---|
| 유닛이 살았나 | `systemctl is-active firewalld` | `systemctl is-active ufw` |
| 실제 정책은 | `firewall-cmd --list-all` | `ufw status verbose` |
| **진짜 커널 규칙** | `nft list ruleset` | `nft list ruleset` |

**맨 아래가 최종 진실**이다. 위 두 개는 "그렇게 되어 있을 것"이라는 보고다.

## 3.4 함정 — PATH에 `/usr/sbin` 이 없다

```bash
command -v ufw          # → 없음
ls -l /usr/sbin/ufw     # → -rwxr-xr-x  파일은 있다
echo $PATH              # → /usr/local/bin:/usr/bin:/bin:/usr/local/games:/usr/games
```

`/usr/sbin` 은 **관리자용 명령 디렉터리**라 일반 사용자 PATH에서 빠져 있다.

```
"명령이 없다" 는 결과는 "내 PATH에 없다" 는 뜻일 수 있다.
```

전체 경로로 부르거나 `sudo` 로 실행하면 된다.

# 4. ⭐ SELinux ↔ AppArmor — 여기가 진짜 다르다

## 4.1 질문 방식이 다르다

```
SELinux    "이 라벨을 가진 주체가, 저 라벨을 가진 객체에 이 동작을 해도 되나?"
AppArmor   "이 프로그램이, 이 경로에 접근해도 되나?"
```

**SELinux는 라벨, AppArmor는 경로.**

## 4.2 같은 파일, 다른 내용

```bash
cat /proc/self/attr/current
```

```
RHEL       unconfined_u:unconfined_r:unconfined_t:s0-s0:c0.c1023
Pop!_OS    unconfined
```

한쪽은 필드가 다섯, 한쪽은 단어 하나다.

### SELinux 라벨 구조

```
unconfined_u : unconfined_r : unconfined_t : s0-s0:c0.c1023
     ↑              ↑              ↑              ↑
   사용자          역할           타입          민감도 범위
    (user)        (role)        (type)        (MLS/MCS)
```

**실무에서 99%는 세 번째(타입)만 본다.**

| 타입 | 무엇 |
|---|---|
| `httpd_t` | nginx 프로세스 자신 |
| `httpd_config_t` | 설정 파일 |
| `httpd_sys_content_t` | 웹 콘텐츠 |
| `httpd_log_t` | 로그 |
| `usr_t` | 시스템 파일 |
| `unreserved_port_t` | 1024 이상 미할당 포트 |

네 번째 `s0-s0:c0.c1023` 은 MCS 범주다. 컨테이너를 여러 개 돌릴 때 같은 이미지라도 서로 못 보게 격리하는 데 쓴다.

### `unconfined_t` 가 뜻하는 것

**로그인한 내 셸은 SELinux 제한을 받지 않는다.**

RHEL 기본은 `targeted` 정책이라 **서버 데몬만 가두고 로그인 사용자는 풀어둔다.**
`getenforce` 가 `Enforcing` 인데도 내가 아무거나 할 수 있는 이유가 이것 — SELinux가 안 도는 게 아니라 **나를 대상으로 삼지 않는** 것이다.

## 4.3 실제 라벨 확인

```bash
ls -Z /etc/nginx/nginx.conf
# → system_u:object_r:httpd_config_t:s0

ps -eZ | grep nginx
# → system_u:system_r:httpd_t:s0   1412 ? nginx  (마스터)
# → system_u:system_r:httpd_t:s0   1414 ? nginx  (워커)
```

**볼 것 두 가지**

1. **설정과 콘텐츠의 타입이 다르다** — `httpd_config_t` vs `httpd_sys_content_t`.
   정책이 각각 다르게 허용한다. 설정은 읽기만, 로그는 쓰기까지.
   → **nginx가 뚫려 공격자가 nginx 권한을 얻어도, 정책에 없는 동작은 여전히 못 한다.**
   유닉스 권한만 있었으면 소유자면 다 됐을 일이 막힌다. 이게 SELinux의 값어치다.

2. **역할 필드로 주체/객체가 갈린다** — 파일은 `object_r`, 프로세스는 `system_r`.

## 4.4 AppArmor의 실제 모습

프로파일은 `/etc/apparmor.d/` 에 있다 (관찰 서버에는 121개).

```apparmor
/usr/sbin/cupsd flags=(attach_disconnected) {
  /dev/lp*          rw,        ← 프린터 장치 읽기·쓰기
  /dev/usb/lp*      rw,
  /etc/cups/        rw,
  /etc/cups/**      rw,
  /etc/foomatic/*   r,         ← 읽기만
  /{usr/,}bin/bash  ixr,       ← 실행 가능
}
```

**프로파일 하나가 그 프로그램의 허용 목록 전체**다. 열어보면 뭘 할 수 있는지 다 보인다.
SELinux는 경로가 안 나온다 — 파일이 어디 있든 **라벨만 맞으면** 된다.

> 프로파일이 없는 프로그램은 그냥 `unconfined` 다. **AppArmor는 프로파일이 있는 것만 제한한다.**
> SELinux는 모든 것에 라벨이 붙어 있다.

## 4.5 장단 비교

| | AppArmor | SELinux |
|---|---|---|
| 기본 태도 | 프로파일 있는 것만 제한 | **모두 라벨. 정책에 없으면 거부** |
| 읽기 쉬움 | ✅ 파일 하나 열면 끝 | ❌ 정책이 흩어져 있음 |
| 파일을 옮기면 | ❌ 경로가 달라져 규칙이 안 맞음 | ✅ 라벨이 파일에 붙어 따라감 |
| 하드링크·마운트 우회 | ❌ 가능 | ✅ 막힘 |
| 복구 도구 | 없음 — 프로파일을 고침 | **`restorecon`** (정책 기준 라벨 복원) |
| 배우기 | 쉬움 | 어려움 |

## 4.6 겪은 일로 대조하면

| 실제로 겪은 것 | SELinux에서 | AppArmor라면 |
|---|---|---|
| `/var/www` 밑에 만들었더니 라벨 상속 | `httpd_sys_content_t` 자동 | **그 개념 자체가 없음** |
| 403 → `restorecon` 으로 복구 | 정책 기준 라벨 복원 | **`restorecon` 이 없음** |
| 프록시 502 → `setsebool -P` | 기능 스위치를 켬 | 프로파일에 경로 추가 |

```
SELinux 세계    폴더를 어디에 만드냐가 접근 권한을 결정한다
AppArmor 세계   프로파일에 그 경로가 적혀 있느냐가 결정한다
```

# 5. 아직 안 본 것

| 주제 | 레드햇 | 데비안 |
|---|---|---|
| **스토리지** | LVM | 관찰 서버는 **ZFS** (`/home` 3.3T) |
| 서비스·로그 | systemd | systemd — 같음 (확인만 하면 됨) |
| 네트워크 설정 | `nmcli` / NetworkManager | netplan / NetworkManager |

ZFS 비교가 남아 있다. LVM 전체 사이클을 해봤으므로 대조가 된다.

```
LVM   볼륨 관리만.  파일시스템(xfs/ext4)은 따로
ZFS   볼륨 관리 + 파일시스템 + 스냅샷 + 압축 + 체크섬이 한 덩어리
```

읽기만 해도 되는 것: `zfs list`, `zfs get compression,atime <풀>`, `zpool status`

# 6. 오늘 얻은 원칙

## ① 하위 도구와 상위 도구를 구분한다

```
설치할 때        dnf / apt
이미 깔린 것 조회  rpm / dpkg
```

## ② "없다"는 결과를 곧이곧대로 믿지 않는다

```
dpkg -S 가 빈손      →  conffile 인지 한 번 더
command -v 가 없음    →  PATH 문제일 수 있다
```

## ③ 설정값 ≠ 실제 동작 (또)

```
is-active active      →  규칙이 적용 중이라는 뜻이 아니다
firewall-cmd 출력     →  runtime 인지 permanent 인지 구분
nginx -t 통과         →  실제 리스닝은 ss -tln 으로
```

**상태 확인은 한 겹으로 끝내면 안 된다.**

## ④ 개념이 같으면 계열은 며칠이면 옮겨간다

명령어 대응표를 외우는 것보다 **왜 그렇게 설계됐는지**를 아는 쪽이 오래 남는다.
`dnf`↔`apt` 는 표를 보면 되지만, SELinux↔AppArmor 는 사고방식을 바꿔야 한다.
