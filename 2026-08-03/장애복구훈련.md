## 훈련 전 기준선

```

맥 → HTTPS  200
nginx       active
```

**장애 대응의 첫걸음은 "정상이 어떤 상태인지 아는 것"이다.** 기준선을 모르면 뭐가 이상한지 판단할 수 없다.

# 훈련 #1 — 방화벽 정책 누락

## 증상

> "어제까지 잘 되던 사이트가 안 들어가져요."
> `https://<DB_SERVER_IP>` 접속 불가. HTTP는 정상.

## 진단 과정

```bash
# ① 서비스가 살아있나?
systemctl status nginx
# → active (running)  ... 서비스는 정상. 문제는 다른 층에 있다
```

```bash
# ② 범위 좁히기 — 서버 안에서는 되나?
curl -sk -o /dev/null -w "%{http_code}\n" https://localhost
# → 200
```

**이 시점의 추론:**

```
서버 안 → 200   ✅ nginx·인증서·파일 전부 정상
서버 밖 → 실패   ❌ 나가는 길 어딘가
```

의심 범위가 **방화벽 / 리스닝 주소 / 네트워크** 셋으로 줄어든다.

```bash
# ③ 방화벽 확인  ← sudo 필요
sudo firewall-cmd --list-all
```

```
services: cockpit dhcpv6-client http ssh
                                  ↑ https 가 없다
```

## 원인

방화벽 `public` zone에서 **`https` 서비스가 제거됨.**

```bash
# 심어진 고장
firewall-cmd --permanent --remove-service=https
firewall-cmd --reload
```

실무에서 실제로 일어나는 시나리오 — **누군가 방화벽 정책을 정리하다가 필요한 서비스를 같이 삭제.**

## 복구

```bash
sudo firewall-cmd --permanent --add-service=https
sudo firewall-cmd --reload
```

## 검증

```bash
# 영구 설정에 들어갔는지 (재부팅 후에도 유지되는지)
sudo firewall-cmd --permanent --list-services

# 맥에서
curl -sk -o /dev/null -w "%{http_code}\n" https://<DB_SERVER_IP>   # → 200
```

> ⚠️ **`--permanent` 확인이 중요하다.** runtime에만 추가하면 "지금은 됐는데 재부팅하면 또 터지는" 임시 복구가 된다.

## 배운 것

**"서버 안에서는 되는데 밖에서는 안 된다"를 확인하는 순간 의심 범위가 절반 이하로 줄어든다.** 이게 진단의 핵심 기술.

# 훈련 #2 — nginx 리스닝 주소 오류

## 증상

> "https 사이트가 안 됩니다."
> **훈련 #1과 겉보기 증상이 동일.** 하지만 원인은 다름.

## ⚠️ 이 훈련의 함정

**"저번에 방화벽이었으니 이번에도"** 라고 넘겨짚으면 시간을 낭비한다.
같은 증상이라도 원인은 다를 수 있다. **매번 처음부터 진단.**

## 진단 과정

```bash
# ① 서비스 확인
systemctl status nginx
# → active (running)
```

```bash
# ② 실패 방식 확인  ← 이번 훈련의 결정적 단서
curl -kv https://<DB_SERVER_IP> --max-time 8
```

```
* connect to <DB_SERVER_IP> port 443 failed: 연결이 거부됨
* Failed to connect ... after 0 ms
```

### ⭐ refused vs timeout

| 실패 방식 | 의미 | 의심할 곳 |
|---|---|---|
| **Connection refused** (즉시, 0ms) | 패킷은 **도달**했는데 받아주는 게 없음 | 서비스·리스닝 설정 |
| **Connection timed out** (한참 대기) | 패킷이 **중간에서 막힘** | 방화벽·네트워크 |

**`refused` 이므로 방화벽은 범인이 아니다.** 패킷이 통과했다는 뜻이니까.

```bash
# ③ 누가 어느 주소로 듣고 있나
ss -tln
```

```
LISTEN  0.0.0.0:22        ← 모든 주소
LISTEN  0.0.0.0:80        ← 모든 주소
LISTEN  127.0.0.1:443     ← 자기 자신만  ⚠️
```

**443번만 혼자 다르다.**

## 원인

nginx 설정의 `listen` 지시자가 루프백 주소로 한정됨.

```nginx
listen 127.0.0.1:443 ssl;    # 고장난 상태
listen 443 ssl;              # 정상
```

`127.0.0.1` 은 루프백 — 서버가 **자기 자신에게만** 열어둔 상태. 그래서:

```
curl https://localhost      → 200   (자기 자신 → 자기 자신)
curl https://<DB_SERVER_IP>  → 거부  (외부 주소로 들어오는 건 안 받음)
```

## 복구

```bash
sudo vi /etc/nginx/conf.d/posture-ssl.conf
#   listen 127.0.0.1:443 ssl;  →  listen 443 ssl;

sudo nginx -t                    # 문법 검사
sudo systemctl restart nginx     # reload 가 아니라 restart
```

### ⚠️ `reload` vs `restart`

| | 동작 | 접속 중 사용자 | 언제 |
|---|---|---|---|
| `reload` | 설정만 다시 읽음 | **안 끊김** | 대부분의 설정 변경 |
| `restart` | 프로세스 재시작 | 순간 끊김 | **리스닝 소켓 변경** 등 |

**리스닝 주소 변경은 `reload` 로 반영되지 않는 경우가 있다.** 실제로 이 훈련을 준비할 때 `reload` 로는 적용이 안 됐다.

> "reload 했는데 왜 안 바뀌지?" 싶으면 **`ss -tln` 으로 실제 상태를 확인**하는 게 답.

## 검증

```bash
ss -tln | grep 443            # → 0.0.0.0:443
curl -sk -o /dev/null -w "%{http_code}\n" https://<DB_SERVER_IP>   # 맥에서 → 200
```

## 배운 것

**증상이 같아도 원인은 다르다.** `refused`/`timeout` 이라는 한 글자 차이가 진단 방향을 완전히 바꾼다.

# 훈련 #3 — SELinux 라벨 오류

## 증상

> "사이트가 들어가지긴 하는데 화면이 이상해요. 디자인도 깨지고 버튼도 안 눌려요."
> 접속은 되고 페이지도 뜬다. 그런데 정상이 아니다.

**앞의 두 훈련과 층이 다르다.**

```
#1, #2  →  접속 자체가 안 됨   (네트워크·리스닝 층)
#3      →  접속은 되는데 이상함 (콘텐츠 층)
```

`systemctl status` 나 `ss -tln` 으로는 아무것도 안 나온다. 서비스는 완벽히 정상이기 때문.

## 진단 과정

```bash
# ① 어떤 파일이 실패하는지 특정
curl -sk -o /dev/null -w "%{http_code}\n" https://<DB_SERVER_IP>/assets/index-BqsjyAIp.js
# → 403
```

> 브라우저 **F12 → Network 탭 → 새로고침** 으로도 파일별 상태 코드를 한눈에 볼 수 있다. 빨간 줄이 실패한 요청.

웹페이지는 HTML 하나로 끝나지 않는다. 그 안에서 CSS·JS를 추가로 불러온다. **HTML은 200인데 하위 리소스가 403** 인 상황.

| 코드 | 의미 |
|---|---|
| 403 | **권한 거부** — 파일은 있는데 못 읽음 |
| 404 | 파일이 없음 |
| 500 | 서버 내부 오류 |

**403 → 원인은 둘 중 하나: 일반 권한(rwx) 또는 SELinux 라벨.**

```bash
# ② 라벨 비교
ls -lZ /usr/share/nginx/html/
```

```
unconfined_u:object_r:user_tmp_t:s0            assets       ⚠️ 혼자 다름
system_u:object_r:httpd_sys_content_t:s0       icons
unconfined_u:object_r:httpd_sys_content_t:s0   index.html
```

```bash
# ③ 증거 확보 — SELinux가 실제로 막았나  ← sudo 필요
sudo ausearch -m AVC -ts recent
```

```
avc: denied { open } for comm="nginx"
     path="/usr/share/nginx/html/assets/index-BqsjyAIp.js"
     scontext=system_u:system_r:httpd_t:s0            ← 주체: nginx 프로세스
     tcontext=unconfined_u:object_r:user_tmp_t:s0     ← 대상: 라벨이 틀림
```

**추측이 아니라 로그로 증거를 확보한 것이 핵심.**

## 원인

```bash
# 심어진 고장
chcon -R -t user_tmp_t /usr/share/nginx/html/assets
```

`assets` 디렉토리의 SELinux 타입이 `user_tmp_t` 로 변경됨. nginx(`httpd_t`)는 `httpd_sys_content_t` 만 읽을 수 있으므로 거부.

## 복구

```bash
sudo restorecon -Rv /usr/share/nginx/html/
```

| 옵션 | 뜻 |
|---|---|
| `-R` | 재귀 (하위 전부) |
| `-v` | 바뀐 것 출력 — **실제로 고쳐졌는지 눈으로 확인** |

> **`restorecon` 이 "원래 라벨"을 아는 이유** — SELinux 정책에 경로별 기본 라벨 규칙이 등록돼 있다.
> ```bash
> sudo semanage fcontext -l | grep "nginx/html"
> ```
> **기본 경로가 아닌 곳**(예: `/data/web`)은 규칙이 없어서 `restorecon` 이 소용없다. 그때는 `semanage fcontext -a` 로 규칙을 먼저 등록해야 한다.

## 검증

```bash
ls -lZ /usr/share/nginx/html/          # assets → httpd_sys_content_t
curl -sk -o /dev/null -w "%{http_code}\n" https://<DB_SERVER_IP>/assets/index-BqsjyAIp.js  # → 200
```

브라우저는 **강제 새로고침**(`Cmd+Shift+R`) — 캐시 때문에 안 바뀐 것처럼 보일 수 있다.

## 배운 것

**403은 로그로 증거를 남길 수 있다.** "어쩌다 고쳐졌다"가 아니라 장애 보고서에 쓸 수 있는 수준의 원인 규명.

# 총정리

| | 증상 | 결정적 단서 | 원인 | 복구 |
|---|---|---|---|---|
| **#1** | HTTPS 접속 불가 | **timeout** | 방화벽에서 https 제거 | `--add-service=https` + `--reload` |
| **#2** | HTTPS 접속 불가 | **refused** + `127.0.0.1:443` | nginx listen 주소 | 설정 수정 + `restart` |
| **#3** | 접속되나 화면 깨짐 | **403** + AVC 로그 | SELinux 라벨 | `restorecon -Rv` |

## 진단 원칙 3개

```
① 접속 자체가 안 되면   →  timeout(방화벽) vs refused(리스닝) 로 갈라라
② 접속은 되는데 이상하면 →  개별 파일 응답 코드를 봐라 (F12 Network / curl)
③ 403이면              →  일반 권한과 SELinux 라벨 둘 다 확인, ausearch로 증거
```

**이 세 개가 웹 서비스 장애의 8할.**

## 진단 명령 모음

```bash
# 서비스
systemctl status <서비스> --no-pager
journalctl -xeu <서비스>
systemctl is-active nginx firewalld chronyd

# 설정 문법
nginx -t
sshd -T | grep -i <옵션>

# 네트워크 · 리스닝
ss -tln                      # 리스닝 주소·포트  ← 주소도 반드시 볼 것
ss -tlnp                     # + 프로세스 (sudo 필요)
curl -kv https://주소         # 실패 방식 확인 (refused / timeout)
curl -sk -o /dev/null -w "%{http_code}\n" https://주소

# 방화벽  ← sudo 필요
sudo firewall-cmd --list-all
sudo firewall-cmd --permanent --list-services

# SELinux
ls -lZ <경로>
sudo ausearch -m AVC -ts recent          # sudo 필요
sudo sealert -a /var/log/audit/audit.log # 해결책까지 제시
sudo restorecon -Rv <경로>

# 시각
date; chronyc tracking
```

## ⚠️ 반복된 실수 — `sudo` 누락

3판 동안 **세 번** 빠뜨렸다 (`firewall-cmd`, `ausearch`).

> **시스템 전체 상태를 조회하는 명령은 대부분 root가 필요하다.** 방화벽 정책, 감사 로그, 다른 사용자의 프로세스 등.
> "조회니까 괜찮겠지"가 아니라 **보안 관련 정보는 조회조차 제한**된다고 생각할 것.

## 또 하나 — 엉뚱한 경로를 봤다

```
~/miniproject_web/dist/     ← 소스 (빌드 재료)
/usr/share/nginx/html/      ← nginx가 실제로 읽는 곳  ← 웹 문제는 항상 여기
```

# 장애 보고서 형식 (실무용)

훈련 #3을 실무 양식으로 옮기면 이렇게 된다. **이 형식으로 기록해두면 포트폴리오 자료가 된다.**

```
[2026-08-03] 웹 정적 리소스 접근 불가 (약 10분)

증상   : 페이지는 로드되나 CSS/JS가 적용되지 않음. 기능 동작 불가
영향   : 서비스 이용 불가 (화면은 뜨나 사용 불가 상태)
원인   : /usr/share/nginx/html/assets 의 SELinux 컨텍스트가
        httpd_sys_content_t → user_tmp_t 로 변경됨.
        nginx(httpd_t)의 파일 open이 거부됨 (AVC 로그 확인)
조치   : restorecon -Rv /usr/share/nginx/html/
검증   : 해당 리소스 HTTP 200 확인, 브라우저 정상 렌더링 확인
재발방지: 배포 시 cp 사용(mv 금지), 배포 후 ls -lZ 로 라벨 검증 절차 추가
```

**"백업이 있다"보다 "복구해봤다"가 강하듯, "안다"보다 "겪고 기록했다"가 강하다.**
