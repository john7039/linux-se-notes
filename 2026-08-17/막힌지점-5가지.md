# 2026-08-17 — 막힌 지점 5가지

> 세 번째 사이트를 올리면서 실제로 걸린 것들.
> **증상 → 원인 → 해결** 순으로 적어둔다. 몇 달 뒤에 또 만날 것들이라서.

| # | 증상 | 진짜 원인 | 급 |
|---|---|---|---|
| 1 | `mkdir` 허가 거부 | 디렉터리에 `w` 가 없음 | 기본 |
| 2 | vi가 **0바이트** 파일 저장 | 입력 모드에 못 들어감 | 기본 |
| 3 | `nginx -t` 가 실패 | sudo 없이 실행 | 흔함 |
| 4 | `localhost` 로 curl 하면 **301** | **localhost가 IPv6로 감** | ★ 함정 |
| 5 | 파일을 고쳤는데 반영이 안 됨 | **다른 기계를 고침** | ★ 사고 |

**4·5번이 핵심.** 1~3번은 반복하면 손에 붙는다.

# 1. mkdir 허가 거부

## 증상

```
$ mkdir /var/www/notes
mkdir: `/var/www/notes' 디렉터리를 만들 수 없습니다: 허가 거부
```

## 원인

```
$ ls -ld /var/www
drwxr-xr-x  root root  /var/www
        ↑
    그 외 사용자 = r-x.  w 가 없다
```

디렉터리에서 `w` 는 **"안에 파일을 만들거나 지울 권한"** 이다. 읽고(`r`) 들어갈(`x`) 수는 있지만 만들 수는 없는 상태.

## 해결

```bash
sudo mkdir /var/www/notes
```

## 하지 말 것

```bash
sudo chmod 777 /var/www      # ✗ 절대
```

시스템 디렉터리 권한을 헐겁게 만드는 것은 나중에 반드시 문제가 된다. 권한이 필요하면 **잠깐 빌리는 것**(sudo)이지 **영구히 열어두는 것**이 아니다.

여러 사람이 써야 하면 **그룹 + setgid** 로 푼다.

## 알아둘 것

디렉터리에 `w` 가 있으면 **남의 파일도 지울 수 있다.** 파일 자체의 권한과 무관하다.
`/tmp` 가 누구나 쓸 수 있는데도 남의 파일을 못 지우는 건 **sticky bit**(`drwxrwxrwt`) 때문.

# 2. vi가 빈 파일을 저장한다

## 증상

저장하고 나왔는데 파일이 0바이트다.

```
$ ls -l index.html
-rw-r--r--. 1 root root 0  index.html      ← 크기 0

$ cat index.html
                                            ← 아무것도 없음
```

## 원인

**명령 모드에서 타이핑했다.** vi를 열면 처음은 명령 모드라서, 친 글자들이 화면에 안 들어가고 명령으로 해석돼버린다.

| 모드 | 상태 | 전환 |
|---|---|---|
| 명령 모드 | 열자마자 여기. **타이핑해도 글자가 안 들어감** | `ESC` |
| 입력 모드 | 글자가 써짐 | `i`, `o`, `a` 등 |

## 해결

```
i            입력 모드 진입
             ↓ 화면 맨 아래에 -- INSERT -- / -- 끼워넣기 -- 가 떠야 함
내용 타이핑
ESC          명령 모드로 복귀
:wq          저장하고 종료  (w=write, q=quit)
```

**확인 지점 두 개:**
- `i` 누른 뒤 화면 **맨 아래**에 `-- INSERT --` 가 뜨는가
- `:wq` 칠 때 화면 맨 아래에 `:wq` 라고 **보이는가** (안 보이면 아직 입력 모드 → ESC 한 번 더)

## 자주 쓰는 것

| 키 | 동작 |
|---|---|
| `i` | 커서 위치에서 입력 시작 |
| `o` | 아랫줄에 새 줄 만들고 입력 시작 |
| `G` | 파일 맨 끝으로 |
| `:8` | 8행으로 이동 |
| `dd` | 커서가 있는 줄 삭제 |
| `:wq` | 저장하고 나가기 |
| `:q!` | **버리고** 나가기 |

## vi를 피하는 방법

한 줄 추가라면 vi를 안 써도 된다.

```bash
echo "내용" | sudo tee -a /etc/hosts
```

`sudo echo "내용" >> /etc/hosts` 는 **안 된다.** `>>` 는 sudo가 아니라 내 셸이 처리하는데, 셸은 일반 사용자 권한이라 파일을 못 연다.

# 3. nginx -t 가 실패한다

## 증상

```
$ nginx -t
nginx: [alert] could not open error log file: open() "/var/log/nginx/error.log" failed (13: Permission denied)
nginx: [warn] the "user" directive makes sense only if the master process runs with super-user privileges, ignored
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: [emerg] open() "/run/nginx.pid" failed (13: Permission denied)
nginx: configuration file /etc/nginx/nginx.conf test failed
```

## 출력 읽는 법 — 이게 핵심

네 줄을 갈라보면:

```
[alert] error.log ... Permission denied      ← 권한
[warn]  "user" directive ... ignored          ← 권한 때문에 파생
        syntax is ok                          ← ★ 문법은 이미 통과!
[emerg] /run/nginx.pid ... Permission denied  ← 권한.  이것 때문에 test failed
```

**`13: Permission denied` 는 문법 오류가 아니다.** 숫자 13은 errno로 "권한 없음".

문법 오류라면 전혀 다른 메시지가 나온다:

```
nginx: [emerg] unexpected "}" in /etc/nginx/conf.d/notes.conf:5
nginx: [emerg] unknown directive "server_nam" in ...
       → 파일 이름과 줄 번호를 콕 집어준다
```

## 원인

`nginx -t` 는 텍스트만 읽는 게 아니라 **실제로 뜰 수 있는지까지 흉내 낸다.** 그래서 로그 파일과 PID 파일을 열어보려 하고, 그건 root만 가능하다.

## 해결

```bash
sudo nginx -t
```

정상이면 **두 줄만** 나온다.

```
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful
```

## 교훈

오류 메시지가 여러 줄일 때 **전부 같은 원인이 아니다.** 종류를 먼저 갈라야 한다.
`Permission denied` 를 문법 오류로 오해하고 설정 파일을 뜯어보면 시간만 버린다.

# 4. ★ localhost로 curl 하면 301이 나온다

## 증상

```
$ curl -H "Host: notes.local" http://localhost
<html><head><title>301 Moved Permanently</title></head>
...
Location: https://notes.local/
```

설정은 분명히 맞는데 엉뚱한 리다이렉트가 나온다.

## 범인 좁히기

**멀쩡히 돌아가던 기존 사이트로도 찍어봤다.**

```
서버 안에서  curl -H "Host: arcade.local" http://localhost        →  301
맥에서       curl -H "Host: arcade.local" http://<DB_SERVER_IP>   →  200
```

arcade.local 도 301이 났다 = **원인이 새로 만든 설정이 아니다.** 여기서 범인이 갈렸다.

> **잘 되던 것으로 같이 찍어보기** — 이게 범인 좁히는 가장 빠른 방법이다.

## 원인 — localhost는 IPv6로 간다

요즘 리눅스에서 `localhost` 는 **`::1` (IPv6)로 먼저 해석**된다. 그리고 각 설정의 `listen` 을 보면:

```nginx
# /etc/nginx/nginx.conf — 기본 블록
server {
    listen       80 default_server;
    listen       [::]:80 default_server;      ← IPv6 도 받는다
    server_name  _;
    return 301 https://$host$request_uri;
}

# /etc/nginx/conf.d/retro-arcade.conf
server { listen 80; server_name arcade.local; ... }     ← IPv4 만

# /etc/nginx/conf.d/notes.conf
server { listen 80; server_name notes.local; ... }      ← IPv4 만
```

| 접속 경로 | 그 소켓에 있는 server 블록 | 결과 |
|---|---|---|
| `localhost` → `::1` | 기본 블록 **하나뿐** | 무조건 301 |
| `<DB_SERVER_IP>` → IPv4 | 세 개 중 이름으로 매칭 | 정상 |

**nginx는 "어느 소켓으로 들어왔나"를 먼저 보고, 그다음에 `server_name` 을 본다.**
IPv6 소켓에는 기본 블록밖에 없으니 **이름 매칭이 일어날 기회조차 없었다.**

## 해결 / 회피

확인할 때 `localhost` 대신 **IP를 명시**한다.

```bash
curl -H "Host: notes.local" http://127.0.0.1      # IPv4 강제
curl -H "Host: notes.local" http://<DB_SERVER_IP>
```

근본 해결은 각 사이트 설정에도 IPv6 listen을 추가하는 것:

```nginx
listen 80;
listen [::]:80;
```

## 다음에 이런 증상이면

> **"서버 안에서 curl 하면 이상한데 밖에서는 멀쩡해요"** — 십중팔구 이것.
> `localhost` 말고 `127.0.0.1` 로 찍어보면 바로 갈린다.

`ss -tlnp` 로 `0.0.0.0:80` 과 `[::]:80` 이 각각 뭘 물고 있는지 확인하는 습관.

# 5. ★ 파일을 고쳤는데 반영이 안 된다

## 증상

맥의 `/etc/hosts` 에 한 줄 추가했는데:

```
$ ping notes.local
ping: cannot resolve notes.local: Unknown host
```

vi에서 저장도 잘 됐고, 오류도 없었다.

## 원인 — 다른 기계를 고쳤다

```
$ ls -l /etc/hosts               # 맥
-rw-r--r--  ...  2026-08-10 13:08 /etc/hosts     ← 오늘 손댄 적이 없다

$ ssh rhel2 'grep notes /etc/hosts'
<DB_SERVER_IP> notes.local                        ← 여기 들어가 있었다
```

**ssh 세션 안에서 vi를 열었다.** 서버의 파일을 고친 것.

## 어떻게 알 수 있었나 — 프롬프트

이미 화면에 쓰여 있었다.

```
[DB <DB_USER>@rhel-db ~]$ nginx -t
              ↑
          여기가 어디인지 이미 표시돼 있음
```

| 프롬프트 | 여기는 |
|---|---|
| `[<DB_USER>@rhel-db ~]$` | **서버** |
| `Mac:~$` | **맥** |

프롬프트 읽기가 헷갈리면 확실한 방법:

```bash
hostname
```

| 나오는 값 | 여기는 |
|---|---|
| `rhel-db` | 서버 (아직 ssh 세션) |
| `Mac.local` | 맥 |

## 해결

```bash
exit          # ssh 세션 나가기
hostname      # Mac.local 확인
sudo vi /etc/hosts
```

## 이름 해석은 클라이언트 쪽 일이다

애초에 헷갈린 이유는 **"이름을 누가 풀어야 하는가"** 를 놓쳐서다.

```
브라우저가 notes.local 을 친다
   ↓
"notes.local 이 어디지?"  ← 이 질문을 하는 건 접속하는 쪽(맥)
   ↓
맥의 /etc/hosts 를 본다
```

서버는 자기 이름을 알 필요가 없다. **`/etc/hosts` 는 접속하는 기계에 있어야 한다.**

## 교훈 — 실무 사고의 씨앗

초보만 하는 실수가 아니다. **서버 여러 대를 동시에 열어놓고 작업하다 엉뚱한 서버에 명령을 때리는 사고**가 실무에서 정말 자주 난다.

오늘은 hosts 파일이라 웃고 넘겼지만, `systemctl stop` 이나 `rm` 이었으면 사고다.

```
명령 치기 전에 프롬프트 한 번 보기
```

회사에서 **운영 서버 프롬프트를 빨간색으로 바꿔놓는** 것도 같은 이유다.

# 덤 — 과거의 흔적 발견

서버의 `/etc/hosts` 를 열어보니 이런 게 있었다.

```
8:sudo sh -c 'echo <DB_SERVER_IP> arcade.local >> /etc/hosts'<DB_SERVER_IP>   arcade.local
9:<DB_SERVER_IP>   arcade.local
10:<DB_SERVER_IP> arcade.local
```

**명령어 자체가 파일 안에 들어가 있다.** 예전에 명령을 복사해서 vi에 붙여넣은 흔적. 그리고 같은 항목이 세 번 중복.

동작에는 지장이 없었다(중복은 첫 줄만 쓰인다). 하지만 이런 게 쌓이면 **나중에 원인을 못 찾는 문제**가 된다. `dd` 로 정리했다.

> **동작한다 ≠ 깨끗하다.**
> 설정 파일은 가끔 열어서 전체를 읽어볼 것.
