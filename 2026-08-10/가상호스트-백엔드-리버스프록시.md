# 2026-08-10 — 한 서버에 사이트 두 개: 가상호스트 · 백엔드 · 리버스 프록시

> 두 번째 사이트(RETRO ARCADE)를 기존 서버에 얹었다.
> **이번엔 백엔드 프로그램이 있어서** systemd·리버스 프록시·SELinux boolean이 새로 필요했다.

**결과**

```
https://<DB_SERVER_IP>   →  Posture Guard   (정적만)
http://arcade.local     →  RETRO ARCADE    (정적 + 백엔드 + DB)
```

같은 서버, 같은 nginx, 같은 포트. **설정 파일 두 개**로 갈린다.

---

# 0. 먼저 — "사이트를 올린다"의 정체

혼란스러웠던 부분을 먼저 정리한다. **올린다는 건 딱 두 가지다.**

```
① 파일을 서버 어딘가에 놓는다
② nginx에게 "이 이름으로 오면 저 폴더를 보여줘" 라고 알려준다
```

실제 설정 파일에서 **핵심은 두 줄뿐**이다.

```nginx
# 사이트 1
server_name <DB_SERVER_IP>;              ← 이 이름으로 오면
root        /usr/share/nginx/html;      ← 이 폴더를 보여줘

# 사이트 2
server_name arcade.local;               ← 이 이름으로 오면
root        /var/www/retro-arcade;      ← 이 폴더를 보여줘
```

**`server_name` = 누가 부르면 / `root` = 뭘 줄지.**

나머지(`ssl_certificate`, `access_log`, `location`…)는 세부 옵션이다.

## 그럼 오늘 한 나머지는 다 뭐였나

①②가 아닌 것들은 **특정 상황 때문에 추가로 필요했던 것**이다.

| 한 것 | 왜 | 언제 필요 |
|---|---|---|
| `restorecon` | 새로 만든 폴더라 SELinux 라벨이 안 맞음 | RHEL 계열 |
| `default_server` | 사이트가 둘이 되면서 충돌 | 사이트 2개부터 |
| **systemd 등록** | **백엔드 프로그램이 있어서** | 백엔드 있을 때 |
| **리버스 프록시** | 위와 같은 이유 | 백엔드 있을 때 |
| `setsebool` | 프록시를 SELinux가 막아서 | 프록시 쓸 때 |
| `/opt` + 전용 계정 | 백엔드를 안전하게 돌리려고 | 백엔드 있을 때 |

> **Posture Guard(8/3)는 ①②만으로 끝났다.** 백엔드가 없었으니까.
> RETRO ARCADE는 백엔드가 있어서 뒤의 것들이 줄줄이 따라왔다.

# 1. 요청 하나의 여정

`http://arcade.local/api/health` 를 쳤을 때:

```
① 맥       arcade.local 이 뭐지? → /etc/hosts → <DB_SERVER_IP>
           그 IP의 80번으로 접속하며 "Host: arcade.local" 을 같이 보냄

② nginx    Host 값을 보고 server_name 이 맞는 블록을 찾음
           → retro-arcade.conf

③ nginx    경로가 /api/ 로 시작 → 내가 처리 안 하고 127.0.0.1:8090 에 넘김
                                                    ← 리버스 프록시

④ uvicorn  요청 처리 → JSON 응답
           (systemd가 이 프로세스를 상시 관리)

⑤ nginx    받은 응답을 브라우저에 전달
```

## ⭐ 역할 분담

```
이름 → IP 변환    클라이언트(맥)의 일    /etc/hosts
어느 사이트인가   서버(nginx)의 일       server_name
```

**둘 다 있어야 한다.**
- 맥 설정만 있으면 → 엉뚱한 사이트가 나옴 (오늘 실제로 겪음)
- 서버 설정만 있으면 → 이름 자체가 해석 안 됨 (`000`)

# 2. 이름 기반 가상호스트

IP도 포트도 하나인데 사이트는 둘이다. 어떻게 구분하나?

**HTTP 요청에 `Host` 헤더가 들어있다.**

```
GET /api/health HTTP/1.1
Host: arcade.local        ← 이게 열쇠
```

nginx가 이 값을 보고 `server_name` 이 맞는 블록을 고른다.

## 실무에서도 이렇게 쓴다

```
서버 1대
├── www.회사.com     회사 홈페이지
├── admin.회사.com   관리자
├── api.회사.com     API
└── docs.회사.com    문서
```

**서브도메인마다 server 블록 하나.** 도메인 하나로 사이트를 무제한 운영한다.

# 3. ⚠️ `default_server` — 오늘 겪은 사고

`retro-arcade.conf` 를 추가했더니 **기존 사이트가 가려졌다.**
`<DB_SERVER_IP>` 으로 접속했는데 게임 사이트가 나왔다.

## 왜

```
Host: <DB_SERVER_IP> 으로 요청
  → arcade.local 과 안 맞음
  → 다른 매칭도 없음
  → "기본 서버" 로 보냄
  → 그런데 기본 서버 지정이 없어서
  → 먼저 선언된 블록(retro-arcade)이 기본이 됨   ⚠️
```

`nginx.conf` 를 보면 `include conf.d/*.conf` 가 **기본 server 블록보다 위**에 있다.
그래서 나중에 추가한 파일이 먼저 읽힌다.

## `server_name _` 는 와일드카드가 아니다

nginx에서 `_` 는 **절대 매칭되지 않는 이름**이다. 관례적으로 기본 서버 표시에 쓰지만,
**실제 효력은 `listen 80 default_server` 키워드에 있다.**

## 해결 — HTTP → HTTPS 리다이렉트로 겸사겸사

```nginx
server {
    listen       80 default_server;
    listen       [::]:80 default_server;
    server_name  _;
    return 301 https://$host$request_uri;
}
```

결과:

```
Host: arcade.local     → server_name 일치 → 게임 사이트 (리다이렉트 안 됨)
Host: <DB_SERVER_IP>    → 매칭 없음 → default_server → HTTPS 로 301
```

> **교훈**: 새 사이트를 올린 뒤 **기존 사이트도 반드시 확인**할 것.
> 실무에서 "신규 사이트 올렸더니 기존 사이트가 안 나온다"는 전형적인 사고다.

# 4. 백엔드가 생기면서 달라진 것

```
정적 사이트   파일이 그냥 놓여 있음
백엔드        살아있는 프로세스
```

프로세스가 생기니 새로운 질문이 줄줄이 따라온다.

| 질문 | 답 |
|---|---|
| 누가 실행시키나 | systemd — `enable --now` |
| 죽으면 누가 살리나 | systemd — `Restart=on-failure` |
| 재부팅하면 | systemd — `WantedBy=multi-user.target` |
| 어떤 계정으로 | 로그인 불가 전용 계정 `arcade` |
| nginx는 어떻게 부르나 | 리버스 프록시 `proxy_pass` |
| 데이터는 어디에 | `/var/lib/retro-arcade/arcade.db` |

# 5. 리버스 프록시

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8090;
    proxy_http_version 1.1;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 15s;
}
```

**"`/api/` 로 오는 건 내가 처리하지 말고 8090번한테 물어봐라"**

## ⚠️ `proxy_pass` 끝에 슬래시 금지

```
proxy_pass http://127.0.0.1:8090;    →  /api/health 가 그대로 전달
proxy_pass http://127.0.0.1:8090/;   →  /api 가 잘려서 /health 로 전달
```

## 백엔드를 `127.0.0.1` 에만 여는 이유

```bash
uvicorn app:app --host 127.0.0.1 --port 8090
```

**자기 자신에게만** 포트를 연다. 외부에서 8090에 직접 못 닿는다.

| | |
|---|---|
| 보안 | 백엔드가 인터넷에 직접 노출되지 않음. 모든 요청이 nginx를 거침 |
| HTTPS | 인증서를 nginx 한 곳에서만 관리 |
| 통합 | 사용자에겐 사이트 하나. 정적 파일과 API가 같은 도메인 |
| 확장 | 나중에 백엔드를 여러 개 띄우면 nginx가 나눠줌 |

**nginx가 문지기, 백엔드는 안쪽 방.**

# 6. systemd 서비스 등록

## 왜 필요한가 — 오늘 실제로 겪음

손으로 `uvicorn` 을 띄웠더니 세션이 끝나면서 **죽었다.** 그래서 502가 났다.

| 실행 방식 | 로그아웃 | 재부팅 |
|---|---|---|
| 셸에서 그냥 | 죽음 | 죽음 |
| tmux 안 | 살아있음 | **죽음** |
| **systemd** | **살아있음** | **살아있음** |

## 유닛 파일

```ini
[Unit]
Description=RETRO ARCADE leaderboard API
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=arcade
Group=arcade
WorkingDirectory=/opt/retro-arcade/server
Environment="ARCADE_DB=/var/lib/retro-arcade/arcade.db"
ExecStart=/opt/retro-arcade/server/.venv/bin/uvicorn app:app --host 127.0.0.1 --port 8090
Restart=on-failure
RestartSec=3

NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/var/lib/retro-arcade

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload          # 유닛 파일 변경 후 필수
sudo systemctl enable --now retro-arcade-api
systemctl status retro-arcade-api --no-pager
journalctl -xeu retro-arcade-api      # 실패하면 여기
```

## 보안 옵션

| | |
|---|---|
| `NoNewPrivileges` | 권한 상승 차단 |
| `PrivateTmp` | 전용 `/tmp` — 다른 프로세스와 격리 |
| `ProtectSystem=strict` | 시스템 경로 전체 읽기 전용 |
| `ProtectHome=true` | **`/home` 접근 차단** |
| `ReadWritePaths` | 예외적으로 쓰기 허용할 경로 |

> **`ProtectHome=true` 때문에 앱을 `/opt` 로 옮겨야 했다.**
> 앱이 홈 디렉토리에 있었으면 자기 코드를 못 읽어서 아예 안 떴을 것이다.

# 7. `/opt` 배치와 전용 계정

```bash
sudo mkdir -p /opt/retro-arcade
sudo cp -r ~/retro-arcade/server /opt/retro-arcade/
sudo rm -rf /opt/retro-arcade/server/.venv    # 홈에서 만든 venv는 경로가 박혀 못 씀

sudo useradd -r -s /sbin/nologin arcade

cd /opt/retro-arcade/server
sudo python3 -m venv .venv
sudo .venv/bin/pip install -r requirements.txt

sudo mkdir -p /var/lib/retro-arcade
sudo chown -R root:root      /opt/retro-arcade
sudo chown -R arcade:arcade  /var/lib/retro-arcade
```

## `useradd` 옵션

| | |
|---|---|
| `-r` | **시스템 계정** — UID 1000 미만, 홈 디렉토리 안 만듦 |
| `-s /sbin/nologin` | **로그인 불가** — 서비스 전용 |

> 서비스마다 전용 계정을 두는 게 실무 원칙. nginx가 `nginx` 계정으로, DB가 `mysql` 계정으로 도는 이유가 같다. 앱이 뚫려도 그 계정 권한 안에서만 움직인다.

## 소유권 설계

```
/opt/retro-arcade       root:root       앱은 읽기만
/var/lib/retro-arcade   arcade:arcade   앱이 DB를 씀
```

**앱이 자기 코드를 못 고치게** 하는 구조.

## venv — `activate` 는 필요 없다

`activate` 는 **PATH 앞에 venv의 `bin` 을 끼워넣는 편의 기능**일 뿐이다.
전체 경로로 직접 부르면 같은 결과다.

```bash
/opt/retro-arcade/server/.venv/bin/uvicorn app:app
```

**systemd는 셸을 안 거치므로** `source` 같은 셸 문법을 못 쓴다. 그래서 전체 경로가 정석이다.
`sudo .venv/bin/pip install` 도 같은 원리.

# 8. ⭐ 502가 두 번, 원인은 달랐다

같은 에러 코드였지만 원인이 완전히 달랐다.

## 1차 — 백엔드가 죽어 있었다

포그라운드로 띄운 uvicorn이 세션 종료와 함께 사망.

```bash
ss -tln | grep 8090        # 없음
pgrep -af uvicorn          # 없음
```

→ systemd 등록으로 해결

## 2차 — SELinux가 연결을 막았다

백엔드는 살아있는데 nginx만 못 갔다.

```bash
curl http://127.0.0.1:8090/api/health              # 200  ← 백엔드 정상
curl -H "Host: arcade.local" http://127.0.0.1/...  # 502  ← nginx 경유만 실패
```

**이 비교 하나로 "nginx→백엔드 구간"으로 범위가 확정됐다.**

```bash
sudo tail -n 10 /var/log/nginx/retro-arcade.error.log
```

```
connect() to 127.0.0.1:8090 failed (13: Permission denied) while connecting to upstream
```

> `127.0.0.1` 은 자기 자신이고 방화벽은 루프백을 막지 않는다.
> **일반 권한으로 설명이 안 되는 거부** → SELinux 의심

```bash
sudo ausearch -m AVC -ts recent
```

```
avc: denied { name_connect } for comm="nginx" dest=8090
     scontext=system_u:system_r:httpd_t:s0            ← nginx
     tcontext=system_u:object_r:unreserved_port_t:s0  ← 8090 포트
     tclass=tcp_socket                                ← 파일이 아니라 소켓!
```

```bash
sudo setsebool -P httpd_can_network_connect on
```

## SELinux 문제는 종류가 다르다

| 언제 | 막힌 것 | 해결 |
|---|---|---|
| 8/3 | 파일 읽기 `tclass=file` | `restorecon` — **라벨**을 고침 |
| **오늘** | 포트 연결 `tclass=tcp_socket` | `setsebool -P` — **기능**을 켬 |

**파일이 아니라 소켓이라 `restorecon` 으로는 안 됐다.**
라벨의 문제가 아니라 "웹서버가 네트워크로 나가도 되는가"라는 **기능**의 문제였다.

> **왜 기본이 꺼져 있나** — 웹서버는 인터넷에 가장 먼저 노출되는 관문이라 뚫리기 쉽다.
> 뚫린 웹서버가 **내부망 다른 서버를 스캔하는 발판**이 되는 걸 막으려고 아웃바운드 연결을 기본 차단한다.
> 리버스 프록시처럼 정말 필요할 때만 관리자가 명시적으로 연다.
>
> 범위가 좁은 `httpd_can_network_connect_db` 도 있다 — DB만 필요하면 그쪽이 더 안전하다.

## SELinux 해결 3단계 (완성판)

```
① 라벨이 틀렸나?         → restorecon              (파일)
② 정책에 없는 경로인가?   → semanage fcontext       (파일)
③ 기능이 꺼져 있나?      → setsebool -P            (동작)
```

# 9. SELinux 라벨 — `/var/www` 는 정책에 있다

새로 만든 디렉토리는 **상위 디렉토리의 라벨을 상속**받는다.

```
/usr/share/nginx/html/   원래 있던 경로  →  httpd_sys_content_t 자동
/var/www/retro-arcade/   mkdir 로 생성   →  var_t 상속  ⚠️
```

확인:

```bash
sudo semanage fcontext -l | grep "/var/www"
```

```
/var/www(/.*)?    all files    system_u:object_r:httpd_sys_content_t:s0
```

**정책에 이미 등록돼 있다** → `restorecon` 만으로 해결.

```bash
sudo restorecon -Rv /var/www/
```

## 웹 관련 라벨 종류

| 라벨 | 용도 |
|---|---|
| `httpd_sys_content_t` | 읽기 전용 콘텐츠 (일반 웹 파일) |
| **`httpd_sys_rw_content_t`** | **웹서버가 쓰기도 하는 것** (업로드 폴더 등) |
| `httpd_log_t` | 로그 |
| `httpd_sys_script_exec_t` | 실행 스크립트 (CGI) |

> `wp-content`, `uploads`, `moodledata` 가 `rw` 인 이유 — 사용자가 파일을 올리는 곳이라
> 웹서버에 쓰기 권한이 필요하다.

# 10. 겪은 자잘한 것들

## `>` 프롬프트에 갇힘

따옴표·괄호가 안 닫혔거나 줄 끝에 `\` 가 있으면 셸이 "명령이 안 끝났다"고 판단해 이어받는다.

**탈출: `Ctrl-c`** — 입력하던 명령은 실행되지 않고 버려진다.

## `curl` 이 `000` 을 준다

```
000        HTTP 응답을 아예 못 받음 (DNS 실패 / 네트워크 / 포트 닫힘)
200,404…   서버가 응답함 → 서버 쪽 문제
```

**`000` 이면 서버 설정을 뒤지기 전에 "거기까지 갔는지"부터 확인.**

진단 순서: `ping`(이름 해석 + 도달) → `nc -z IP 포트`(포트) → `curl`(응답)

## `.local` 도메인

`http:/127.0.0.1` 처럼 **슬래시 하나**로 쓰면 도구에 따라 다르게 동작한다. `://` 가 맞다.

| | |
|---|---|
| **가상호스트** | `Host` 헤더 → `server_name` 매칭. 설정 파일 하나 = 사이트 하나 |
| **`default_server`** | 매칭 실패 시 어디로. 없으면 **먼저 선언된 블록**이 기본이 됨 |
| **리버스 프록시** | nginx가 문지기, 백엔드는 안쪽 방. `127.0.0.1` 에만 열어 직접 노출 방지 |
| **systemd** | 프로세스 상시 관리. 죽으면 재시작, 재부팅해도 자동 |
| **`/opt` + 전용 계정** | 앱이 자기 코드를 못 고치게. 최소 권한 |
| **SELinux boolean** | 라벨이 아닌 **기능** 스위치. 세 번째 종류의 문제 |

**이 구조가 실무 웹 서비스의 표준 형태다.** 조별 프로젝트도 거의 같은 모양이 된다.

# 다음에 사이트를 하나 더 올린다면

```
1  코드 받고 구조 파악          정적인가 백엔드가 있는가
2  /var/www/<사이트> 에 복사     mv 아니라 cp, .git 제외
3  restorecon -Rv /var/www/
4  nginx server 블록 작성        server_name + root
5  default_server 확인           기존 사이트가 안 가려지는지
6  클라이언트에 이름 등록         /etc/hosts (실서비스는 DNS)
7  백엔드는 /opt + 전용 계정
8  systemd 유닛 등록             daemon-reload → enable --now
9  리버스 프록시                  proxy_pass 끝 슬래시 금지
10 setsebool -P httpd_can_network_connect on
11 재부팅 후 자동 복구 확인       ← 여기까지 해야 끝
```
