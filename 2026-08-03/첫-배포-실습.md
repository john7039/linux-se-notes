# 2026-08-03 — 첫 배포: GitHub 프로젝트를 서버에 올려 HTTPS로 서비스하기

> 개발이 아니라 **배포와 운영**을 한 날.
> GitHub 코드 → 빌드 → nginx 서빙 → HTTPS → 재부팅 자동복구까지 전 과정을 밟았다.

**대상**: `github.com/john7039/miniproject_web` (Posture Guard — 웹캠 자세 모니터링)
**서버**: `rhel-db` (<DB_SERVER_IP>)
**결과**: `https://<DB_SERVER_IP>` 에서 카메라까지 정상 동작, 재부팅 후 자동 복구 확인

---

## 0. 배포 대상 파악이 먼저다

코드를 받기 전에 **어떤 구조인지** 먼저 봤다. 이게 배포 방식을 결정한다.

```
백엔드 없음 — 순수 프론트엔드
MediaPipe·Chart.js·html2canvas → 전부 CDN에서 로드
데이터 저장 → 브라우저 localStorage
Gemini API → 브라우저에서 직접 호출
```

→ **서버가 할 일은 정적 파일을 배달하는 것뿐.** Vite로 빌드한 `dist/` 를 nginx가 서빙하면 끝.

> 같은 저장소에 Streamlit 버전(`app.py`)도 있었지만 **웹캠이 서버에 달려 있어야** 동작하므로 배포 대상이 아니다. 헤드리스 서버에 카메라는 없다.

### 확인 방법

```bash
git clone <저장소>
cat README.md package.json requirements.txt    # 실행 방식·의존성
grep -rn "fetch(\|localhost:\|http://" *.js    # 백엔드 호출 여부
grep -c "localStorage" main.js                 # 데이터 저장 위치
```

## 1. 배포 절차 (실제로 한 순서)

### ① 런타임 설치

```bash
sudo dnf install -y git nodejs
```

`npm` 은 `nodejs` 에 딸려온다. 설치 전 확인:

```bash
for c in git node npm; do printf "%-6s " $c; command -v $c >/dev/null && $c --version || echo "미설치"; done
```

### ② 코드 받기

```bash
cd ~
git clone https://github.com/john7039/miniproject_web.git
cd miniproject_web
```

### ③ 빌드

```bash
npm install      # 의존성 설치 (1~2분)
npm run build    # → dist/ 생성
```

> **`npm run dev` 가 아니라 `npm run build` 인 이유**
> `dev` 는 개발용 서버다. 코드 수정 자동 반영 같은 편의 기능이 붙어 있고 **성능·보안이 운영에 맞지 않으며, 터미널을 닫으면 죽는다.**
> `build` 는 **정적 파일 묶음(`dist/`)** 을 만든다. 그걸 nginx가 서빙하는 것이 실제 배포 방식.

### ④ nginx 설치·기동

```bash
sudo dnf install -y nginx
sudo systemctl enable --now nginx
sudo firewall-cmd --permanent --add-service=http
sudo firewall-cmd --reload
```

`enable --now` = 부팅 시 자동시작 등록 + 지금 시작.

### ⑤ 문서 루트로 배포

```bash
sudo cp -r dist/* /usr/share/nginx/html/
ls -lZ /usr/share/nginx/html/
```

라벨이 **`httpd_sys_content_t`** 인지 확인. 아니면 `sudo restorecon -Rv /usr/share/nginx/html/`

### ⑥ HTTPS 구성

```bash
sudo openssl req -x509 -nodes -newkey rsa:2048 \
  -keyout /etc/pki/tls/private/posture.key \
  -out /etc/pki/tls/certs/posture.crt \
  -days 365 \
  -subj "/C=KR/ST=Seoul/O=PostureGuard/CN=<DB_SERVER_IP>" \
  -addext "subjectAltName=IP:<DB_SERVER_IP>"

sudo chmod 600 /etc/pki/tls/private/posture.key
```

`/etc/nginx/conf.d/posture-ssl.conf`:

```nginx
server {
    listen 443 ssl;
    server_name <DB_SERVER_IP>;

    ssl_certificate     /etc/pki/tls/certs/posture.crt;
    ssl_certificate_key /etc/pki/tls/private/posture.key;

    root  /usr/share/nginx/html;
    index index.html;
}
```

```bash
sudo nginx -t              # 문법 검사 — 반드시!
sudo systemctl reload nginx
sudo firewall-cmd --permanent --add-service=https
sudo firewall-cmd --reload
```

## 2. ⭐ HTTPS가 필수였던 이유 — 보안 컨텍스트

**웹캠(`getUserMedia`)은 보안 컨텍스트에서만 동작한다.**

| 주소 | 카메라 |
|---|---|
| `https://...` | ✅ |
| `http://localhost` | ✅ (예외적으로 허용) |
| `http://<DB_SERVER_IP>` | ❌ **차단** |

`http://` 로 접속하면 화면은 뜨는데 카메라 권한 요청조차 안 뜬다. 이것 때문에 자체 서명 인증서로 HTTPS를 구성해야 했다.

### openssl 옵션

| 옵션 | 의미 |
|---|---|
| `req -x509` | CSR 대신 **인증서를 바로 생성** (자체 서명) |
| `-nodes` | 개인키에 암호를 걸지 않음 (걸면 nginx 시작마다 암호 입력) |
| `-newkey rsa:2048` | 2048비트 RSA 키 생성 |
| `-days 365` | 유효기간 |
| `-subj` | 주체 정보 (대화형 질문 건너뜀) |
| **`-addext "subjectAltName=IP:..."`** | **최신 브라우저 필수.** 없으면 CN만으로는 거부됨 |

### 자체 서명의 한계

브라우저가 `NET::ERR_CERT_AUTHORITY_INVALID` 경고를 띄운다. 실습·내부망에서는 "고급 → 이동"으로 넘어가면 되지만, **남이 쓰는 서비스에서는 불가능하다.** 정식 인증서는 도메인이 있어야 받을 수 있다(Let's Encrypt).

### `nginx -t` 를 반드시 할 것

설정에 오타가 있는 채로 `reload` 하면 nginx가 죽고 사이트가 통째로 내려간다. `mount -a` 와 같은 성격의 **"적용 전 검증"**.

그리고 `restart` 가 아니라 **`reload`** — 설정만 다시 읽어서 **접속 중인 사용자를 끊지 않는다.** 운영 중에는 항상 `reload` 를 먼저 고려한다.

## 3. 오늘 만난 함정 4개

### ① root로 작업하고 있었다

```
[<DB_USER>@rhel-db ~]$    ← 일반 계정
[root@rhel-db ~]#       ← root
```

**맨 끝 기호가 `#` 이면 root다.** 리눅스의 오랜 관례.

root로 `cd ~` 를 치면 `/root` 로 간다. 그래서 클론한 코드가 `/root/miniproject_web` 에 들어갔고, `/root` 는 권한이 `700` 이라 일반 사용자로는 보이지도 않아 한참 찾았다.

**root로 상시 작업하면 안 되는 이유**
- 오타 하나가 시스템을 날린다
- **`npm install` 을 root로 하면** 인터넷에서 받은 남의 코드가 시스템 전체 권한으로 실행된다 (npm이 경고를 띄우는 이유)
- root로 만든 파일은 소유자가 root라, 이후 일반 계정 작업에서 권한 오류가 계속 난다

> **습관에 추가: `whoami`**
> 지난주의 `hostname`(어느 서버?)에 이어 `whoami`(어느 계정?)가 필요해졌다. 사실 프롬프트에 이미 `root@rhel-db` 라고 적혀 있었다 — **프롬프트를 읽는 습관**이 핵심.

### ② 서버 시계가 4일 어긋나 있었다

```
맥      2026-08-03 13:56
서버    2026-07-30 18:41   ← 4일 느림
RTC     2026-08-03 04:56 UTC  ← 하드웨어 시계는 정확
```

**VM을 종료하지 않고 일시정지했다가 재개**하면 이렇게 된다. VM의 시계는 멈춰 있었는데 바깥은 4일이 흘렀고, 재개하면 멈춘 지점부터 다시 간다.

**왜 문제인가**

| 영역 | 문제 |
|---|---|
| TLS 인증서 | 시각이 틀리면 "아직 유효하지 않음"으로 거부될 수 있다 |
| 로그 | 장애 시각을 못 믿는다 — 트러블슈팅의 기본이 무너짐 |
| cron | 예약 작업이 엉뚱한 때 돌거나 건너뛴다 |
| 파일 타임스탬프 | 뭐가 최신인지 판단 불가 |

**해결**

```bash
sudo chronyc makestep      # 시각을 즉시 점프
chronyc tracking           # 동기화 상태·오차 확인
chronyc sources            # 참조 NTP 서버
```

> **`makestep` 이 따로 있는 이유** — `chronyd` 는 평소 시계를 아주 조금씩 빠르게/느리게 돌려 서서히 맞춘다(slew). 시각이 갑자기 점프하면 로그 순서가 꼬이고 프로그램이 오작동할 수 있어서다. 그런데 4일 차이는 서서히 맞추는 데 몇 년이 걸리므로 `makestep` 으로 강제한다.

**이 인증서를 만들기 전에 시계를 맞춰서 다행이었다.** 서버 시계가 미래였다면 "아직 유효하지 않은 인증서"로 브라우저가 거부했을 것이다.

### ③ 심볼릭 링크에 `cp` 를 했다

```bash
sudo cp -r dist/* /usr/share/nginx/html/
```

동작은 했는데 파일이 엉뚱한 곳에 들어갔다.

```
/usr/share/nginx/html/index.html  →  /usr/share/testpage/index.html   (심볼릭 링크였음)
```

**`cp` 는 링크를 덮어쓰지 않고, 링크를 따라가 그 끝의 파일에 쓴다.** 그래서 nginx의 기본 테스트 페이지 원본을 앱으로 덮어써 버렸다.

증거: 대상 파일 라벨이 `usr_t` (웹 콘텐츠용 `httpd_sys_content_t` 가 아님), 위치도 시스템 파일 자리.

**해결**

```bash
sudo rm -f /usr/share/nginx/html/index.html     # 링크 제거
sudo cp -r dist/* /usr/share/nginx/html/        # 다시 복사 → 진짜 파일 생성
ls -lZ /usr/share/nginx/html/index.html         # 맨 앞이 - 인지 확인
```

> **`ls -l` 맨 앞 글자를 보는 습관**
> ```
> -rw-r--r--   일반 파일
> lrwxrwxrwx   심볼릭 링크 (화살표 -> 도 표시됨)
> drwxr-xr-x   디렉토리
> ```
> 링크 자체를 덮어쓰려면 `cp --remove-destination` 을 쓴다.

### ④ 브라우저 캐시

서버에는 새 파일이 올라갔는데 브라우저에는 nginx 테스트 페이지가 계속 보였다.

**판별법**

```bash
curl -s http://주소 | head -20
```

`curl` 은 캐시를 쓰지 않는다. **`curl` 결과와 브라우저가 다르면 = 캐시 문제.** 서버를 의심하기 전에 이걸 먼저 확인한다.

**해결**: `Cmd + Shift + R`(강제 새로고침) 또는 시크릿 창. 개발 중엔 개발자도구(F12) → Network → **Disable cache** 체크.

## 4. 재부팅 검증 — 진짜 확인은 이것

```bash
sudo reboot
```

1~2분 뒤 아무것도 안 했는데 전부 살아났다.

```
nginx      active     ← systemctl enable
firewalld  active     ← --permanent 설정 유지
chronyd    active     ← 시각 정확
리스닝      22, 80, 443
맥 → HTTP  200 / HTTPS 200
```

### "재부팅해도 살아남게 하는 법" 총정리

| 요소 | 영구화 방법 |
|---|---|
| 서비스 실행 | `systemctl enable` |
| 방화벽 규칙 | `--permanent` + `--reload` |
| 파일 배치 | 디스크에 저장 |
| 시각 | `chronyd` enable |

지난주부터 계속 나온 **"임시 vs 영구"** 패턴이 오늘 실전으로 확인됐다.

## 5. 서비스는 로그인과 무관하다

SSH로 접속하지 않아도 웹사이트는 계속 돈다. `systemctl enable` 로 등록돼 있어서 **부팅 시 systemd가 자동으로 띄우기** 때문이다. SSH는 관리하러 들어가는 통로일 뿐.

| 실행 방식 | 로그아웃하면 | 재부팅하면 |
|---|---|---|
| 셸에서 그냥 실행 | **죽음** | 죽음 |
| `&` 백그라운드 | 상황에 따라 | 죽음 |
| tmux 안에서 | 살아있음 | **죽음** |
| **systemd 서비스** | **살아있음** | **살아있음** ✅ |

**24시간 서비스는 반드시 systemd로 등록.** 나중에 백엔드(Python/Node)를 붙이면 그것도 서비스 등록이 필요하다. 그때 `Restart=always`(죽어도 자동 재시작)도 같이 보게 된다.

## 6. 맥북 VM의 한계

**맥이 잠들면 VM도 멈춘다.** 오늘 시계가 4일 어긋나 있던 게 그 증거다.

| 방법 | 결과 |
|---|---|
| `caffeinate -imsu` + 뚜껑 열어둠 + 전원 연결 | ✅ 안전 |
| `sudo pmset -a disablesleep 1` (뚜껑 닫아도 유지) | ⚠️ 방열이 막혀 발열 위험 |
| 외부 모니터 연결 (클램셸 모드) | ✅ 정석 |

**뚜껑을 닫으면 `caffeinate` 로도 못 막는다.** 구조적 한계이고, 이것이 맥 미니가 필요한 이유다.

지금은 외부 공개를 안 했으므로 24시간 유지가 필요 없다. **실습할 때 켜고 끝나면 끄면 된다.**

> 끌 때는 **일시정지가 아니라 정상 종료**: `sudo poweroff`

## 7. 다음 단계 — 정식 공개를 위한 조건

발표장에서 웹사이트에 접속해 시연하는 것이 목표라면:

```
① 정식 HTTPS  — 자체 서명은 경고 때문에 시연 불가, 카메라도 안 켜짐
② 외부 접속   — 학교 네트워크에서 접근 가능해야
③ 당일 안정성 — 발표 5분간 확실히 떠 있어야
```

→ **도메인이 필요하다.** 정식 인증서는 도메인 없이 못 받는다.

### 공개 방식 두 가지

| | A. 포트포워딩 + Let's Encrypt | B. Cloudflare Tunnel (정식) |
|---|---|---|
| 구성 | 공유기 80/443 포워딩 + DDNS + certbot | 서버가 밖으로 연결 |
| 열린 포트 | 있음 (집 네트워크 노출) | **없음** |
| 인증서 | certbot 자동 갱신 | 자동 |
| 학습 가치 | ⭐⭐⭐ | ⭐ |
| 보안 | 공인 IP 노출, 상시 스캔 대상 | 집 IP 숨겨짐 |

**권고: 서비스는 B로, 학습은 A로 따로 (`rhel-lab` 에서 실습).**
면접에서 "둘 다 해봤고 이래서 B를 골랐다"가 가장 강력하다.

### ⭐ 발표 당일 보험

**`http://localhost` 도 보안 컨텍스트다.** 인터넷 없이도 카메라가 동작한다.

```
주 계획   https://내도메인       ← 운영 서버 시연
보험 1    노트북 localhost       ← 네트워크 문제 대비
보험 2    시연 영상 녹화         ← 최악의 상황 대비
```

"잘 되겠지"가 아니라 **"안 되면 어떻게 하지"를 미리 준비하는 것**이 실무 SE의 사고방식이다.

### 일정

```
이번 주     도메인 구입 (DNS 전파 시간 확보)
~8/14      맥 미니 환경설정
8월 중     서버 이전 → 터널 구성 → 정식 공개
9~11월     조별 프로젝트를 같은 환경에 배포, 운영 기록 축적
12월       발표
```

> **도메인 이름은 프로젝트에 종속되지 않게** 지을 것. 졸업프로젝트는 조별로 새로 만들게 되므로, 중립적인 이름을 사서 서브도메인으로 나눠 쓰는 편이 낫다.
> ```
> posture.내도메인.dev
> 팀프로젝트.내도메인.dev
> ```

## 오늘의 의미

**개발이 아니라 배포와 운영을 했다.**

지금 만들고 있는 것의 실체는 "자세 앱 서버"가 아니라 **어떤 프로젝트든 올릴 수 있는 배포 환경**이다. 앱은 교체 가능하고, nginx·HTTPS·도메인·systemd·백업·모니터링은 그대로 재사용된다.

조별 프로젝트에서도 이 포지션은 드물다:

| 역할 | 흔한가 |
|---|---|
| 프론트엔드 / 백엔드 개발 | 흔함 |
| **배포·운영 담당** | **거의 없음** |

---

## 복습 문제

<details>
<summary>1. <code>npm run dev</code> 와 <code>npm run build</code> 중 배포에 쓰는 것은? 왜?</summary>

**`npm run build`.**

`dev` 는 개발용 서버로, 코드 자동 반영 같은 편의 기능이 붙어 있고 성능·보안이 운영에 맞지 않으며 **터미널을 닫으면 죽는다.**

`build` 는 정적 파일 묶음(`dist/`)을 만들고, 그걸 nginx 같은 웹서버가 서빙하는 것이 실제 배포 방식이다.
</details>

<details>
<summary>2. <code>http://<DB_SERVER_IP></code> 으로 접속하니 화면은 뜨는데 웹캠이 안 켜진다. 왜?</summary>

**보안 컨텍스트(Secure Context) 문제.** `getUserMedia`(웹캠)는 HTTPS에서만 동작한다.

| 주소 | 카메라 |
|---|---|
| `https://...` | ✅ |
| `http://localhost` | ✅ (예외) |
| `http://192.168.x.x` | ❌ |

해결: HTTPS 구성. 실습이면 자체 서명 인증서, 공개 서비스면 도메인 + Let's Encrypt.
</details>

<details>
<summary>3. 프롬프트가 <code>[<DB_USER>@rhel-db ~]$</code> 와 <code>[root@rhel-db ~]#</code> 로 다르다. 무슨 차이인가?</summary>

**맨 끝 기호가 계정 종류를 나타낸다.** `$` = 일반 계정, `#` = root.

root로 작업하면 `cd ~` 가 `/root` 로 가고, `npm install` 이 시스템 전체 권한으로 남의 코드를 실행하며, 생성한 파일 소유자가 root가 되어 이후 권한 오류가 난다.

**`whoami` 로 확인하는 습관을 들일 것.**
</details>

<details>
<summary>4. VM의 시계가 4일 느리다. 원인과 해결은?</summary>

**원인**: VM을 종료하지 않고 일시정지했다가 재개했다. VM 시계는 멈춰 있었는데 바깥은 4일이 흘렀다.

**해결**:
```bash
sudo chronyc makestep
```

`chronyd` 는 평소 시계를 조금씩 조정(slew)하는데, 4일 차이는 그렇게 맞추는 데 몇 년이 걸리므로 `makestep` 으로 즉시 점프시킨다.

**왜 중요한가**: TLS 인증서 유효성, 로그 시각, cron 실행, 파일 타임스탬프가 전부 어긋난다.
</details>

<details>
<summary>5. <code>cp</code> 로 파일을 복사했는데 엉뚱한 위치의 파일이 바뀌었다. 왜?</summary>

**대상이 심볼릭 링크였다.** `cp` 는 링크를 덮어쓰지 않고 **링크를 따라가 그 끝의 파일에 쓴다.**

확인: `ls -l` 맨 앞 글자가 `l` 이고 `->` 화살표가 보이면 링크다.

해결: 링크를 먼저 지우고 복사하거나, `cp --remove-destination` 을 쓴다.
</details>

<details>
<summary>6. 서버 파일을 바꿨는데 브라우저에 반영이 안 된다. 서버 문제인지 어떻게 판별하나?</summary>

```bash
curl -s http://주소 | head -20
```

`curl` 은 캐시를 쓰지 않는다. **`curl` 결과가 정상이면 브라우저 캐시 문제**다.

해결: 강제 새로고침(`Cmd+Shift+R`), 시크릿 창, 개발자도구 Network 탭의 "Disable cache".
</details>

<details>
<summary>7. nginx 설정을 바꾼 뒤 반영하는 명령은? <code>restart</code> 와 <code>reload</code> 중 무엇을 쓰나?</summary>

```bash
sudo nginx -t              # ① 문법 검사 — 반드시 먼저
sudo systemctl reload nginx # ② 적용
```

**`reload`** 를 쓴다. 설정만 다시 읽어서 **접속 중인 사용자를 끊지 않는다.** `restart` 는 프로세스를 죽였다 살리므로 순간적인 서비스 중단이 생긴다.

`nginx -t` 없이 reload 하면 오타 하나로 nginx가 죽고 사이트가 통째로 내려간다.
</details>

<details>
<summary>8. SSH로 접속하지 않았는데도 웹사이트가 동작한다. 왜?</summary>

`systemctl enable nginx` 로 등록해두면 **부팅 시 systemd가 자동으로 띄운다.** 로그인 세션과 무관하다. SSH는 관리하러 들어가는 통로일 뿐이다.

| 실행 방식 | 로그아웃 | 재부팅 |
|---|---|---|
| 셸에서 실행 | 죽음 | 죽음 |
| tmux 안 | 살아있음 | **죽음** |
| **systemd 서비스** | **살아있음** | **살아있음** |
</details>
