# 2026-08-18 — 두 계열 비교, 그리고 보안은 층으로 쌓는다는 것

> 서버를 만들지 않은 날. **읽고 비교한 날**이다.
> RHEL 실습 서버와, 관찰만 허용된 Pop!_OS 서버를 나란히 놓고 같은 질문을 던졌다.

**두 서버**

```
RHEL 10.2          내 실습 서버 — 직접 조작
Pop!_OS 24.04 LTS  관찰용 서버 — 읽기만.  권한 범위 밖은 손대지 않음
```

정리된 대응표는 [배포판 계열 비교](../가이드/배포판-계열-비교.md) 로 따로 뺐다.
**이 문서에는 거기 안 들어간 것** — 어떻게 막혔고 어떻게 풀었는지, 그리고 마지막에 나눈 보안 구조 이야기를 남긴다.

# 1. 막힌 곳 세 개 — 전부 "없다"는 거짓말

오늘 걸린 세 가지가 우연히도 같은 모양이었다.

| 도구가 한 말 | 실제 |
|---|---|
| `dpkg -S` — 일치하는 경로 없음 | 파일은 존재. 다른 방식으로 관리될 뿐 |
| `command -v ufw` — 없음 | 파일은 존재. 내 PATH에 없을 뿐 |
| `systemctl is-active ufw` — active | 방화벽은 꺼져 있었음 |

**"없다"는 답을 곧이곧대로 믿으면 오판한다.** 셋 다 그 교훈이다.

## 1.1 `dpkg -S` 가 빈손이었던 건

```bash
dpkg -S /etc/ssh/sshd_config
# → dpkg-query: no path found matching pattern /etc/ssh/sshd_config

ls -l /etc/ssh/sshd_config
# → -rw-r--r-- 1 root root 3517 Jan 15 2026     ← 파일은 분명히 있다
```

패키지가 뭘 설치했는지 봤더니:

```bash
dpkg-query -L openssh-server | grep -i sshd_config
```
```
/etc/ssh/sshd_config.d              ← 디렉터리만
/usr/share/openssh/sshd_config      ← 원본 템플릿
/usr/share/openssh/sshd_config.md5sum
```

**패키지는 템플릿만 놓고, 설치 스크립트가 `/etc/ssh/` 로 복사한다.** 그래서 dpkg 파일 목록에 없다.

> 레드햇은 반대다. `rpm -qf /etc/nginx/nginx.conf` → `nginx-core` 가 소유한다.
> **설정 파일이 패키지 안에 들어 있느냐**가 두 계열의 갈림길이다.

## 1.2 `command -v ufw` 가 없다고 한 건

```bash
ls -l /usr/sbin/ufw     # -rwxr-xr-x  있다
echo $PATH              # /usr/local/bin:/usr/bin:/bin:/usr/local/games:/usr/games
```

`/usr/sbin` 이 일반 사용자 PATH에 없다. **관리자용 명령 디렉터리**라서다.

```
"명령이 없다" ≠ "프로그램이 없다"
```

## 1.3 `is-active` 가 active 인데 방화벽이 꺼져 있던 건

```
systemctl is-active ufw    →  active
/etc/ufw/ufw.conf          →  ENABLED=no
```

모순처럼 보였다. 유닛 타입을 보고 풀렸다.

```bash
systemctl show ufw -p Type -p SubState
# Type=oneshot
# SubState=exited
```

`ufw.service` 는 **한 번 실행되고 끝나는 서비스**다. 계속 떠 있는 데몬이 아니다.

```
① 부팅 시 ufw-init 실행
② ufw.conf 가 ENABLED=no 라 아무것도 안 함
③ 정상 종료 → systemd 는 "실패하지 않음" 으로 기록
④ is-active 가 active (exited) 를 반환
```

> **`is-active` 는 "규칙이 적용 중"이 아니라 "유닛이 실패하지 않았다"는 뜻이다.**

이건 어제 겪은 것과 같은 계열이다 — `nginx -t` 는 통과했는데 실제 리스닝은 IPv6 문제였던 것.

```
설정값 ≠ 실제 동작.  상태 확인은 한 겹으로 끝내면 안 된다.
```

# 2. ⭐ 오늘의 본론 — 그 서버는 방화벽이 없다

## 2.1 확인한 것

```
ufw ENABLED=no · nftables inactive · firewalld inactive
```

호스트 방화벽이 없다. 그런데 왜 굴러가고 있나? 인터페이스를 봤다.

```bash
ip -brief addr
```
```
eno2         <OBS_INTERNAL_IP>/16        ← 사설 IP
tailscale0   <TAILSCALE_IP>/32     ← Tailscale 이 추가한 가상 인터페이스
eno1, wlp8s0 DOWN
```

**공인 IP가 이 서버에 직접 붙어 있지 않다.** `10.x` 는 사설 대역이라 인터넷에서 라우팅되지 않는다.

```
인터넷
  ↓
기관 경계 방화벽 / 라우터        ← 여기가 막아준다
  ↓
내부망 <OBS_INTERNAL_IP>/16
  ↓
이 서버 (호스트 방화벽 없음)
```

**방화벽이 아니라 "네트워크 위치"로 보호받고 있는 구조**다.

## 2.2 다만 내부망에는 열려 있다

```bash
ss -tln
```
```
0.0.0.0:22      SSH
0.0.0.0:25      SMTP
0.0.0.0:111     rpcbind
0.0.0.0:2049    NFS
0.0.0.0:4xxxx   NFS 부속
```

`0.0.0.0` = **모든 인터페이스에서 받는다.** 어제 훈련 #2에서 본 `listen 127.0.0.1:443` 의 정반대다.

같은 내부망의 다른 장비는 이 포트들에 **Tailscale 인증 없이** 붙을 수 있다.

> ⚠️ 여기까지가 선이다. **기관 네트워크를 밖에서 스캔하지 않는다.** 안에서 `ss` 로 읽는 것까지.

# 3. ⭐ Tailscale 이 담당하는 것과 담당하지 않는 것

오늘 제일 크게 정리된 부분. 처음에 잘못 짚었다가 바로잡았다.

## 3.1 처음 생각했던 것 (틀림)

```
❌ "Tailscale 이 방화벽 역할을 하니까, 인증된 사람만 들어올 수 있어서 안전하다"
```

**두 군데가 틀렸다.**

## 3.2 Tailscale 은 방화벽이 아니다

```
방화벽        이미 있는 문 앞에서 "들여보낼까" 판단한다
Tailscale     문을 안 쓰고 별도 통로를 새로 만든다
```

**적용 범위가 `tailscale0` 인터페이스뿐이다.** `eno2` 로 들어오는 트래픽에는 관여하지 않는다.
그래서 `0.0.0.0:22`, `0.0.0.0:2049` 는 Tailscale과 무관하게 열려 있는 것이다.

비유하자면:

```
방화벽        건물 정문의 경비
Tailscale     건물 사이를 잇는 지하 전용 통로 (입구에 출입증 검사 있음)
```

**지하 통로가 생겼다고 정문 경비가 필요 없어지지 않는다.**

## 3.3 그래도 Tailscale 이 하는 보안은 있다

무보안 통로는 아니다. 세 가지는 한다.

```
암호화   중간에서 훔쳐봐도 못 읽음 (WireGuard)
인증     tailnet 구성원 기기만 참여
ACL      구성원 중에서도 "누가 누구에게" 제한 가능
```

그래서 "다리"보다 **"출입증 검사가 있는 전용 통로"** 가 정확하다.

## 3.4 구조 — 공유기가 아니라 "랜카드를 하나 더 꽂은 것"

```
              [ 좌표 서버 ]          ← 누가 어디 있는지만 알려줌
               /        \               실제 데이터는 안 지나감
   [ 내 맥 ]  ←—————→  [ 서버 ]
              암호화 터널
```

좌표 서버는 **전화번호부**다. 트래픽은 두 기기가 직접 주고받는다(P2P). 양쪽 다 NAT 뒤라 직통이 안 될 때만 릴레이(DERP)를 경유한다.

`ip -brief addr` 에 `tailscale0` 이 보이는 게 그 증거 — **가상 랜카드가 하나 더 꽂힌 것**이다.

### 왜 포트를 안 열어도 되나

```
포트포워딩    밖에서 안으로 들어오는 문을 연다      → 스캔 봇이 붙는다
Tailscale     양쪽이 각자 밖으로 나가는 연결을 만든다  → 열 문이 없다
```

방화벽은 보통 **나가는 연결은 허용**한다. Tailscale은 그 성질을 이용해 양쪽에서 나가는 연결을 만들고 이어붙인다. 사설 IP만 있는 서버에 집에서 접속되는 이유다.

## 3.5 "인증되면 해킹이 거의 불가능한가" — 아니다

남아 있는 경로들:

```
① 내부망 다른 장비가 뚫리면    →  <OBS_INTERNAL_IP> 에서 22 · 2049 · 25 접근 가능
② NFS(2049)                 →  전통적으로 인증이 약함. IP 신뢰 기반
③ tailnet 기기 하나가 감염     →  그 기기는 이미 "인증된 사람"
④ 키·계정 탈취               →  도난, 피싱, 맬웨어
⑤ 서버에서 도는 프로그램 취약점  →  네트워크 층과 무관
⑥ 패키지 공급망 오염
```

**③번이 인증 기반 접근의 근본 한계다.** 인증된 기기가 나쁜 짓을 하면 막을 수 없다.
내 맥이 감염되면 Tailscale은 그걸 정상 접속으로 본다.

```
❌ "인증이 있으니 안전하다"
✅ "이 층은 이걸 막고, 저 층은 저걸 막는다. 다 뚫리면 피해는 여기까지다"
```

**보안에 "불가능"이라는 단어를 쓰는 순간이 제일 위험하다.**

# 4. 정리 — 패킷 하나가 지나가는 길

```
어디서 왔든
   ↓
[ 이 서버에 도달할 수 있나 ]         ← Tailscale · 네트워크 위치
   ↓
[ 이 포트로 들어와도 되나 ]          ← firewalld     (호스트 방화벽)
   ↓
[ sshd 가 이 사람을 받아주나 ]       ← SSH 키 인증    (서비스 자체 인증)
   ↓
[ 이 프로세스가 이 파일을 만져도 되나 ] ← SELinux      (커널)
```

**층마다 묻는 질문이 다르다.** 아래로 갈수록 "이미 들어온 상태"를 전제한다.

| 층 | 담당 | 담당 안 하는 것 |
|---|---|---|
| **Tailscale** | 암호화 · 기기 인증 · tailnet ACL | 물리 랜카드로 들어오는 것 |
| **방화벽** | 포트·주소 단위 차단 (모든 경로) | 허용된 연결 뒤의 행동 |
| **서비스 인증** | 사용자가 진짜 그 사람인지 | 인증된 뒤의 행동 |
| **SELinux/AppArmor** | 침해 후 피해 범위 제한 | 애초에 들어오는 것 |
| **백업** | 다 실패했을 때 되돌리기 | 예방 |

```
Tailscale 은 "안전한 길"을 만들 뿐,
       "다른 길을 막는" 일은 방화벽이 한다.
```

# 5. 내 서버와 비교

```
관찰 서버   Tailscale ✅   firewalld ❌   AppArmor ✅
rhel2      Tailscale ❌   firewalld ✅   SELinux  ✅
맥 미니 목표  Tailscale ✅   firewalld ✅   SELinux  ✅
```

**호스트 방화벽 없이 경계에 의존하는 구성은 흔하다.** 관리가 편하고 경계 방화벽이 이미 있으니까. 다만 요즘은 이 가정을 다시 본다.

```
전통적       "내부망은 신뢰할 수 있다"    ← 경계만 지킨다
제로트러스트   "내부망도 못 믿는다"        ← 호스트마다 방어
```

내부망 장비 하나가 뚫리면 나머지가 무방비가 되기 때문이다.
8/10에 `setsebool` 을 배울 때 나온 **"뚫린 웹서버가 내부망 스캔 발판이 된다"** 가 정확히 이 시나리오다.

## 면접에서 쓸 형태

```
❌ "Tailscale 을 써서 해킹이 불가능합니다"

✅ "공인 IP에 SSH를 노출하지 않으려고 Tailscale로 접근 경로를 제한했고,
    내부에서 오는 것은 firewalld로 걸렀으며,
    침해 후 영향은 SELinux로 제한했습니다"
```

두 번째가 **뭘 막고 뭘 못 막는지 아는 사람의 말**이다.
