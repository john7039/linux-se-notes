# 1. journalctl 기본기

## 1.1 자체 필터를 먼저 쓴다

```
journalctl 필터    구조를 알고 거른다 (서비스, 시각, 우선순위, 부팅 회차)
grep              그냥 글자를 찾는다
```

**자체 필터가 있으면 그걸 먼저 쓴다.** `grep ERROR` 로 찾으면 안 되는 이유는 명확하다 —
**메시지에 "ERROR"라는 글자가 없어도 에러일 수 있다.** 등급은 내용이 아니라 **메타데이터**로 붙어 있다.

## 1.2 자주 쓰는 옵션

```bash
journalctl --help | grep -iE "boot|priority"   # 필요한 것만 좁혀서 보기
```

| 옵션 | 뜻 |
|---|---|
| `-b` | 이번 부팅 이후 |
| `-b -1` | 직전 부팅 |
| `-p err` | **그 등급 이상**만 (덜 심각한 것을 잘라냄) |
| `-u <유닛>` | 특정 서비스만 |
| `-t <태그>` | 특정 프로그램만 |
| `--no-pager` | 화면 넘김 없이 |
| `--list-boots` | 부팅 기록 목록 |
| `--header` | 저널 파일 자체의 정보 (**저장 위치 확인**) |

### 우선순위 등급

```
0 emerg    ← 제일 심각
1 alert
2 crit
3 err       ← -p err 로 자르면
4 warning   ← 이 아래는 안 나옴
5 notice
6 info
7 debug
```

숫자로 `-p 3` 이라고 써도 같다.

## 1.3 ⭐ "아무것도 안 나옴"을 의심하는 법

```bash
journalctl -b -p err --no-pager
# → -- No entries --
```

**이걸 보고 "괜찮네"로 끝내면 안 된다.** 두 가지 뜻이 있기 때문이다.

```
① 진짜 에러가 없다
② 내가 조건을 잘못 줘서 못 찾고 있다
```

**확인법은 범위를 넓혀 뭔가 나오는지 보는 것.** 넓혀도 안 나오면 도구가 이상한 것이고, 나오면 조건이 제대로 작동한 것이다.

```bash
journalctl -b -p warning --no-pager     # 한 칸 낮춰봤더니 13줄
```

**등급을 한 칸 낮춘 게 오늘 발견의 전부였다.**

# 3. 발견 ① — 시계가 또 밀렸다

```
8월 18 14:54:12   chronyd: System clock wrong by -4.742030 seconds
8월 18 14:54:08   chronyd: System clock was stepped by -4.742030 seconds
```

## ⭐ 시각이 거꾸로 찍혀 있다

14:54:12 다음 줄이 14:54:08이다. 버그가 아니라 실제로 이렇게 된 것:

```
① 14:54:12 (틀린 시계 기준)   chronyd 가 "4.7초 어긋났다" 고 기록
② chronyd 가 시계를 -4.7초 되돌림
③ 14:54:08 (고쳐진 시계 기준)  "되돌렸다" 고 기록
```

**시계를 되돌리면 로그 순서가 꼬인다.** 8/3 노트에 적어둔 문장의 실물 증거다.

> 8월엔 4일, 이번엔 4.7초. **규모만 다르고 원인은 같다** — 맥이 잠깐 멈춘 사이 VM 시계가 뒤처졌다.
> 이번엔 `chronyd` 가 자동으로 잡아 무해했지만 **구조는 그대로**다. 맥 미니 + `pmset` 이전에는 못 막는다.

# 4. 발견 ② — 호스트명이 initramfs 에 남아 있었다

부팅 초기 로그의 호스트명이 다르다.

```
8월 18 14:53:48   enp0s2  kernel: ...            ← 693줄
8월 18 14:53:50   enp0s2  systemd[1]: Switching root.   ← 여기까지
8월 18 14:53:51   rhel-db lvm[878]: ...          ← 이후
```

`hostnamectl` 은 `Static hostname: rhel-db` 로 멀쩡한데도 그렇다.

## `Switching root` 가 단서

리눅스 부팅은 두 단계다.

```
① initramfs 단계    메모리의 임시 루트파일시스템.  디스크 드라이버·LVM 준비
② Switching root    진짜 디스크로 루트를 바꿔치기
③ 본 시스템 단계     /etc/hostname 을 읽어 rhel-db 로 설정
```

**`enp0s2` 는 initramfs 안에 박혀 있는 옛 호스트명이다.** initramfs는 만들 때의 `/etc/hostname` 을 담는데, 그 이미지가 **설치 당시(호스트명이 `enp0s2` 였을 때)** 만들어졌다.

```bash
sudo dracut -f      # 현재 설정으로 initramfs 재생성 (아직 미실행)
```

## 교훈

```
7/30  설치 때 호스트명을 enp0s2 로 넣음
      → hostnamectl 로 고침
      → 겉으로는 해결
      → initramfs 에는 그대로 남음        ← 오늘 발견
```

**"고쳤다"고 생각한 것이 한 겹만 고친 것이었다.**

# 5. ⭐ 발견 ③ — 재부팅하면 로그가 사라지고 있었다

```bash
journalctl --list-boots
```
```
IDX BOOT ID    FIRST ENTRY                 LAST ENTRY
  0 85f7dc44…  2026-08-18 14:53:48         2026-08-18 15:16:29
```

**부팅 기록이 1개뿐.** 어제도 그제도 재부팅했는데 없다.

## 24시간 서버에서 이게 뜻하는 것

```
새벽에 서버가 죽음 → 자동 재부팅 → 아침에 확인
→ 죽기 직전 로그는?   →  없다
```

**장애 원인을 영영 못 찾는 상태였다.**

## 원인

```bash
journalctl --header | grep "File path"
# → /run/log/journal/...      ← 메모리
```

| 위치 | 성격 |
|---|---|
| `/run/log/journal/` | **메모리 기반. 재부팅하면 날아감** |
| `/var/log/journal/` | 디스크. 남음 |

`Storage=` 기본값이 `auto` 인데, `auto` 의 동작이 이렇다:

```
/var/log/journal/ 이 있으면    →  거기 저장 (영구)
없으면                        →  /run/log/journal/ (휘발)
```

**디렉터리 존재 여부로 결정된다.** 그 디렉터리가 없었다.

## 조치 — 다섯 단계를 거쳤다

### ① 설정 파일이 있어야 할 곳에 없었다

```bash
cat /etc/systemd/journald.conf
# → 그런 파일이나 디렉터리가 없습니다
```

RHEL 10에서는 패키지 기본값이 옮겨갔다.

```bash
man journald.conf     # SYNOPSIS 가 우선순위 순으로 경로를 알려준다
```
```
/etc/systemd/journald.conf              ← 관리자가 고치는 곳 (우선)
/usr/lib/systemd/journald.conf          ← 패키지 기본값 (여기 있었다)
/etc/systemd/journald.conf.d/*.conf     ← 조각 설정
```

> **설정 파일을 못 찾으면 `man` 의 SYNOPSIS 를 본다.** 이게 정석이다.
> 패키지 기본값 파일은 직접 고치면 안 된다 — 업데이트 때 덮어써진다.

### ② 파일 생성

```bash
printf '[Journal]\nStorage=persistent\n' | sudo tee /etc/systemd/journald.conf
```

`Storage=persistent` 한 줄만 쓰면 안 된다. **`[Journal]` 섹션 머리말이 필요**하다.

> `sudo ... > 파일` 은 안 된다. 리다이렉션은 sudo가 아니라 내 셸이 처리하므로.

### ③ 디렉터리를 직접 만들어야 했다

```bash
grep -rn "log/journal" /usr/lib/tmpfiles.d/
```
```
systemd.conf:22        z /run/log/journal 2755 root systemd-journal    ← /run 만 만든다
journal-nocow.conf:25  h /var/log/journal ...    ← h = 있을 때만 속성 조정
```

**`/var/log/journal` 을 만들어주는 규칙이 없다.** journald도 안 만들었다.

```bash
sudo mkdir -p /var/log/journal
sudo systemd-tmpfiles --create --prefix /var/log/journal
```

권한이 중요하다 — `root:systemd-journal`, `2755`(setgid). `systemd-tmpfiles` 가 규칙대로 붙여준다.

### ④ ⭐ flush 신호를 보내야 전환된다

```bash
sudo systemctl restart systemd-journald     # 이것만으로는 안 됨
sudo journalctl --flush                     # 이게 필요
```

journald는 시작할 때 **일단 `/run` 에 쓴다** (`/var` 가 아직 마운트 안 됐을 수 있으니까).
부팅 과정에서 `systemd-journal-flush.service` 가 "이제 옮겨라" 신호를 보내면 그때 전환된다.

```
14:53:51   부팅 중 flush 실행 → 그때는 /var/log/journal 이 없었음 → 아무것도 안 함
15:28:59   journald 재시작 → /run 에서 시작 → 신호를 보내주는 사람이 없음
15:30      journalctl --flush → 전환
```

### ⑤ 라벨 정정

```bash
sudo restorecon -v /etc/systemd/journald.conf    # etc_t → systemd_conf_t
```

# 6. 헛짚은 것 — 이게 제일 배울 거리

진단 도중 **SELinux 라벨이 틀린 것을 발견**했다.

```
현재      unconfined_u:object_r:etc_t:s0          ← tee 로 만들면서 붙음
정책 기대  system_u:object_r:systemd_conf_t:s0
```

그럴듯했다. 8/3에 403을 SELinux 라벨로 고친 경험도 있었다. 그런데:

```bash
sudo ausearch -m AVC -ts recent
# → <no matches>
```

**원인이 아니었다.**

```
그럴듯한 원인 ≠ 진짜 원인.  증거를 먼저 확보한다
```

여기서 바로 `restorecon` 을 하고 "고쳐졌다"고 했다면, **엉뚱한 것을 원인으로 장애기록에 적었을 것**이다.

> AVC가 `journalctl` 에 안 보인 이유도 알아둘 것 — `systemctl status systemd-journald` 에
> `Collecting audit messages is disabled` 가 떠 있었다. **감사 로그는 journald가 아니라 auditd로 간다.**
> 그래서 `journalctl` 이 아니라 `ausearch` 로 봐야 한다.

# 7. 오늘 하루를 관통한 것

## `active (exited)` 의 두 얼굴

같은 날 두 번 만났다.

```
오전  ufw.service              is-active 가 active 인데 방화벽은 꺼져 있었다
오후  systemd-journal-flush    부팅 때 한 번 돌고 끝나서 반영이 안 됐다
```

**`Type=oneshot` 은 "지금 상태"가 아니라 "그때 한 번 했다"를 뜻한다.**

## "없다"는 답을 믿지 않는다

```
dpkg -S 빈손          →  conffile 일 수 있다
command -v 없음        →  PATH 문제일 수 있다
journalctl 결과 없음   →  조건이 좁았을 수 있다
```

## 설정값 ≠ 실제 동작 (계속)

```
systemd-analyze cat-config  →  Storage=persistent 로 읽히고 있었다
journalctl --header         →  그런데도 /run 에 쓰고 있었다
```

**읽히는 것과 적용되는 것은 다르다.**
