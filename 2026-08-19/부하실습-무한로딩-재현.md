# 2026-08-19 — 무한로딩을 직접 재현하고, 뒷정리에서 크게 헤매다

> 학교 어느 대학 수강신청이 정각에 터졌다. 밖에서는 "무한로딩"만 보였다.
> **그 증상을 내 서버에 재현해서, 밖에서 못 본 "왜"를 안에서 봤다.**
> 그리고 뒷정리에서 1시간 넘게 헤맸는데, 그게 오늘 제일 큰 교훈이 됐다.

---

# 1. 시작 — 학교 서버는 밖에서만 볼 수 있었다

정각 장애를 사용자로서 겪고, **남의 서버는 찌르지 않는다**는 선을 지키며 공개 정보만 봤다.

```
확인됨(공개 정보)   온프레미스(단일 IP, CDN 없음), <L4/L7 로드밸런서> LB, <Java WAS> WAS,
                   <대기열 솔루션>(대기열) 보유하나 이 페이지엔 주석 처리, 학사 DB 연동
확인 불가          왜 느렸나 — WAS 스레드? DB 락? 커넥션 풀?  내부 지표 필요
```

> ⭐ **밖에서 알 수 있는 건 "어느 층"까지고, "왜"는 내부 지표 없이는 못 간다.**
> 이게 모니터링이 왜 필요한지의 답이다. 운영자도 지표가 없으면 추측만 한다.

**"DB가 문제일 확률 99%"** 라고 단정하려 했지만, 무한로딩을 내는 원인은 최소 셋(스레드 고갈·DB 락·커넥션 풀)이고 밖에서는 구분이 안 된다. 그래서 재현으로 넘어갔다.

---

# 2. 재현 — 무한로딩은 DB가 아니라 "일꾼이 다 찬 것"

## 2.1 재료 — 워커 1개짜리 백엔드

```
retro-arcade 백엔드:  uvicorn app:app --workers 1
```

**워커 1개 = 한 번에 요청 하나만 처리.** 학교 WAS 스레드 400개가 다 찬 상황의 축소판이다.

## 2.2 기준선부터 (정상을 알아야 이상을 안다)

```bash
curl -s -o /dev/null -w 'API: %{http_code} %{time_total}s\n' http://arcade.local/api/health
# → 0.002 ~ 0.016초    ← 이게 "정상"
```

## 2.3 부하 — 동시 요청을 몰아넣기

이 백엔드엔 이미 방어가 둘 있었다.

```python
if rate_limited(client_ip(request)):   # ① 앱 레벨 rate limit (IP당 5분에 20회)
    raise HTTPException(429, ...)
with _db_lock, db() as conn:           # ② 쓰기를 한 줄로 직렬화
```

`rate_limited` 가 `X-Forwarded-For` 첫 주소를 그대로 믿길래, 헤더를 매번 바꿔 IP를 위장해 우회했다(= 방어 없는 상태).

```bash
# 창1: POST 30개를 IP 위장해서 동시 투입
for i in $(seq 1 30); do
  curl -s ... -H "X-Forwarded-For: 10.0.0.$i" -d '{"game":"snake",...}' &
done; wait

# 창2: 그동안 단순 GET 을 반복 측정
while true; do curl -s -w "GET %{time_total}s\n" .../api/health; sleep 0.3; done
```

## 2.4 결과 — GET 이 3ms → 5초

```
정상        GET 0.003초
부하 중      GET 5초        ← 1600배
```

**GET `/api/health` 는 `{"ok":true}` 만 주는 초간단 요청**이다. DB도 거의 안 건드린다. 그런데도 5초 걸렸다.

```
워커 1개
→ POST 30개가 그 워커를 하나씩 차지
→ GET 은 줄 뒤에서 대기
→ 5초
```

> ⭐ **오늘의 핵심**: "무한로딩" = DB가 느린 게 아니라 **요청을 처리할 일꾼이 다 찬 것.**
> 이 실습에서 DB는 거의 놀고 있었다. 병목은 워커였다.
> **"DB 99%" 는 밖에서 본 추측이었다.** 안에서 보니 아니었다.

대규모 서비스로 대입하면: retro-arcade는 워커 1개가, 학교는 스레드 400개가 다 찬 것. **같은 현상, 규모만 다르다.**

# 3. 방어는 "어디서 막느냐"가 전부다

## 3.1 앱 레벨 rate limit 만으로는 부족했다

방어를 켠 상태(IP 위장 안 함)로 같은 부하를 줬더니 — **GET 시간이 별로 안 줄었다.**

이유:

```
앱 레벨 rate limit 은 요청이 워커까지 들어온 뒤에 429 를 뱉는다
→ 429 를 뱉는 것도 워커를 거쳐야 한다
→ 워커 경합 자체는 못 막는다
```

## 3.2 nginx 레벨(`limit_req`)은 확실히 달랐다

nginx에 rate limit을 걸었다. **워커 도달 전에** nginx가 쳐낸다.

```nginx
# 00-ratelimit.conf (http 블록 — include 순서상 먼저 로드되게 00- 접두)
limit_req_zone $binary_remote_addr zone=apilimit:10m rate=5r/s;

# retro-arcade.conf 의 location /api/ 안
limit_req zone=apilimit burst=10 nodelay;
```

같은 부하를 다시:

```
POST 30개 → 201: 9개 / 503: 21개 (nginx 가 즉시 거절)
GET → 0.001 ~ 0.011초   ← 부하 중에도 기준선 유지!
```

## 3.3 정리 — 앞에서 막을수록 강하다

| 방어 위치 | 무한로딩 | 이유 |
|---|---|---|
| 앱 레벨 (rate_limit) | 못 막음 (5초) | 요청이 워커까지 온 뒤 거절 |
| **프록시 레벨 (limit_req)** | **막음 (3ms 유지)** | 워커 도달 전에 거절 |
| 대기열 (<대기열 솔루션>) | 더 강함 | 접속 단계에서 대기 |

**제대로 만든 곳이 대기열을 앞단에 두는 이유가 이것.** 앱까지 들어오면 이미 늦다.
오늘 그런 서비스에 이 층이 없었거나 꺼져 있었다면, 우리가 처음 본 그 5초 무한로딩이 났을 것이다.

# 4. ⭐ 뒷정리 재앙 — 오늘 진짜 배운 것

부하 실습은 성공했다. 문제는 넣은 테스트 점수(`load*`)를 지우는 **뒷정리**였다.

## 4.1 증상

```
DELETE 를 아무리 해도 API 조회에 load* 이 계속 나온다
도중에 사이트가 502 까지 났다
```

## 4.2 헛짚은 것 세 개

```
① readonly database → SELinux 라벨(usr_t) 탓?
   ausearch -m AVC → <no matches>.  아님. (옆 파일도 다 usr_t = 정상이었다)

② readonly → 디렉터리 권한 탓?
   소유자 정상.  아님.

③ load 가 계속 보임 → uvicorn 이 '지워진 파일'을 물고 있다?
   /proc/<pid>/fd 확인 → DB 를 fd 로 안 물고 있었다.  아님.
```

## 4.3 진짜 원인 — 처음부터 다른 파일이었다

```bash
systemctl cat retro-arcade-api
```
```
User=arcade                                        ← <DB_USER> 이 아니다
Environment=ARCADE_DB=/var/lib/retro-arcade/arcade.db   ← /opt 가 아니다
```

```
내가 계속 만진 것   /opt/retro-arcade/server/arcade.db   (개발 잔재, 0행)
서비스가 쓰는 것    /var/lib/retro-arcade/arcade.db      (여기 load 31행)
```

**코드는 `/opt`, 데이터는 `/var/lib`** — 리눅스 표준 분리인데, 그걸 모르고 눈에 보이는 `/opt` 파일만 붙잡았다.
`sudo -u arcade` 로 진짜 DB에서 `DELETE` 하니 한 번에 끝났다.

## 4.4 근본 원인은 하나

```
파일·서비스를 고치기 전에, 그게 "무엇을 어느 계정으로 쓰는지" 확인 안 함
→ systemctl cat 한 줄이면 처음부터 알았다
```

곁가지로 벌어진 일들(빈 백업으로 덮을 뻔, readonly, chown 실수로 소유권 틀어짐)은 **전부 이 하나에서 파생**됐다.

## 4.5 AI 도 틀린다

이 과정에서 보조자(AI)가 **세 번 틀렸다**(SELinux·디렉터리 권한·지워진 파일). 조언을 검증 없이 그대로 실행했다면 `chown`·`restorecon` 을 엉뚱하게 걸어 더 꼬였을 것이다. 실제로 `chown <DB_USER>` 이 그런 실수였다.

```
AI 는 가설을 준다.  검증은 내가 한다.
되돌리기 어려운 명령(rm·chown·덮어쓰기)은 특히 두 번 확인.
```

상태·설정·파일 — 무엇이든 **"보이는 표면"을 믿지 말고 "실제 동작"을 확인**한다.

# 6. 얻은 것 / 남은 것

## 얻은 것
```
무한로딩의 정체 = 워커 고갈 (DB 아닐 수 있음)
방어는 앞에서 막을수록 강하다 (앱 < 프록시 < 대기열)
장애 훈련 5판 — 처음으로 '내가 만든 진짜 장애'를 복구
"고치기 전에 systemctl cat 으로 확인" 습관
AI 는 검증 대상이다
```

## 배포 취약점 발견 (맥 미니 때 반영)
```
client_ip 가 X-Forwarded-For 를 그대로 신뢰 → rate limit 우회 가능
→ nginx 가 X-Forwarded-For 를 덮어써서 진짜 접속 IP 만 넣어줘야 한다
세션 쿠키에 WAS 인스턴스 이름이 노출되는 것도 점검 대상
```

## 남은 것
```
□ WAL 모드 SQLite 백업 방법 정리 (sqlite3 .backup)
□ 모니터링에서 봐야 할 지표 = 워커 사용률·대기 큐 (자원 지표보다 먼저)
□ 학교 재공지 때: 대기 화면 뜨는지 관찰 (<대기열 솔루션> 켰는지)
```

> 학교 서버에 대한 판단은 **"증상을 봤다 + 공개 정보로 이렇게 보였다"** 까지다.
> "DB가 원인" 은 확정 못 한 추론이다. 내부 지표는 운영자만 안다.
