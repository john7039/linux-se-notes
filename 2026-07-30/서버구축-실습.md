# 2026-07-30 — 서버 구축 실습 (2번째 서버 `rhel-db`)

> 커리큘럼 순회식 학습을 접고 **직접 서버를 짓는 방식**으로 전환한 첫날.
> RHEL 10을 새로 설치하고 요구사항 8개를 혼자 충족시켰다. 명령어를 받아 치지 않고 직접 떠올렸다.

---

## 0. 왜 방식을 바꿨나

커리큘럼대로 따라가는 건 **시험공부와 다르지 않다**는 판단. 명령어를 읽어서 아는 것과 서버 앞에서 손이 움직이는 것은 다르다. 실제로 7/29 실습에서 `lvcreate`/`lvextend` 를 혼동하고 `/dev/<VG>/<LV>` 순서를 세 번 틀렸다.

**새 방침**

```
커리큘럼  →  체크리스트 (빠진 영역 확인, RHCSA 범위 대조용)
구축·운영  →  학습 방법 (실제로 익히는 방식)
```

둘은 대립하지 않는다. 혼자 만들다 보면 아는 방식만 반복하게 되므로, 커리큘럼은 "아직 안 건드린 게 뭔지" 알려주는 용도로 옆에 둔다.

## 2. VM 생성 설정 (UTM)

| 항목 | 값 | 이유 |
|---|---|---|
| 메모리 | 4096 MB | 실습용 DB 서버엔 충분. **필요한 만큼만 주는 게 서버 사이징의 기본** |
| CPU | 2 | 실습 부하는 미미 |
| 하드웨어 OpenGL | **끄기** | 서버는 GUI를 안 씀 |
| 디스크 | 20~30G | |
| 네트워크 | 공유 (기존 VM과 동일) | 같은 대역이어야 서버 간 통신 가능 |

### 설치 시 소프트웨어 선택

- 기본 환경: **`서버`** (Workstation 아님 — GUI 불필요, 공격 표면만 넓어짐)
- 추가 소프트웨어: **아무것도 선택 안 함**

> 필요한 건 나중에 `dnf install` 로 깐다. 그게 실무 원칙(**필요한 것만 설치**)이고, 필요를 느끼고 직접 설치하는 편이 기억에도 남는다.

### 설치 후

**ISO를 빼야 한다.** 안 빼면 재부팅 시 설치 화면으로 다시 부팅될 수 있다.
`VM 종료 → 설정 → 드라이브 → CD/DVD 지우기`

## 3. 오늘 걸린 곳 3개 — 전부 같은 뿌리

### ① `enp0s2` 를 인터페이스 이름으로 착각

콘솔에 `enp0s2 login:` 이 떠서 네트워크 인터페이스 이름인 줄 알았다. 실제로는 **호스트명**이었다. 설치 때 호스트명 입력란에 `enp0s2` 를 넣었던 것. 실제 인터페이스는 `enp0s1` 이었다.

> **로그인 프롬프트의 맨 앞은 항상 호스트명이다.** (`rhel-lab login:` 처럼)

이것 때문에 `nmcli` 로 없는 장치를 설정하려다 `Connection activation failed` 가 났다.

### ② `hostnamectl` 이 안 먹음

명령을 쳤는데 반영이 안 됐다. 어느 서버에서 쳤는지 불확실했던 것으로 보인다.

### ③ `.ssh/config` 를 서버에 씀

맥에 써야 할 파일을 **SSH로 접속한 서버 안에** 만들었다. `/home/<DB_USER>/.ssh/config` 에 생성됨.

---

### 세 개의 공통 원인

전부 **"지금 내가 어디에 있는가"** 문제였다. 서버가 두 대가 되니 바로 드러났다.

> ⭐ **습관: 명령 치기 전에 `hostname`**
> `Mac` → 맥 / `rhel-lab` → 1번 서버 / `rhel-db` → 2번 서버
>
> 실무에서 서버 수십 대를 오갈 때 이 습관이 사고를 가른다. 프롬프트에 호스트명이 나오게 하는 이유도 이것이다.

## 4. 새로 배운 것

### `nmcli connection add` — 프로필이 아예 없을 때

설치 시 네트워크를 켜지 않으면 연결 프로필이 없다. 이때는 `modify` 가 아니라 `add` 다.

```bash
nmcli connection show          # 프로필 목록 먼저 확인

# 프로필이 있으면
nmcli connection modify enp0s1 ipv4.method manual \
  ipv4.addresses <DB_SERVER_IP>/24 ipv4.gateway <GATEWAY_IP> ipv4.dns 8.8.8.8

# 프로필이 없으면
nmcli connection add type ethernet ifname enp0s1 con-name enp0s1 ipv4.method manual \
  ipv4.addresses <DB_SERVER_IP>/24 ipv4.gateway <GATEWAY_IP> ipv4.dns 8.8.8.8

nmcli connection up enp0s1
```

`add` 는 `modify` 앞에 **"어떤 장치(`ifname`)에 어떤 이름(`con-name`)으로 만들지"** 가 붙은 형태.

### 장치 확인 순서

```bash
ip link                  # 커널이 인식한 모든 인터페이스 (NM 무관)
nmcli device status      # NetworkManager가 보는 장치와 상태
nmcli connection show    # 설정 프로필 목록
```

`ip link` 에도 안 보이면 **VM에 네트워크 카드가 안 붙은 것** → UTM 설정 문제.

### `ssh -G` — 클라이언트 설정의 실제 적용값

```bash
ssh -G rhel2 | grep forwardx11
# forwardx11 no
```

`sshd -T`(서버 측)의 **클라이언트 버전**. `~/.ssh/config` 에 쓴 게 진짜 먹었는지 확인할 때 쓴다.

### 인터페이스 이름이 같아도 충돌하지 않는다

`rhel-lab` 도 `enp0s1`, `rhel-db` 도 `enp0s1` 이다. **이름은 각 머신 안에서만 의미가 있다.** 두 PC가 모두 `C:` 드라이브를 갖는 것과 같다. 네트워크에서 겹치면 안 되는 것은 **IP와 MAC 주소**다.

> `enp0s1` = **e**thernet + **p**ci **0** + **s**lot **1**. 하드웨어 위치로 이름을 만들기 때문에 같은 구성이면 같은 이름이 나온다.

## 5. 다시 만난 것들

### first-match-wins (또)

`~/.ssh/config` 에 `Host rhel2` 를 **`Host *` 아래**에 넣었더니 `ForwardX11 no` 가 무시됐다.

```
Host *
    ForwardX11 yes      ← 여기서 확정

Host rhel2
    ForwardX11 no       ← 무시됨
```

**접속은 됐다.** `HostName`, `User`, `IdentityFile` 은 `Host *` 에 없는 항목이라 정상 적용됐기 때문. **`Host *` 에도 있는 항목만** 무시된다. 그래서 "되긴 되는데 경고가 뜨는" 애매한 상태가 됐다.

→ **개별 호스트 블록은 항상 `Host *` 위에.**

### 설정값 ≠ 실제 동작

비밀번호 인증을 끈 뒤 두 단계로 확인했다.

```bash
sudo sshd -T | grep -i passwordauthentication      # ① 설정 파일 기준 최종값
```

```bash
# ② 실제 동작 — 맥에서 비밀번호 인증만으로 시도
ssh -o PubkeyAuthentication=no -o PreferredAuthentications=password <DB_USER>@<DB_SERVER_IP>
# → Permission denied (publickey,gssapi-keyex,gssapi-with-mic)
#                                      password 가 목록에 없음 = 차단됨
```

`sshd -T` 는 *파일에 뭐라고 적혀 있는지*만 보여준다. **재시작을 안 했다면 실제 동작은 다르다.**

### 이 서버는 `sshd_config.d/` 가 비어 있었다

```bash
sudo grep -rn "PasswordAuthentication" /etc/ssh/
```

전부 `#` 주석이었고 `sshd_config.d/*.conf` 에는 관련 설정이 없었다. 즉 **sshd 기본값(`yes`)** 으로 동작 중이었다. 그래서 본 파일 65번 줄의 주석만 풀어 `no` 로 바꾸면 됐다.

> 서버마다 다르므로 **고칠 파일은 `grep` 으로 먼저 찾는다.** 노트를 보고 경로를 그대로 옮겨 적으면 안 된다.

## 6. 재사용 가능한 서버 구축 절차서

앞으로 서버를 만들 때마다 이 순서로.

### A. VM 생성 · OS 설치
1. UTM에서 VM 생성 (메모리·CPU는 용도에 맞게 최소로)
2. 기본 환경 `서버`, 추가 소프트웨어 없음
3. 설치 중 **호스트명을 정확히 입력** (나중에 바꿔도 되지만 헷갈림의 원인)
4. 설치 후 **ISO 제거**

### B. 네트워크
5. `ip link` 로 인터페이스 이름 확인
6. `nmcli connection show` 로 프로필 유무 확인
7. `add` 또는 `modify` 로 고정 IP 설정 → `up`
8. `ip -4 -brief addr` 로 확인
9. **맥에서 `ping` 으로 외부 도달 확인**

### C. 접속
10. 맥에서 `ssh-copy-id` 로 공개키 등록
    `DISPLAY= SSH_ASKPASS_REQUIRE=never ssh-copy-id -i ~/.ssh/id_ed25519.pub 계정@IP`
11. 키 인증 접속 확인 → **이때부터 콘솔 탈출** (복붙 가능해짐)
12. `~/.ssh/config` 에 별칭 추가 — **`Host *` 위에**
13. `ssh -G 별칭` 으로 적용값 확인

### D. 기본 설정
14. `hostnamectl set-hostname` (필요시)
15. `sudo` 권한 확인 (`id` 에 `wheel`)
16. `grep -rn PasswordAuthentication /etc/ssh/` → 해당 파일 수정 → `sshd -T` 확인 → 재시작
17. 방화벽 상태 확인 (`firewall-cmd --list-all`)
18. SELinux `Enforcing` 확인 (`getenforce`)

### E. 검증
19. 맥에서 키 인증 접속 ✅
20. 맥에서 비밀번호 인증 차단 확인 ✅
21. **재부팅 후에도 전부 유지되는지 확인**

> ⚠️ **설정 파일 수정 전 백업**(`cp ... .bak`), **SSH 설정 변경 시 기존 세션 유지**는 항상.

## 복습 문제

<details>
<summary>1. 콘솔에 <code>enp0s2 login:</code> 이라고 떴다. <code>enp0s2</code>는 무엇인가?</summary>

**호스트명이다.** 로그인 프롬프트의 맨 앞은 항상 호스트명이다. 네트워크 인터페이스 이름이 아니다.

인터페이스 이름은 `ip link` 또는 `nmcli device status` 로 확인한다.
</details>

<details>
<summary>2. <code>nmcli connection up enp0s1</code> 이 "Connection activation failed" 로 실패했다. 확인할 것 3가지는?</summary>

1. `nmcli device status` — 그 장치가 목록에 있는가, STATE는?
2. `ip link show enp0s1` — `NO-CARRIER` 가 있는가? (있으면 VM에 네트워크 카드가 안 붙었거나 모드가 다름)
3. `ip link` — 장치 이름이 정말 맞는가? (`lo` 뿐이면 네트워크 카드 자체가 없음)
</details>

<details>
<summary>3. <code>nmcli connection modify</code> 가 "unknown connection" 이라며 실패한다. 왜?</summary>

**연결 프로필이 아직 없기 때문.** 설치 시 네트워크를 켜지 않으면 프로필이 생성되지 않는다.

`nmcli connection show` 로 확인하고, 없으면 `modify` 대신 **`add`** 를 쓴다.

```bash
nmcli connection add type ethernet ifname enp0s1 con-name enp0s1 ipv4.method manual ...
```
</details>

<details>
<summary>4. <code>~/.ssh/config</code> 에 <code>ForwardX11 no</code> 를 썼는데 여전히 X11 경고가 뜬다. 원인과 확인 방법은?</summary>

**first-match-wins.** `Host *` 블록이 먼저 매칭되어 `ForwardX11 yes` 가 확정됐고, 그 뒤의 `no` 는 무시된다. 개별 호스트 블록을 **`Host *` 위로** 옮겨야 한다.

확인: `ssh -G 별칭 | grep forwardx11` → 실제 적용값이 나온다.
</details>

<details>
<summary>5. 두 서버의 인터페이스 이름이 둘 다 <code>enp0s1</code> 이다. 충돌하지 않나?</summary>

**충돌하지 않는다.** 인터페이스 이름은 각 머신 안에서만 의미가 있다. 네트워크에서 겹치면 안 되는 것은 **IP 주소와 MAC 주소**다.

이름이 같은 이유는 두 VM 모두 같은 가상 슬롯(PCI 0, slot 1)에 네트워크 카드가 붙었기 때문이다.
</details>

<details>
<summary>6. 비밀번호 인증을 껐다. 진짜로 적용됐는지 확인하는 두 단계는?</summary>

```bash
# ① 설정 파일 기준 최종값
sudo sshd -T | grep -i passwordauthentication      # no 여야 함

# ② 실제 동작 — 클라이언트에서 비밀번호 인증만으로 시도
ssh -o PubkeyAuthentication=no -o PreferredAuthentications=password 계정@IP
# → 거부 메시지 괄호에 password 가 없어야 함
```

`sshd -T` 는 파일 내용만 보여준다. **재시작을 안 했으면 실제 동작은 다르다.**
</details>

<details>
<summary>7. 서버를 새로 구축할 때, 키 인증을 언제 설정하는 것이 좋은가? 왜?</summary>

**가능한 한 빨리 — 네트워크 설정 직후.**

키 인증이 되면 VM 콘솔에서 벗어나 SSH 터미널로 작업할 수 있다. 콘솔은 **복사·붙여넣기가 안 되어** 긴 명령을 손으로 쳐야 하고 오타가 나기 쉽다.

순서: 네트워크(고정 IP) → `ssh-copy-id` → 그 뒤 나머지 설정 전부 SSH로.
</details>
