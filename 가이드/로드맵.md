# 1. 시기별 계획

## 8월 남은 기간 — 맥 미니로 이사

```
□ UTM + RHEL 10 설치            혼자, 시간 재기
□ 브리지 네트워크               ← 이게 핵심. 안 하면 맥 안에 갇힌 VM
□ 고정 IP + SSH 키 인증
□ 24시간 설정 4종
     pmset             잠자기 방지
     pmset autorestart 정전 후 자동 부팅
     자동 로그인        재부팅 후 사람 없이
     launchd           VM 자동 시작
□ 저널 영구화 (구축 절차에 포함)
□ 서비스 3개 이전
□ 네 번째 사이트 — 30분 목표    8/17 은 1시간 19분이었다
```

> **24시간 설정 4종은 macOS 쪽 작업**이다. 리눅스 공부가 아니라 "리눅스를 24시간 돌리기 위한 준비". 이것 때문에 맥 미니가 필요했다.

## 9월 — 복학, 조별 졸업프로젝트 시작

```
□ 맥 미니 가동률 카운터 시작     ← 이때부터 숫자가 쌓인다
□ 조별 프로젝트를 기존 환경 위에 올리기
□ Tailscale (본인 tailnet) — 밖에서 접속이 필요해지는 시점
```

**앱은 교체 가능하고 인프라가 자산이다.** 팀에서 "배포와 운영 맡는 사람" 포지션이 그대로 강점이 된다.

## 10월 — 정보처리기사 실기

**리눅스 속도를 줄이는 구간.** 병행하지 않기로 이미 정했다.
서버는 켜두고, 장애 나면 대응하는 정도로.

# 2. 꾸준히 복습할 것

## 2.1 ⭐ 반복해서 나온 원리 다섯

23일 동안 **같은 원리가 계속 다른 얼굴로** 나왔다. 명령어보다 이게 오래 남는다.

### ① 임시 vs 영구

| 영역 | 임시 | 영구 |
|---|---|---|
| 서비스 | `systemctl start` | `systemctl enable` |
| 방화벽 | `firewall-cmd --add-xxx` | `--permanent` + `--reload` |
| 마운트 | `mount` | `/etc/fstab` |
| SELinux boolean | `setsebool` | `setsebool -P` |
| 저널 | `Storage=auto` (조건부) | `Storage=persistent` |

### ② 설정값 ≠ 실제 동작

```
nginx -t 통과          →  실제 리스닝은 IPv6 문제였다      (8/17)
is-active active       →  방화벽은 꺼져 있었다             (8/18)
cat-config 에 반영됨    →  그런데도 /run 에 쓰고 있었다      (8/18)
```

**읽히는 것과 적용되는 것은 다르다.** 최종 진실은 항상 실제 상태(`ss -tln`, `--header`, `nft list ruleset`)에 있다.

### ③ 실패 방식으로 범위를 가른다

```
timeout   패킷이 중간에서 막힘        →  방화벽 · 네트워크
refused   패킷은 도달, 받는 게 없음    →  서비스 · 리스닝 설정
403       파일은 있는데 못 읽음        →  권한 · SELinux 라벨
404       파일을 못 찾음              →  경로 설정
502       중계했는데 뒤가 응답 없음     →  백엔드 사망 또는 SELinux 차단
```

### ④ "없다"는 답을 믿지 않는다

```
dpkg -S 빈손          →  conffile 일 수 있다
command -v 없음        →  PATH 문제일 수 있다 (/usr/sbin)
journalctl 결과 없음   →  조건이 좁았을 수 있다 → 범위를 넓혀 확인
```

### ⑤ 그럴듯한 원인 ≠ 진짜 원인

```
증거를 먼저 확보한다.  고치고 나면 증거가 사라진다.
```

8/18에 SELinux 라벨이 틀린 걸 발견했지만 `ausearch` 결과 원인이 아니었다.
바로 고쳤다면 **엉뚱한 것을 원인으로 기록**했을 것이다.

## 2.2 손에 붙여야 할 절차

### 사이트 배포 8단계 — 노트 없이 나와야 한다

```
1. 문서 루트를 /var/www/<이름> 에            sudo mkdir
2. index.html                              sudo vi
3. /etc/nginx/conf.d/<이름>.conf            listen / server_name / root
4. sudo nginx -t                           test is successful
5. sudo systemctl reload nginx
6. curl -H "Host: <이름>" http://<서버IP>    nginx 쪽 확인
7. 클라이언트의 /etc/hosts                   맥에서!
8. 재부팅 후 전 사이트 확인                   이걸 해야 끝
```

### SELinux 3단계

```
① 라벨이 틀렸나?         → restorecon              (파일)
② 정책에 없는 경로인가?   → semanage fcontext       (파일)
③ 기능이 꺼져 있나?      → setsebool -P            (동작)
```

### 서비스가 안 뜰 때

```
① systemctl status        에러 메시지
② 설정 문법 검사           nginx -t · sshd -T
③ ss -tlnp                포트 충돌
④ sudo ausearch -m AVC    SELinux 차단
```

## 2.3 주기별 점검 — 습관으로 만들 것

### 서버에 붙을 때마다

```
□ 프롬프트 / hostname 확인      ← 2회 재발. 아직 습관 안 됨
□ 명령 치기 전에 대상 확인
```

### 매주

```
□ journalctl -b -p warning      노이즈와 진짜 가르기
□ df -h · free -h               디스크·메모리
□ systemctl --failed            실패한 유닛
□ 사이트 전부 응답 확인
```

### 매월

```
□ journalctl --list-boots       예상치 못한 재부팅이 있었나
□ 백업이 실제로 복구되는지 시험    "있다" 가 아니라 "해봤다"
□ 장애기록 정리 — 패턴이 보이나
□ 가이드 PDF 재생성              python3 도구/build-all.py --stale
```

### 설정을 바꿀 때마다

```
□ 바꿈 → 재시작 → 확인          세 단계를 다 해야 끝
□ 임시인가 영구인가
□ 재부팅해도 유지되나
```

# 3. 절대 하지 말 것

```
❌ setenforce 0 / SELINUX=disabled     면접 감점.  Enforcing 유지하며 해결한다
❌ chmod 777                           그룹 + setgid 로 푼다
❌ 남의 서버에 설치·설정 변경            읽기만.  허용 범위를 문서로 남길 것
❌ 확인 없이 pkill -f                   pgrep 으로 먼저.  자기 셸을 죽인다
❌ usermod -G (‑a 누락)                기존 그룹이 날아간다
❌ sudo ... > 파일                     리다이렉션은 셸이 처리한다.  tee 를 쓴다
```

# 4. 검증 지표 — 늘었는지 어떻게 아나

실력은 눈에 안 보이므로 **숫자로 남긴다.**

| 지표 | 현재 | 목표 |
|---|---|---|
| 사이트 배포 소요 | 1시간 19분 (8/17, 도움받음) | **30분 · 혼자** |
| 같은 유형 장애 2회차 진단 시간 | 기록 시작 | 절반 이하 |
| 서버 가동률 | 측정 안 함 | **99.x% (9월부터)** |
| 장애기록 | 17건 | 원인 규명률 100% 유지 |
| 재부팅 후 자동 복구 | 수동 확인 | 무조건 통과 |

> **소요 시간을 꼭 적을 것.** 진단 속도는 늘지만 눈에 안 보이므로, 적어두지 않으면 알 수 없다.
